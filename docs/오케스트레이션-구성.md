# 오케스트레이션 구성 — 소규모 모드

> 이 하네스를 **여러 세션으로 나눠 쓸 때** 그 세션들을 어떻게 엮을지 정하는 가이드다. 세션 하나로만 쓰면 이 문서는 필요 없다. 세션 하나에 거는 규율(청사진→승인→구현→검증·가역성·커밋 안전)은 혼자서도 작동한다. 설계 근거와 결정 기록은 `design-notes/10-오케스트레이션-구성.md`.

## 이 문서의 용어

이 문서에 나오는 "세션"은 모두 Claude Code의 AI 세션이다. 사람은 "사람"이라고만 부른다.

- **게이트웨이 세션:** 사람과 다른 세션 사이에서 메시지를 전하고 진행을 지켜보는 AI 세션. 오케스트레이터라고도 한다.
- **실무자 세션(실무자):** 게이트웨이 세션이 작업을 맡기려고 띄운 AI 세션. 실제 구현을 한다. 규칙 문서의 developer 세션, 실전 기록의 "워커"와 같은 것이다.
- 게이트웨이 세션은 총괄 세션의 한 형태이고, 실무자 세션은 워커 세션이다(이름은 [`환경값-정의.md`](./환경값-정의.md) B).

## 언제 쓰나

- 작업을 **여러 Claude Code 세션**에 나눠 동시에 진행하고 싶을 때.
- 원본 SI의 완전형(전용 `qa-master` 세션·대기 장부·순찰)을 **안 갖춘** 혼자/소규모 환경에서.

## 그림 — 3단 구조

```
사람(결정)  →  게이트웨이 세션(전달·감시)  →  실무자 세션(구현)
```

- **사람** = 게이트(승인)를 쥔다. 좁은 위임(아래 선택 절)을 켜면 위임기록의 "위임한 게이트" 절에 적은 게이트만 게이트웨이가 검증을 거쳐 승인한다.
- **게이트웨이 세션**(오케스트레이터) = 사람과 실무자 사이의 **통신·감시 창구**. **스스로 결정하지 않는다** — 사람의 승인을 원문 그대로 실무자에 전달하고, 진행을 지켜보다 막히면 사람에게 올린다.
- **실무자 세션**(developer) = 실제 구현. 게이트에서 멈추고, 게이트웨이를 통해 사람의 승인을 기다린다.

핵심 한 줄: **"게이트웨이"는 관문이 아니라 창구다.** 기본은 승인이 끝까지 사람에게 있다. 좁은 위임을 켜도 청사진·push·병합·업무 결정은 사람이 한다.

## 소규모 모드 = 없어도 되는 것

완전형이 전제하는 인프라를 **안 갖춰도 된다.** 그 역할은 사람이 메운다.

| 완전형(원본 SI) | 소규모 모드 |
|---|---|
| `qa-master`(위임 승인자) | 사람이 직접 모든 게이트 승인(좁은 위임을 켜지 않았을 때) |
| 대기 장부(AG-15) | 생략(사람이 직접 상태 확인) |
| 순찰 세션 | 생략 |
| 공유문서 루트 | 저장소 내 폴더, 또는 생략 |

안 갖췄다고 규칙이 깨지지 않는다. 사람이 위임기록에 **"그 역할은 내가 맡는다"고 적어 두면** 된다.

## 세팅 — 네 걸음

### 1. 역할을 가른다

- 어느 세션이 **게이트웨이**인지, 어느 세션이 **실무자**인지 정한다.
- **게이트웨이 ≠ 실무자.** 같은 세션이 구현도 하고 자기 걸 승인하면 "자기 채점"이 된다 — 하네스가 막으려는 바로 그것이다. 구현은 **별도 실무자 세션**에 맡긴다.
- 자기 채점은 "만든 쪽이 자기 결과를 승인하는 것"만 뜻한다. 같은 맥락에서 보면 못 보는 맹점은 따로 막는다. 승인 전에 만든 쪽의 맥락을 물려받지 않은 검증자(새 맥락 재검증)가 한 번 더 본다.

### 2. 위임기록을 쓴다

- 게이트웨이에 위임한 것을 **글로 남긴다**(저장소 안 `위임기록.md`).
- 소규모 모드에서 위임 대상 = **코디네이션 역할뿐**이다: 실무자 세션 생성·종료, 사람 승인의 원문 전달, 상태 감시. **게이트 결정 권한은 위임하지 않는다**(좁은 위임을 켜면 위임기록의 "위임한 게이트" 절에 적은 게이트만 예외, 아래 선택 절).
- 템플릿은 [`위임기록-템플릿.md`](./위임기록-템플릿.md).
- 규칙: **목록에 없는 건 전부 사람에게 올린다(화이트리스트).** 사람은 언제든 위임을 거둬들인다.

### 3. 실무자 세션을 띄운다

실무자는 서브에이전트(`Agent` 도구)가 아니라 별도 세션(`claude --bg`)으로 띄운다. 게이트를 여러 번 오가며 사람의 승인을 기다려야 하기 때문이다. 둘의 차이와 언제 무엇을 쓰는지는 `session-wake` 스킬 문서의 "먼저: 별도 세션이 필요한 일인가"에 있다.

띄우기 전에 프로젝트 `.claude/settings.json`에 `worktree.bgIsolation: "none"`을 넣는다(규칙 WT-03, 권한 모드와 상관없이 필수). 넣지 않으면 백그라운드 세션이 따로 떨어진 임시 체크아웃으로 옮겨져 저장소의 docs·워크트리를 쓰지 못한다.

각 실무자 세션에 정할 것:

- **모델** · **권한 모드**(아래 "권한 모드" 참고).
- **지시문 3줄**(공백이 세션을 멈춰 세우지 않게): ① 정본 근거(언급하는 값·명칭의 출처), ② 정본 도착 전 대기 중 행동(해도 되는 범위와 멈출 지점), ③ 막히면 문의처.
  - ① 정본 근거에는 **하네스가 설치된 위치를 경로로 적는다.** 규칙(`rules/`)과 스킬(`skills/`) 둘 다다. 적지 않으면 세션이 문서를 찾으러 여기저기 뒤지다 멈추거나, 지난 버전의 사본(플러그인 캐시)을 쓴다(2026-11-21 gate3 실측). 플러그인을 저장소 폴더에서 바로 읽는 설치(로컬 폴더 마켓)면 그 폴더가 하네스 위치다. `claude plugin list`의 "Read from"으로 확인한다.
  - ②에 운영 줄 하나를 더한다: **"셸 명령에서 경로를 변수에 담거나 `cd`로 옮기지 말고 절대 경로를 그대로 적는다."** 변수·`cd`가 섞이면 Claude Code가 명령을 미리 검사하지 못해 권한 창이 뜬다. 새 맥락 재검증자(서브에이전트)는 이 지시를 물려받지 않으니 재검증을 맡길 때 따로 넣는다.

#### 권한 모드 — 기본은 auto, 꼭 막을 것은 장치로 (2026-11-21 결정)

**권장: 게이트웨이·실무자 모두 `--permission-mode auto`로 띄운다.** 명령 하나하나를 사람이 승인하게 하면, 사람은 읽기 명령 승인에 지쳐 정작 중요한 결정을 덜 보게 된다. gate3 시험에서 `acceptEdits`로 띄우자 권한 창이 약 68번 떴고, 그중 사람이 꼭 봐야 했던 것은 약 14번(세션 띄우기·커밋·push·PR·삭제)뿐이었다. auto로 바꾼 뒤에는 0번이었다.

auto를 쓰는 대신 아래 장치로 선을 지킨다.

| 무엇을 | 어디서 막나 |
|---|---|
| main 직접 push·강제 push | **GitHub 브랜치 보호**(PR 필수·강제 push 금지·관리자 포함). 띄우기 전에 켠다. 켤 수 없으면 아래처럼 사람에게 먼저 확인받는다 |
| 기밀 유출 | push 전에 기밀 문자열을 거르는 훅. 이 저장소는 `pre-push` 훅을 쓰지만 공개판에는 없어, 팀이 직접 마련한다 |
| AI 귀속 줄 | Claude Code `attribution` 설정([`환경값-정의.md`](./환경값-정의.md) H, 규칙 CM-11). git 훅은 팀 선택이다 |
| 결정(청사진·업무 결정·병합·위임 범위) | 위임기록의 게이트 — 권한 창이 아니라 게이트에서 사람이 정한다 |

**띄우기 전에 사람에게 확인받는다 — 브랜치 보호를 켤 수 있는가.** GitHub 무료 요금제의 비공개 저장소는 브랜치 보호를 쓸 수 없다(공개 저장소이거나 Pro·Team 이상이어야 한다). 켤 수 없으면 세팅을 돕는 세션(게이트웨이)은 auto로 띄우기 전에 그 사실을 사람에게 알리고, 다음 가운데 무엇으로 할지 동의를 받아 위임기록에 적는다.

- 저장소 호스팅의 보호 브랜치 기능을 쓴다(GitHub가 아닌 사내 GitLab 등)
- auto 대신 `acceptEdits`와 허용 목록으로 띄워, push 명령을 사람이 직접 본다
- 위험을 알고 auto를 그대로 쓴다

대가: 커밋 직전에 사람이 명령을 보는 단계가 사라진다. 그 자리는 위임 조건(게이트웨이의 직접 확인 + 새 맥락 재검증)이 메운다. 좁은 위임을 켜지 않았다면 커밋 계획 승인도 사람이 하니 대가는 더 작다.

**보수적 선택지 — `acceptEdits` + 허용 목록:** 처음 써 보는 팀, 폐쇄망처럼 무엇이 실행되는지 다 보고 싶은 환경용이다. `acceptEdits`는 파일 편집만 자동으로 허용하고 셸 명령은 매번 묻는다. 쓸 때 알아 둘 것:

- 반복해서 쓰는 읽기 명령은 `.claude/settings.local.json`에 **이름 자리를 비운 규칙**으로 미리 넣는다. 예: `Bash(git -C * status*)`·`diff*`·`log*`·`branch -vv*`·`show*`, `Bash(python3 -m unittest*)`·`Bash(python3 -B -m unittest*)`, 하네스 스킬 스크립트(`session_stall_check.py *`, `seosul_lint.py *`, `new_worktree.py *` — 하네스 경로를 그대로 적는다). 커밋·세션 띄우기·push·삭제는 넣지 않는다.
- 창의 "다시 묻지 않기"는 내용을 보고 고른다. 세션 이름까지 넣어 너무 좁게 저장하거나(`… gate3-w0`), 반대로 `python3 *`·`git *`·`gh pr *`·`cd *`처럼 push·병합·임의 코드까지 여는 넓은 규칙을 제안하기도 한다.
- 실무자가 게이트가 아닌 권한 창에서 멈추면 게이트웨이에게 메시지가 가지 않아 아무도 모른다. 사람이 가끔 `session-stall-check`로 사람 입력 대기에 멈춘 세션이 없는지 확인한다(순찰은 0.5.0).
- **겹치지 않는 세션 이름.**
- 문의처(소규모 모드) = **사람, 또는 지시한 세션(게이트웨이)**. 세션이 사람에게 직접 묻는 창을 띄우는 대신, 지정한 창구에 질의하게 한다.
- **미리 할 준비 — "프로젝트 밖"을 먼저 연다 (실전 교훈):** bg 실무자 세션은 **프로젝트 폴더 밖**이 자동 허용되지 않을 수 있다(특히 `acceptEdits`). 띄우기 전에 두 가지를 미리 정리한다.
  - **하네스 폴더 읽기 허용:** 실무자가 하네스의 `rules/`·`skills/`를 읽어야 하는데 그게 프로젝트 밖이라 권한 프롬프트에 멈춘다. **좁게 미리 허용**한다(`.claude/settings.local.json`에 `Read(//<하네스 경로>/**)`).
  - **산출물 저장 경로:** 격리 가드가 공유 체크아웃 쓰기를 막으면, 실무자가 쓴 청사진이 임시 job 폴더에 저장된다. 그래서 규칙 WT-03은 띄우기 전에 프로젝트 `.claude/settings.json`에 `worktree.bgIsolation: "none"`을 넣게 한다. 그래도 자동 격리된 세션은 작업을 시작하지 않고 보고한다. 사람은 설정을 넣은 뒤 그 세션을 새로 띄운다.
  - **게이트웨이는 권한을 대신 못 연다** — 권한은 사람 몫이다(우회 금지, 1단계 GL·2단계 RL-12).
- **더 깔끔한 대안 — 워커를 본 폴더에서 띄우기(권고, 2026-11-18):** 위 두 마찰(규칙 읽기·산출물 저장)은 워커 세션 루트를 **본 폴더**(프로젝트 최상위 체크아웃)로 두면 한 번에 사라진다. docs도 워크트리도 본 폴더 하위라 "밖"이 아니기 때문.
  - 전제: 프로젝트 `.claude/settings.json`에 `worktree.bgIsolation: "none"`(백그라운드 세션이 본 폴더를 직접 고쳐도 되는지 정하는 설정, 기본값은 차단). 규칙 WT-03이 어차피 넣게 하는 설정이다. 전역 말고 **프로젝트별**로 넣는다(전역은 하네스 안 쓰는 레포까지 가드 해제).
  - 규율: 코드 수정은 워크트리 파일에만, git은 `git -C <워크트리>`로(bare `git`은 main이라 위험). 커밋 전 스테이징 검사가 보조.
  - 설정은 **새 세션부터** 로드됨 — 이미 떠 있는 세션엔 적용 안 됨.
  - **이건 per-세션 워크트리 규칙(WT-02, "워크트리 안에서 작업")에서 일부러 벗어난 것이다.** 세션이 워크트리 밖(본 폴더)에서 시작하니, 위 규율(코드는 워크트리 경로만)과 커밋 전 스테이징 검사가 **유일한 안전망**이다 — 조심하는 운영자용 opt-in. 실전 2회 통과(2026-11-18).
- **push는 실무자에게 맡기지 않는다 — 막는 곳은 명령 옵션이 아니라 플랫폼이다(2026-11-19 결정).**
  - push·PR은 사람 몫이다(게이트웨이가 사람 지시를 받아 한다). 실무자 지시문에 "push·PR 하지 않는다"를 넣는다.
  - 기계로 막는 곳은 둘이다. ① **GitHub 브랜치 보호** — main 직접 push·강제 push 금지(사고가 큰 쪽). ② **실무자가 쓰는 인증에 push 권한을 안 준다**(가능한 환경이면).
  - feature 브랜치 push는 되돌리기 쉬워 지시문과 세션 자제에 맡긴다. 실전 시험에서 세션은 다른 세션이 보낸 push 요청을 스스로 거부했다.
  - **`--disallowedTools`로 막으려 하지 않는다.** 시험 결과(2.1.328): `Bash(git push:*)`는 `git -C <경로> push`·`sh -c "…"`로 뚫린다 — 위 규율대로 `git -C`를 쓰는 실무자에겐 효과가 없다. `Bash(git -C * push *)`처럼 가운데를 넓히면 막히지만, 커밋 메시지에 "push"가 든 커밋까지 막는다.
- **`--disallowedTools`를 다른 용도로 쓴다면 함정 하나:** 이 옵션은 뒤에 오는 말을 끝까지 다 금지 목록으로 받아 적는다. 그 뒤에 시작 지시를 쓰면 지시까지 금지 목록에 들어가고, 세션은 에러 없이 할 일 없는 채로 뜬다. 등호로 붙여 쓴다.

  ```
  claude --bg -n <세션이름> --model <모델> --permission-mode auto \
    "--disallowedTools=<금지 값>" "<시작 지시>"
  ```

  지시를 옵션보다 앞에 두거나, 옵션 뒤에 `--`를 넣고 지시를 써도 된다. 세 방법 모두 시험 통과. 이 옵션은 깨울 때(session-wake) 그대로 되살아난다.

### 4. 운영한다

- 실무자는 **게이트에서 멈추고** 게이트웨이에 보낸 뒤 대기한다.
- 게이트웨이는 메시지를 받으면 깨어나 사람에게 올린다 → 사람이 결정 → 게이트웨이가 **원문 그대로** 실무자에 전달한다.
- **짧은 승인은 대상이 분명할 때만 전달한다.** 사람이 "권장대로 승인"처럼 짧게 답하면, 게이트웨이는 어느 작업의 무엇을 승인했는지 분명할 때만 전달한다. 분명하지 않으면 짐작하지 않고 사람에게 되묻는다. 짧은 답을 펼쳐서(예: "질문 3은 A") 전달하려면, 펼친 내용을 사람에게 먼저 보여 확인받는다.
- 게이트웨이는 범위 밖 결정을 대신하지 않는다.
- **Esc로 끊어도 메시지는 이미 전달된 것이다.** 보내고 곧바로 Esc를 누르면 끊기는 건 세션의 답이고, 보낸 메시지는 대화에 남아 다음 입력과 함께 읽힌다. 잘못 보냈으면 "앞 메시지는 무시하고 이걸로 정한다"처럼 다시 분명히 보낸다.
- **화면 입력창의 회색 글씨는 입력 제안이다.** Claude Code가 다음 답을 미리 띄워 주는 것이라 사람이 쓴 것이 아니다. 그대로 Enter를 누르면 그 문장이 보내진다.
- **실무자는 한동안 놀면 사라진다 — 평소 흐름이다.** 게이트에서 사람 답을 기다리는 동안 백그라운드 세션은 정리된다(실측으로 1시간 남짓에서 사라짐, 정확한 값은 재지 않기로 함). 그래서 게이트웨이는 보내기 전에 수신자를 확인한다.
  1. `session-stall-check <세션이름>`으로 상태를 본다. 사람 입력 대기면 재요청 대신 사람에게 알린다.
  2. 프로세스가 없다고 나오면 `session-wake <세션이름>`으로 같은 id에 되살린 뒤 보낸다. 기동 옵션(모델·권한 모드·`--disallowedTools`)은 그대로 되살아난다. 띄운 뒤 창에서 권한 모드를 바꿨다면 그 변경은 되살아나지 않고 처음 기동 옵션으로 돌아간다 — 그래서 권한 모드는 처음 띄울 때 정한다.
  - `claude agents`의 `state=done`은 '종료'가 아니다 — 턴을 끝내고 지시를 기다리는 살아 있는 세션도 `done`이다. 살았는지는 pid로 본다(`session-stall-check`가 대신 판정).
- **게이트웨이는 메시지를 받으면 스스로 깨어난다.** 살아 있는(`/exit`로 끝내지 않은) 세션이면 된다. 2026-11-16에 처음 관측했고 gate3(2026-11-21)까지 여러 번 다시 확인했다.

## 선택: 게이트 결정의 좁은 위임

기본은 "게이트 승인은 전부 사람"이다. 세션·작업이 늘어 사람이 승인하는 부담이 커지면, 일부 게이트를 게이트웨이가 대신 승인하게 할 수 있다.

- **맡길 수 있는 것:** 커밋 계획 승인(CS-01)과 요구사항·결과 대조(CM-01). 되돌릴 수 있고 규칙으로 확인할 수 있는 게이트다.
- **늘 사람이 하는 것:** 청사진 승인, push·PR·병합, 되돌리기 어려운 git 명령, 업무 결정.
- **검증은 그대로다.** 게이트웨이는 직접 확인과 새 맥락 재검증을 둘 다 통과해야 승인한다. 바뀌는 건 "누가 승인이라고 말하나"뿐이다. 하나라도 통과하지 못하면 근거째 사람에게 올린다.
- **재검증자에게 줄 지시:** 새 맥락 재검증자(서브에이전트)는 하네스 규칙을 읽지 않고 시작한다. 지시에 "저장소 파일은 고치지 않는다, 실험은 임시 폴더에서 한다, 지울 때는 `safe-delete`(영구 삭제 `rm -rf` 금지), 경로는 절대 경로로"를 넣는다(gate3에서 재검증자가 `rm -rf`를 썼다).
- **기록하고 언제든 번복한다.** 게이트웨이의 승인은 위임기록에 근거째 남는다. 사람은 그 승인도, 위임 자체도 언제든 되돌린다.
- **1회 지시는 상시 권한이 아니다.** "이번 PR은 네가 병합해"처럼 그때만 맡긴 일은 그 건에 한해 하고, 다음부터는 다시 사람 몫이다.
- 켜는 법: 위임기록에 "위임한 게이트" 절을 더한다([템플릿](./위임기록-템플릿.md)).
- **한 칸 더 넓히기(선택, gate3에서 써 봄):** 사람에게 오는 질문이 너무 잘면 이렇게 더한다. 모두 내용(코드·테스트·파일 목록·업무 규칙)은 바뀌지 않는 경우다.
  - **문구 보정 후 승인:** 코드·테스트·파일 목록은 두 검증을 통과했고 걸린 것이 커밋 메시지 문구나 완료보고서 서술뿐이면, 게이트웨이가 고치게 하고 다시 검증해 통과하면 승인한 뒤 사람에게 사후 보고한다.
  - **청사진에서 정한 예외는 다시 묻지 않는다:** 청사진 승인 때 사람이 정한 예외(예: 특정 파일 커밋 허용)는 그 작업의 이후 커밋에도 유효하다. 내용이 바뀌면 다시 묻는다.
  - 경계는 게이트웨이가 좁게 읽어야 한다. gate3에서는 코드가 바뀐 재제출이나 확인 명령만 빠진 계획도 "문구가 아니다"라며 사람에게 올렸다.
- 실전: 좁은 위임은 실전 검증 네 번에서 써 봤다(2026-11-17~20 같은 저장소에서 세 번, 2026-11-21 새 공개 저장소 gate3에서 한 번). 게이트웨이가 검증을 거쳐 커밋 계획을 승인했고, 그 과정에서 실무자의 커밋 메시지가 숨긴 동작 차이를 찾아 실무자에게 고치게 했다. 게이트웨이 자신의 보정 지시가 틀렸을 때는 실무자가 따르지 않았고, 게이트웨이가 오류를 인정했다.

## 왜 안전한가

- 게이트웨이는 **위임기록에 적힌 것만** 한다. 게이트 승인은 사람 몫이다. 좁은 위임을 켜도 게이트웨이는 적힌 게이트만, 두 검증을 통과한 뒤에 승인한다.
- 범위 밖은 **전부 에스컬레이션.** 사람이 위임을 **언제든 번복**한다.
- 그래서 세션이 여럿이어도 하네스의 사람 게이트는 그대로 작동한다.

## 아직 안 넣은 것 (키울 때 더한다)

- **작업을 자동으로 나눠주는 엔진**(coordinator) — 소규모 모드는 사람이 작업을 나눈다.
- **장부·순찰.**
- **워커가 워커를 띄우는 단계 구조.** 워커가 하위 작업을 나눌 때는 같은 세션 안의 서브에이전트까지만 쓴다. 게이트가 없는 일(조사, 새 맥락 재검증 등)만 맡긴다. 워커가 별도 세션을 띄워 하위 작업을 지시하는 것은 아직 넣지 않았다. 깊이와 상관없이 게이트 승인은 사람에게 간다.

## 알아둘 것 (아직 검증 안 된 부분)

- **유휴 정리:** 백그라운드 실무자는 1시간쯤 논 세션은 살고 1시간 15분 넘게 논 세션은 사라졌다(2026-11-18, 표본 작음). 앞에 띄운 게이트웨이는 같은 시간을 넘겨도 살아 있었다. 값을 알아도 할 일(보내기 전 확인·깨우기)이 같아 더 재지 않는다. 백그라운드 작업을 걸어 두고 기다리는 실무자도 정리되는지는 미확인.
- **워커 루트 전략:** 위 "본 폴더에서 띄우기"는 **실전 2회 통과**(2026-11-18, flag-validation·write-timeout) — 걸렸던 지점(청사진 읽기 프롬프트·완료보고서 임시폴더 갇힘·자동 격리)이 본 폴더 루트에서 안 걸림. 단 WT-02(워크트리 안에서 작업)에서 벗어나는 opt-in이라 조심하는 운영자용.
- **실전 검증 이력:** 처음 한 번(게이트웨이 1 + 실무자 1)에서 추려냈고, 좁은 위임으로 두 번, 실무자 세 명이 동시에 청사진부터 PR·병합·정리까지 간 작업으로 한 번 더 써 봤다(2026-11-16~20, 같은 저장소). 세 번째에서 침범과 잘못된 승인은 없었다. 그 뒤 0.2.0 출시 전 점검으로 새 공개 저장소([gate3-trial](https://github.com/neisii/gate3-trial))에서 게이트웨이 1 + 실무자 4가, 한 작업의 변경이 다른 작업에 영향을 주도록 일부러 짠 일을 처음부터 끝까지 진행했다(2026-11-21). 침범·잘못된 승인은 없었고, 그 영향은 청사진 단계에서 사람에게 올라왔다. 실무자가 권한 창에 막히는 일이 여러 번 생겨 이 문서의 권한 모드·지시문 절을 고쳤다. 표본이 작으니, 쓰는 사람이 자기 환경에서 써 보며 고쳐 쓰길 권한다.
