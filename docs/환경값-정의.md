# 환경값 정의 — 이 하네스를 내 환경에 맞추는 법

> 이 문서는 공개 `rules/`(향상된_AI-DLC 12단계)를 **다른 팀·환경에서 쓸 때 갈아끼우는 값**을 한곳에 모은 설정 페이지다. 규칙 문장을 일일이 고치지 않고, 여기 적힌 값만 내 환경 값으로 바꿔 읽는다.

## 왜 이 문서가 있나 (요리책 비유)

규칙 문서는 **요리책**과 같다. 이 요리책은 원래 한 팀(어느 폐쇄망 SI의 차세대 사업)에 딱 맞게 쓰였다. 그래서 "그 팀 전용" 부분이 두 종류 섞여 있다.

1. **이름표** — "CJ 설탕"처럼 브랜드 이름일 뿐인 것. 자리에서 "설탕"으로 고쳐 쓰면 문장이 그대로 멀쩡하다. 규칙에서는 폴더 경로나 `화면ID` 같은 식별자가 이에 해당하며, 이미 플레이스홀더(`<워크스페이스>` 등)로 바꿔 두었다.
2. **책 전체에 밴 전제** — "넌 늘 김치찌개를 만든다"처럼 모든 줄에 박힌 가정. 남이 볶음밥을 만든다고 "김치찌개"를 전부 "요리"로 바꾸면, 끝도 없고 문장이 "요리를 간 봐라"처럼 속 빈 맹탕이 된다. 그래서 전수 교체하지 않는다. 대신 **이 설정 페이지에 "이 팀은 이렇게 쓴다"를 모아 두고, 규칙 본문은 구체적인 예시로 그냥 둔다.**

**원칙:** 규칙의 구체 값을 지우지 않는다. 그 자리의 값은 "이 팀 예시"로 읽고, 내 환경 값은 이 표에서 찾아 바꾼다. 구체 예시가 남아 있어야 규칙이 맹탕이 되지 않는다.

## 갈아끼우지 않는 것 (핵심 원리)

환경이 바뀌어도 이 뼈대는 그대로다. 이게 하네스의 정체성이다.

- 사람 게이트(되돌리기 어렵거나 바깥으로 나가는 일은 사람 확인).
- 검증은 검증으로만 닫는다(검증하지 못한 것을 검증 완료로 쓰지 않는다).
- 비동기 검수(사람 병목을 큐·장부로 흘린다).
- 가역성 분류(거부권 기준은 점수로 못 덮는다).
- 청사진 → 승인 → 구현 → 검증 → 완료보고의 흐름.
- 정보가 명확한 영역만 병렬화한다.

## 갈아끼우는 값 (swap-list)

아래 범주별로 **이 팀 예시 → 내 환경 값 → 규칙이 말하는 역할 → 나오는 곳**을 적는다. 역할만 남기고 값을 바꾸면 규칙은 그대로 돈다.

### A. 경로·워크스페이스

| 플레이스홀더 | 이 팀 예시(원본) | 역할 |
|---|---|---|
| `<워크스페이스>` | `{본인 경로}\IdeaProjects` | 레포들이 체크아웃된 상위 폴더 |
| `<공유문서 루트>` | `…\project_docs\docs` | 세션들이 공유하는 문서·장부·스크립트 루트 |
| `<공유문서 저장소>` | 위 루트의 레포 루트 | 공유 문서 저장소 자체 |
| `<팀구분>` | `team2` | 산출물·브랜치의 팀 세그먼트 |
| `<이름약자>` | `ghbaek` | 산출물·브랜치의 담당자 세그먼트 |

- 규칙은 "산출물은 지정된 산출물 루트에 둔다"처럼 **역할**만 말한다. 산출물 루트·대기 장부 위치·워크스페이스 루트를 내 값으로 정한다.
- `지시대기`·`_작업중` 같은 하위 폴더 이름은 공유문서 루트 내부 구조다. 이름이 달라도 역할(대기 장부 / 작업 중 임시)만 맞추면 된다.
- 정의 정본: `rules/00` 상단 "경로 플레이스홀더(환경값)".

아래 두 경로는 아직 플레이스홀더로 바꾸지 않아 규칙 본문에 원본 그대로 보이지만, 이것도 환경값이다(C·F 일반화 때 정리 예정). 규칙은 그대로 두고 여기서 바꿔 읽는다.

| 규칙에 보이는 원본 | 역할 |
|---|---|
| `{본인 경로}\.prj-ai-metrics\<프로젝트>` (12단계) | 저장소 밖에 두는 작업 메트릭 원장 위치(자동커밋 방지). 내 환경의 "저장소 밖 원장 루트"로 읽는다. |
| `{본인 경로}\.claude\secrets\devdb_readonly.env` (6단계) | 개발DB 접속정보 등 비밀 파일 위치. 값 자체는 대화·문서·메모리에 남기지 않는다(10단계 TS-11). |

### B. 브랜치·역할·팀 이름

- **브랜치 스킴:** 구조 `<팀구분>/<이름약자>/<작업ID>`는 유지하고 값만 바꾼다. 예: `your-teamname/ghbaek/asas-112`. 원본의 SI 특유 요소(`_dev` 접미사, 작업 단위를 화면으로 한정한 부분)는 걷어냈다. `작업ID`는 일반 이슈·작업 식별자다.
- **역할 이름:** "결정자 / 검수자 / 구현자"라는 **개념은 핵심**이고, 이름은 환경값이다. 이 팀 예시 `qa-master`·`scenario-master`·`*-developer`를 내 조직의 역할 이름으로 바꾼다.

### C. 스택·빌드·서버

| 이 팀 예시(원본) | 역할 |
|---|---|
| `gradlew`·`bootRun` | 빌드·서버 기동 명령 |
| `ArchitectureTest`·`FeignClient`·core 파일 | 스택 고유의 검증·연동 구성 |
| WT-10 포트 규칙 | 로컬 서버 포트 배정 |
| `memcheck`의 Java 프로세스 | 기동 전 메모리 점검 대상 프로세스 |

- 핵심은 "구현 후 빌드·검증을 한다"이지 특정 빌드 도구가 아니다. 내 스택의 빌드·테스트 명령으로 바꾼다.
- 이 팀 스택 인벤토리(Java·Spring·Gradle·MyBatis·Flyway)는 11단계 CS-09 등에 **예시**로 남아 있다. 그 목록은 "이 팀 환경값"이니, 제외·설정 대상은 내 스택 기준으로 다시 정한다.

### D. 소스 헤더·사내 보안도구

- 원본의 `@programId`/`@processId` 헤더, `NPROTECT`·`ANYID`(사내 보안 에이전트)는 특정 조직 전용이다.
- 조직 고유 헤더·보안 토글이 있으면 같은 자리에 내 것을 넣고, 없으면 그 규칙 줄은 적용하지 않는다(조건부·선택).

### E. 작업 모델 — "화면 단위"라는 전제 (핵심)

이게 요리책의 "김치찌개"다. 규칙 곳곳이 **작업 단위 = 화면(screen)**이라는 가정 위에 쓰여 있다: 화면설계서, 공통코드, 개발DB, 테이블 명세, 퍼블리싱, `청사진.md`, `완료보고서.md`.

- **핵심(그대로):** 청사진 → 승인 → 구현 → 검증 → 완료보고 흐름.
- **환경값(바꿔 읽기):** "화면설계서"는 내 작업의 **요구 명세**로, "화면"은 내 **작업 단위**(API·배치·라이브러리 등 무엇이든)로 읽는다. "공통코드·개발DB·테이블 명세"는 이 팀 도메인 전제이니, 내 도메인의 대응물로 바꾼다.
- 규칙 본문의 "화면"을 전수 치환하지 않는다(그러면 맹탕이 된다). 이 항목을 근거로 **읽을 때 치환**한다.

### F. OS (Windows/PowerShell)

- 원본의 PowerShell 예시(`Remove-Item`, `\\?\` 롱패스 등)는 OS별 예시다.
- 크로스플랫폼 스킬(`safe-delete` 등)은 이미 OS 중립 Python으로 제공된다. 규칙 문서의 명령 예시는 내 OS 예시로 읽는다.

## 읽는 법 요약

1. 규칙에서 플레이스홀더(`<…>`)나 구체 경로·이름·명령을 만나면, 지우지 말고 이 표에서 내 값을 찾아 바꿔 읽는다.
2. "화면" 같은 작업 모델 어휘는 E 항목을 근거로 내 작업 단위로 읽는다.
3. 핵심 원리(사람 게이트·검증·흐름)는 바꾸지 않는다.
