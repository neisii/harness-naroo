# 10. AI를 여럿 쓰니 사람이 승인하느라 더 바빠졌다

> **한 줄 해법:** 되돌릴 수 있는 게이트는 게이트웨이 세션에 좁게 맡기고, 사람에게 물을 결정은 선택지와 추천을 붙여 한 번에 묻는다. 사람이 계속 지켜보지 않고 정한 때 모아 검수하게 하는 장치는 아직 설계 단계다.

2부의 첫 장이다. 2부는 사람이 AI 세션 여러 개를 엮어 함께 쓸 때 겪는 문제를 다룬다. 각 세션이 1부의 규율(청사진 승인, 증거 인용, 커밋 안전 등)을 지킨다는 전제 위에 얹는다.

이 장의 등장인물:

- **사람** — 하네스를 쓰는 개발자. 청사진·커밋·병합을 승인한다.
- **실무자 세션** — 작업 하나를 맡아 구현하는 AI 세션. 게이트(사람의 승인이 필요한 지점)에 닿으면 멈추고 승인을 기다린다.
- **게이트웨이 세션** — 사람과 실무자 사이에서 질문과 승인을 전달하고 실무자를 살피는 AI 세션. 업무 결정은 하지 않고, 사람이 맡긴 게이트만 승인한다(아래 선택 제안 1). 세팅은 [`docs/오케스트레이션-구성.md`](../오케스트레이션-구성.md).

## 문제

사람이 AI 세션을 여러 개 쓰면 일이 빨라질 것 같다. 실제로는 사람이 더 바빠졌다.

원본 SI 프로젝트에서 사람이 역할별로 세션을 나눠 썼을 때 실제로 겪은 일이다(`design-notes/03`).

- 실무자 세션마다 막힘·승인·검수 요청을 보냈다. 세션이 늘어난 만큼 요청도 늘었고, 그 요청은 모두 사람 한 명에게 왔다.
- 사람은 막힘이 생기면 바로 풀어 주려고 모니터를 자주 지켜봤다. AI가 빨라진 만큼 사람도 빨라져야 했다.
- 사람이 알림·순찰을 잘 만들수록 알림에 끌려다녔다. 알림이 좋아질수록 자리를 더 못 떴다.

이 하네스를 시험할 때도 같은 일이 나왔다(2026-11-18, `design-notes/10` 부록 E-2·E-4).

- 실무자 세션 셋이 각자 청사진을 쓰고 승인을 기다렸다. 세 청사진에 사람이 답할 질문이 17개(5·9·3개) 쌓였다.
- 사람은 "1~5 권장대로 승인"이라고 짧게 답했다. 어느 작업의 질문인지 이름이 없었다.
- 게이트웨이 세션은 질문이 정확히 5개인 작업이라고 짐작하고, 되묻지 않은 채 승인을 전달했다. 짐작은 맞았다. 작은 결정이고 되돌릴 수 있었지만, 사람이 정할 일을 AI가 짐작으로 정한 것이다.
- 한 실무자에게는 "나머지 둘도 권장대로 승인"이라는, 앞뒤 맥락이 없는 문장이 전달됐다. 그 실무자는 이 문장이 자기 작업을 가리킨다고 스스로 해석해야 했다.

**왜 생기나.**

- 모든 결정이 사람 한 명에게 모인다. 세션이 N개면 사람에게 오는 요청도 N배다.
- 게이트는 사람이 답할 때까지 실무자를 멈춰 세운다. 사람이 자리를 비우면 일이 멈추니, 사람은 자리를 못 뜬다.
- 요청이 여러 작업에서 한꺼번에 오면, 사람의 답이 어느 작업을 가리키는지 흐려지기 쉽다. 위 사례에서는 실제로 그 빈칸을 AI가 짐작으로 채웠다.

## 해결책 후보

| 후보 | 어떻게 | 아쉬운 점 |
|---|---|---|
| ① 알림·순찰을 더 잘 만든다 | 사람이 막힘을 더 빨리 알도록 알림을 늘린다 | 위 원본 사례가 바로 이 경우다. 알림이 좋아질수록 사람은 알림에 끌려다닌다. 요청 수는 그대로다 |
| ② 승인 게이트를 없앤다 | AI가 사람에게 묻지 않고 진행한다 | 7장의 문제(묻지 않고 커밋·삭제)로 돌아간다 |
| ③ 되돌릴 수 있는 게이트만 좁게 맡긴다 | 사람이 일부 게이트의 승인을 게이트웨이 세션에 맡긴다. 나머지는 계속 사람이 승인한다 | 무엇을 맡길지 사람이 정하고 적어 둬야 한다. 맡긴 뒤에도 검증은 줄지 않는다 |
| ④ 지켜보지 말고 모아서 검수한다 | 실무자는 막힌 일을 제쳐 두고 다음 일을 한다. 사람은 정한 때에 쌓인 결정을 한 번에 처리한다 | 공개판에는 일부만 있다. 결정을 모아 묻는 도구는 있고, 막힌 일을 제쳐 두는 장치는 설계 단계다 |

③은 사람에게 오는 요청의 **수**를 줄인다. ④는 요청이 오는 **때**를 사람이 정하게 한다. 둘은 서로 대신하지 않고 함께 쓴다.

## 선택 제안

**③과 ④를 함께 쓴다.** 지금 공개판으로 할 수 있는 것은 1~3이다. 4는 설계 단계다.

### 1. 되돌릴 수 있는 게이트는 게이트웨이에 좁게 맡긴다 (공개 가이드 `docs/오케스트레이션-구성.md` "선택: 게이트 결정의 좁은 위임")

사람은 모든 게이트를 맡기지 않는다. 되돌릴 수 있고 규칙으로 확인할 수 있는 게이트 둘만 맡긴다.

| 게이트 | 누가 승인하나 |
|---|---|
| 커밋 계획(CS-01), 요구사항과 결과 대조(CM-01) | 맡기면 게이트웨이 세션 |
| 청사진, push·PR·병합, 되돌리기 어려운 git 명령, 업무 결정 | 늘 사람 |

- **사람은 맡긴 것을 위임기록에 적는다.** 위임기록에 없는 게이트는 게이트웨이 세션이 사람에게 올린다. 사람은 위임을 언제든 거둬들인다. 양식은 [`docs/위임기록-템플릿.md`](../위임기록-템플릿.md).
- **맡겨도 검증은 그대로다.** 게이트웨이 세션은 직접 확인하고, 새 맥락의 검증자에게 다시 검증받은 뒤에만 승인한다. 바뀌는 것은 "누가 승인이라고 말하나"뿐이다.
- **그때만 맡긴 일은 그때로 끝난다.** 사람이 "이번 PR은 네가 병합해"라고 하면 게이트웨이 세션은 그 건만 하고, 다음부터는 다시 사람에게 묻는다.

실전에서 맡겨 보니 검증 기준은 낮아지지 않았고, 오히려 실무자의 얼버무림을 걸러냈다(`design-notes/10` 부록 D). 실무자 세션이 커밋 메시지에 "동작 그대로"라고 적었는데, 실제로는 서버가 열려는 주소를 잡지 못할 때(바인드 실패) 기동 로그 두 줄이 사라지는 차이가 있었다. 게이트웨이 세션과 새 맥락의 검증자가 이를 찾았고, 게이트웨이 세션은 실무자에게 메시지를 고치게 한 뒤에야 승인했다. 거꾸로 게이트웨이 세션의 보정 지시가 틀렸을 때는 실무자 세션이 따르지 않았고, 게이트웨이 세션이 자기 오류를 인정했다.

### 2. 결정은 선택지와 추천을 붙여 모아서 묻는다 (스킬 survey-gen)

AI가 "승인 대기 중"만 알리면 사람은 상황을 처음부터 파악해야 한다. 그래서 사람은 AI가 결정을 미리 정리해서 올리게 한다. 사람은 처음부터 생각할 필요 없이 고르기만 한다.

공개 규칙 RL-12(2단계)는 이것을 완전형의 전용 QA 세션(qa-master)에게 요구한다. 소규모 모드에는 이 의무가 없으니, 사람이 게이트웨이 세션의 지시문에 직접 적는다.

- 결정마다 **배경 한두 줄 · 선택지 2~3개 · 추천과 그 이유 · 답이 올 때까지 멈춰 있는 작업**을 붙인다. (설문 화면에서는 추천을 "권고", 멈춰 있는 작업을 "응답 전 보류 작업"이라고 부른다.)
- 결정이 여럿이면 하나씩 묻지 않고 설문 한 장으로 묻는다. `survey-gen` 스킬이 결정 목록을 HTML 설문으로 만들고, 사람이 고른 답을 기록한다. 사람은 권고안을 한 번에 고른 뒤 다르게 정할 문항만 바꿀 수 있다.

실전에서 게이트웨이 세션이 이렇게 했다(`design-notes/10` 부록 E-2·E-5). 세 청사진의 질문 17개를 표 하나로 묶고 권장안을 붙였다. 사람이 꼭 답해야 할 것은 사실상 2개로 줄었다. 구현 뒤에도 세 작업의 커밋 메시지에 공통으로 걸린 질문(범위 표기를 어떻게 할지)을 표 하나로 묶어 한 번에 물었다.

### 3. 짧은 승인은 대상이 분명할 때만 받는다 (공개 가이드 `docs/오케스트레이션-구성.md` 4걸음)

"권장대로 승인" 같은 짧은 답은 편하다. 다만 위 사례처럼 대상이 흐려진다. 그래서 공개 가이드는 게이트웨이 세션에게 이렇게 시킨다.

- 짧은 승인은 **어느 작업의 무엇을** 승인하는지 분명할 때만 유효하다.
- 게이트웨이 세션이 짧은 답을 펼쳐서("질문 3은 A로") 전달하려면, 펼친 내용을 사람에게 먼저 보여 주고 확인받는다.
- 대상이 분명하지 않으면 게이트웨이 세션은 짐작하지 않고 사람에게 되묻는다.

2번처럼 설문으로 물으면 문항마다 번호가 붙는다. 문항 제목에 작업 이름을 넣어 두면 사람의 답에도 작업 이름이 따라 나와, 이 문제가 처음부터 덜 생긴다.

### 4. 사람이 자리를 떠도 일이 멈추지 않게 한다 (설계 단계, 로드맵 0.4.0)

`design-notes/03`이 정리한 방법이다. 아직 공개판 규칙과 스킬에는 없다.

- **제쳐 두고 다음 일:** 실무자 세션은 사람의 답을 기다리는 동안 멈춰 서 있지 않는다. 막힌 일을 옆에 치워 두고 다른 일을 가져와 계속한다.
- **정한 때 모아 처리:** 사람은 요청이 올 때마다 답하지 않고, 스스로 정한 간격(예: 90분)에 쌓인 결정을 한 번에 처리한다.
- **먼저 하고 나중에 검수:** 되돌릴 수 있고 위험이 낮은 일은 AI가 먼저 하고 기록을 남긴다. 사람은 정한 때 기록을 보고, 문제가 있으면 되돌린다. 무엇을 이렇게 내릴지는 7장의 기준 4개(`reversibility-gate` 스킬)로 판정한다.

편의점에 비유하면, 사장님이 자리를 비우면 가게가 멈추던 구조를 바꾸는 것이다. 막힌 아르바이트생은 멍하니 서 있지 않고 다른 일부터 한다. 사장님은 계속 지켜보는 대신 정한 때 와서 쌓인 일을 처리한다.

### 알아 둘 한계

- **좁은 위임은 요청의 일부만 줄인다.** 청사진 승인과 push·병합은 계속 사람 몫이다. 세션이 많으면 이것만으로도 사람에게 오는 요청이 많다. 4의 설계가 공개판에 들어와도 이 요청의 수는 줄지 않는다. 사람이 언제 처리할지를 정할 수 있게 될 뿐이다.
- **실전 검증 표본이 작다.** 좁은 위임은 실전 검증 두 번(작업 세 건)에서 써 봤다. 질문 묶기는 실무자 셋이 함께 일한 한 번의 실전에서 두 번(청사진 질문, 커밋 질문) 나왔다. 모두 같은 저장소에서 했다.
- **`survey-gen`은 묻는 도구다.** 결정을 언제 모아 물을지는 도구가 정하지 않는다. 사람이 지시하거나 세션이 판단한다.

## 해 보기

저장소를 받은 폴더에서 아래 명령을 실행한다. Python 3만 있으면 된다. 설문은 임시 폴더에 만든다.

```sh
python3 skills/survey-gen/survey_gen.py new \
  --input examples/survey_demo.json --root /tmp/survey-demo
```

```
생성: /tmp/survey-demo/2026-11-21-01-가이드10장-예시
  설문ID: 2026-11-21-01-가이드10장-예시
  설문 화면: /tmp/survey-demo/2026-11-21-01-가이드10장-예시/survey.html
문항 2개. 사람에게 survey.html 경로를 전달하세요.
인덱스 갱신: /tmp/survey-demo/index.md (1건)
```

(날짜와 순번은 실행한 날에 따라 다르다. Windows에서는 `python3` 대신 `python`이나 `py`를 쓰고, 줄 끝의 `\`를 빼고 한 줄로 쓴다. `--root`에는 다른 임시 폴더를 준다. 예: 명령 프롬프트 `--root %TEMP%\survey-demo`, PowerShell `--root $env:TEMP\survey-demo`.)

출력된 `survey.html`을 브라우저로 연다. 세 가지를 본다.

- 실무자 세션 둘이 올린 결정이 **문항 하나씩**으로 정리돼 있다. 문항마다 작업 이름·배경·선택지·권고(추천)·응답 전 보류 작업이 붙어 있다.
- "권고안 일괄 선택"을 누르면 권고가 한 번에 골라진다. 사람은 다르게 정할 문항만 바꾼다.
- "답변 생성 및 복사"를 누르면 문항 번호와 문항 제목이 붙은 답이 클립보드에 복사된다. 이 예시는 문항 제목에 작업 이름을 넣어 두었으니 답에도 작업 이름이 나온다. "1~5 권장대로"처럼 대상이 흐려지지 않는다.

입력 파일 [`examples/survey_demo.json`](../../examples/survey_demo.json)을 열어 보면, AI 세션이 결정을 어떤 형식으로 정리해 넘기는지 알 수 있다. 실제로 쓸 때는 사람이 복사한 답을, 설문을 만든 AI 세션(소규모 모드라면 게이트웨이 세션)에 붙여 넣는다. 세션은 그 답을 `record`로 설문 폴더에 기록한다. 자세한 법은 [`skills/survey-gen`](../../skills/survey-gen/SKILL.md)에 있다.

## 확인

사람은 여러 세션을 쓰면서 아래를 점검한다. 앞의 두 줄은 소규모 모드 가이드에 없는 행동이라, 사람이 게이트웨이 세션의 지시문에 적어 둔 경우에만 기대할 수 있다.

| 확인 | 통과 기준 |
|---|---|
| 승인 요청에 무엇이 붙어 오나 (지시문에 적었을 때) | "대기 중"만이 아니라 배경·선택지·추천·멈춰 있는 작업이 붙어 온다 |
| 결정이 여럿일 때 (지시문에 적었을 때) | 하나씩 오지 않고 한 번에 모여 온다(표나 설문) |
| 짧게 답했을 때 | 대상이 흐리면 게이트웨이 세션이 짐작하지 않고 되묻는다 |
| 맡긴 게이트 | 위임기록에 적힌 게이트만 게이트웨이 세션이 승인하고, 승인 근거가 위임기록에 남는다 |
| 맡기지 않은 게이트 | 청사진, push·PR·병합은 매번 사람에게 온다 |
