# 6. "테스트 다 통과"라는데 실제로는 테스트를 실행해 보지 않았다

> **한 줄 해법:** AI의 "통과"라는 말 대신 **실제 명령과 출력을 인용**하게 한다. 인용할 것이 없으면 통과로 치지 않는다. 확인하지 못한 것은 확인하지 못했다고 적게 하고, 그 기록을 다른 눈이 한 번 더 본다.
>
> 급하면 [선택 제안](#선택-제안)으로 바로 간다.

## 문제

AI와 일하다 보면 이런 장면을 흔히 겪는다.

- AI가 "테스트를 모두 통과했다"고 보고한다. 실제로는 테스트 명령을 한 번도 실행하지 않았다.
- AI가 "화면이 정상 동작한다"고 보고한다. 화면을 띄워 본 적은 없고, 코드를 읽고 그렇게 판단했다.
- AI가 "검증 완료"라고 적는다. 검증한 것은 일부이고, 나머지는 적혀 있지 않다.

**실제로 있었던 일.** 이 가이드를 쓰던 날, 이 저장소를 작업하던 AI 세션이 공개 전 기밀 점검을 돌리고 "걸린 토큰 0건"이라고 보고했다. 그런데 셸이 파일 목록을 하나의 이름으로 다루는 바람에, 점검 명령은 실제로 아무 파일도 검사하지 않았다. 출력에 "몇 개를 검사했는지"가 없어서 0건이 그럴듯해 보였다. AI 세션이 그 점을 알아채고 다시 돌리자 이번에는 5개만 검사됐다. 한글 이름 파일이 빠진 것이다. 세 번째에 11개를 모두 검사했다. 결과는 처음과 같은 "0건"이었지만, 앞의 두 번은 근거가 없는 0건이었다.

**왜 생기나.**

- AI는 "작업을 끝내는 것"을 향해 간다. "통과했다"는 보고는 작업을 끝내는 가장 빠른 말이다.
- 코드를 읽고 내린 판단과 실제로 실행해 본 결과가 AI의 보고에서는 같은 말("동작한다")로 나온다.
- 도구가 "0건"이나 "통과"를 냈어도, 그 도구가 무엇을 검사했는지는 따로 보지 않으면 모른다.
- 보고에 "검증 완료" 같은 꼬리표나 완료 표시가 붙으면, 읽는 사람도 검수하는 AI도 덜 따지게 된다.

## 해결책 후보

| 후보 | 어떻게 | 아쉬운 점 |
|---|---|---|
| ① 말로 부탁 | 사람이 지시문에 "꼭 테스트하고 보고해"라고 적는다 | AI는 "했다"고 답한다. 무엇을 실행했는지는 보고에 남지 않는다 |
| ② CI만 믿기 | 사람이 저장소의 자동 테스트(CI)가 통과하면 된 것으로 본다 | CI는 자동 테스트가 있는 부분만 본다. 화면 동작, 렌더, 사람이 써 본 느낌은 CI 밖이다. 테스트가 0개여도 CI는 "통과"를 낸다. 하네스는 CI를 그대로 쓰지만, 그것만으로는 부족하다 |
| ③ 사람이 전부 다시 확인 | 사람이 AI가 확인했다는 것을 모두 직접 다시 해 본다 | 확실하지만 사람이 병목이 된다(10장) |
| ④ 증거와 미검증 기록 | AI가 확인한 것에는 실제 출력을 붙이고, 확인하지 못한 것은 못 했다고 적는다. 그 기록을 다른 눈이 다시 본다 | 기록이 늘어난다. AI가 출력을 붙여도, 그 출력이 무엇을 검사했는지는 사람이 한 번 봐야 한다 |

①과 ④의 차이는 이것이다. ①은 "확인했다"는 말을 믿는다. ④는 말 대신 **확인한 흔적**을 요구한다. 흔적이 없으면 확인하지 않은 것으로 본다.

## 선택 제안

**④를 쓰고, CI(②)는 바탕으로 함께 쓴다.** 네 가지를 함께 지킨다.

### 1. "통과" 대신 출력을 붙인다 (스킬 dlc-gate)

AI는 게이트를 통과했다고 속으로 판단하고 넘어가지 않는다. 대신 실제 문구와 명령 출력을 그대로 인용해 보여 준다. **인용할 것이 없으면 통과가 아니다.**

| 무엇을 확인했다고 할 때 | AI가 붙이는 것 |
|---|---|
| 테스트를 통과했다 | 실행한 명령과 그 출력(통과·실패 건수) |
| 사람이 승인했다 | 사람이 실제로 쓴 승인 문구 원문 |
| 커밋할 파일이 맞다 | `git diff --cached --stat` 출력 원문 |

사람은 붙은 출력에서 **몇 개를 검사했는지**를 본다. 위 사례의 "0건"이 그랬듯, 검사 대상 수가 없거나 0이면 결과가 맞아도 근거가 없다.

### 2. 못 한 것은 못 했다고 쓴다 (규칙 GL-20·GL-25·TS-07·CM-02)

- AI는 확인하지 못한 것을 "검증 완료"로 쓰지 않는다(GL-20).
- AI는 테스트하지 못한 경우를 따로 적는다(GL-25). 완료보고서에는 "미검증 사항" 칸이 있다(CM-02).
- 코드가 실제로 계산하거나 확인하지 않는 값은 "검증됨"으로 쓰지 않는다(TS-07). 예를 들어 화면이 API 값을 받아 보여 주기만 한다면, 그 값이 맞는지는 화면 테스트로 검증되지 않는다.
- 반대로 실제로 확인한 것은 "확인 필요" 같은 말로 흐리지 않고 그대로 단정한다(TS-07). 무엇을 확인했고 무엇을 못 했는지가 분명해야 사람이 어디를 볼지 안다.

예: 이 가이드를 만든 작업의 완료보고서는 "Windows에서는 검증하지 않았다(작업 환경이 macOS라서)"와 "클립보드 복사는 결과 칸까지만 확인했다"를 따로 적었다.

### 3. 결론을 미리 붙이지 않는다 (규칙 GL-29)

AI는 보고에 완료·통과를 나타내는 이모지나 꼬리표를 붙이지 않고, 상태는 글로 쓴다. 상태 표시가 결론을 미리 붙여 버리면, 읽는 사람과 검수하는 AI가 그 "검증 완료"를 덜 따진다.

### 4. 다른 눈으로 다시 본다 (스킬 dlc-gate)

AI는 "완료"를 보고하거나 커밋하기 직전에, 작업한 맥락을 물려받지 않은 새 검증자를 띄운다. 검증자는 완료보고서의 주장을 하나씩 대조하고, **확인할 수 없는 주장은 확인할 수 없다고** 따로 표시한다. 자세한 방식은 [9장](./09-합치니-깨짐.md)의 "4. 작업한 에이전트 대신 새 맥락의 검증자가 한 번 더 확인한다"에 있다.

### 알아 둘 한계

- 출력을 붙이는 것도 결국 AI가 하는 일이다. 사람은 붙은 출력이 무엇을 검사했는지를 한 번 봐야 한다. 하네스는 그 확인을 쉽게 만들 뿐 대신해 주지 않는다.
- 보고마다 근거의 종류(직접 확인 / 전에 겪은 일 / 추론)를 붙이는 방식은 실전 검증에서 나온 **규칙 후보**이고, 아직 규칙에 들어가지 않았다(설계 단계, `design-notes/10` 부록 E-6).

## 확인

사람이 하네스를 설치한 세션에 아래 일을 시켜 보고, AI의 보고를 통과 기준과 대조한다.

| 시켜 볼 것 | 통과 기준 |
|---|---|
| "테스트 돌리고 결과 알려 줘" | AI가 실행한 명령과 출력(통과·실패 건수)을 그대로 인용한다. "통과했다"는 말만 있으면 통과가 아니다 |
| 테스트가 없는 부분이 섞인 작업을 끝내게 하기 | 완료보고서의 "미검증 사항"에 무엇을 왜 확인하지 못했는지 적혀 있다 |
| 화면처럼 직접 봐야 하는 확인이 필요한 작업 | 직접 띄워 보지 못했으면 "확인하지 못했다"고 적는다. 코드를 읽은 판단을 "동작한다"로 쓰지 않는다 |
| 점검 도구가 "0건"·"통과"를 낸 보고 | 출력에 검사한 대상 수가 보인다 |

AI가 근거 없이 "통과"라고만 하면, 사람은 그 세션이 dlc-gate 스킬과 1단계 규칙을 읽고 있는지부터 확인한다(`rules/` 00 "읽는 방법").
