# 9. 작업 하나하나는 성공했는데 합치니 깨졌다

> **한 줄 해법:** 에이전트마다 보고한 "통과"로 끝내지 않고, 병합한 코드 전체를 다시 테스트한다. 병합은 언제든 버리고 다시 만들 수 있는 통합 브랜치에서 하고, 검증은 작업한 에이전트의 맥락을 물려받지 않은 새 세션이 한 번 더 맡는다.
>
> 급하면 [선택 제안](#선택-제안)으로 바로 간다.

[← 상황 지도로](./00-상황지도.md)

이 장이 이 하네스의 한 방이다. 하네스는 에이전트 하나하나가 성공했는지가 아니라, 그 결과들을 병합한 코드가 **전체 정합성**을 지키는지를 본다.

이 장의 등장인물:

- **사람** — 하네스를 쓰는 개발자. 병합과 배포를 결정한다.
- **에이전트 A·B·C** — 각자 자기 브랜치에서 작업하는 AI 세션.
- **검증자** — 작업한 에이전트의 맥락을 물려받지 않고 새로 띄운 AI 세션.

---

## 문제

에이전트 A와 B가 각자 일을 끝냈다. 둘 다 "테스트 통과, 완료"라고 보고했다. 사람이 두 브랜치를 병합했고, git은 충돌을 내지 않았다. 그런데 병합한 코드를 실행하면 오류가 난다.

흔한 경우는 이렇다.

- A가 함수 이름을 바꾸고, 자기가 아는 호출부를 다 고쳤다.
- 그 사이 B가 옛 이름을 쓰는 새 기능을 만들었다.
- A와 B가 고친 줄이 겹치지 않아서 git은 충돌을 내지 않는다. 그런데 B의 새 코드는 A가 없앤 이름을 부른다.

[해 보기](#해-보기)에서 이 상황을 1분 만에 직접 만들어 볼 수 있다.

**왜 생기나.**

- 에이전트는 **자기 브랜치만** 본다. A는 B가 같은 시간에 무엇을 바꾸는지 모른다.
- A와 B가 보고한 "테스트 통과"는 각자 **자기 브랜치에서** 실행한 결과다. 병합한 코드는 아무도 테스트하지 않았다.
- git의 "충돌 없음"은 두 변경이 **같은 줄을 건드리지 않았다**는 뜻이다. 병합한 코드가 동작한다는 뜻이 아니다.
- A가 자기 작업을 직접 검증하면, 작업할 때의 맹점을 검증에도 그대로 가져간다. A는 자기가 아는 호출부만 고쳤으니, 검증할 때도 다른 곳에서 옛 이름을 쓸 가능성을 떠올리지 못한다. A의 맥락을 이어받은 검증자도 마찬가지다.

## 해결책 후보

| 후보 | 어떻게 | 아쉬운 점 |
|---|---|---|
| ① 각자 통과하면 끝 | 에이전트마다 자기 브랜치에서 테스트·CI를 통과하면 사람이 병합한다 | 병합한 코드는 아무도 테스트하지 않았다. 위 예가 정확히 이 경우다 |
| ② 일단 main에 다 병합하고 검증 | 여러 기능이 함께 동작해야 하는 검증이라, 개발자가 기능 브랜치를 main에 모두 병합한 뒤 테스트한다 | 원본 SI 프로젝트에서 실제로 겪었다. main은 "배포된 것"의 기준인데, 개발자가 검증하려고 병합한 미완성 코드가 main에 그대로 남았다. 한 기능에서 문제가 나도 그 기능만 main에서 빼내기 어렵다 |
| ③ 작업한 에이전트가 병합 결과도 검증 | 작업한 에이전트가 병합한 코드까지 직접 확인한다 | 에이전트가 작업할 때의 맹점을 검증에도 가져간다. 이 하네스의 실전 검증에서, 게이트웨이 세션이 같은 맥락에서 검증해 전부 통과시킨 결과를 새 맥락의 검증자가 다시 확인하자 문제 3건이 나왔다 |
| ④ 통합 브랜치 + 새 맥락 재검증 | 버릴 수 있는 통합 브랜치에서 병합해 테스트한다. 검증은 작업한 에이전트의 맥락이 없는 검증자가 맡는다. 사람이 내보낼 것만 골랐으면 그 조합 그대로 한 번 더 테스트한다 | 검증이 한 번 더 들고, 누군가 통합 브랜치를 관리해야 한다. 공통 코드가 얽히면 하나만 빼내기는 여전히 어렵다(아래 한계) |

②가 틀린 건 "병합해서 검증한다"가 아니다. 여러 기능이 함께 동작해야 하는 검증은 병합해야만 할 수 있다. 문제는 **병합한 장소**다. 개발자가 병합할 곳이 main밖에 없어서, 검증용으로 병합한 코드가 main에 남았다.

## 선택 제안

**④를 쓴다.** 아래 네 가지를 함께 지킨다. 1·4는 하네스 규칙·스킬에 들어 있다. 2·3은 아직 규칙이 없어 사람이 손으로 하는 절차다(설계 단계).

### 1. 병합은 통합 전용 브랜치에서 한다 (규칙 BR-05)

요리에 비유하면 이렇다. 전체 맛을 보려면 재료를 다 합쳐야 한다. 그런데 손님상(main)에서 합쳐 맛보면, 실패한 맛이 그대로 손님에게 나간다. 그래서 **임시 작업대**에서 합쳐 맛보고, 통과한 것만 손님상에 담는다.

- 기능 브랜치는 팀 dev 브랜치에 병합해 통합 검증한다(BR-05). 병합은 승인 기록이 있으면 담당 에이전트가, 없으면 사람이 한다(BR-06).
- 팀 dev는 통합 검증 전용이라, 사람도 에이전트도 팀 dev를 팀 main으로 올리지 않는다.
- 에이전트는 새 작업 브랜치를 팀 dev가 아니라 팀 main에서 만든다. 그래야 다른 에이전트가 검증하려고 팀 dev에 병합해 둔 미완성 코드가 새 작업에 섞이지 않는다.

### 2. 검증이 실패하면 그 기능만 빼고 다시 병합한다 (설계 단계, 손으로)

임시 작업대는 언제든 치우고 다시 차린다. 통합 브랜치에 A·B·C를 병합했는데 C 때문에 테스트가 실패하면, 병합을 맡은 사람(또는 에이전트)이 통합 브랜치를 버리고 A·B만 다시 병합한다. C를 맡은 에이전트는 자기 브랜치에서 고친 뒤 다음 병합 때 다시 들어온다. main에도, 다른 에이전트의 브랜치에도 C가 들어간 적이 없으니 C의 미완성 코드가 다른 작업을 깨지 않는다.

### 3. 내보낼 것만 골랐으면, 그 조합 그대로 다시 테스트한다 (설계 단계, 손으로)

사람은 검증을 통과한 것을 전부 내보내지 않고 "이번엔 A와 C만" 고를 때가 있다. A·B·C를 병합한 코드는 테스트를 통과했어도, **A·C만 병합한 코드는 아직 아무도 테스트하지 않았다.** 그래서 내보낼 조합 그대로 병합해 한 번 더 테스트한다. 손님상은 한 번 나가면 무르기 어렵다.

이 하네스의 실전 검증에서도 같은 일이 있었다. 사람의 지시로 게이트웨이 세션이 PR 두 개를 차례로 병합했다. 게이트웨이 세션은 첫 번째 PR을 병합한 뒤, 두 번째 PR이 여전히 충돌 없이 병합되는지 GitHub에서 다시 확인하고 병합했다. 그다음 병합된 main에서 전체 테스트를 다시 실행했다.

### 4. 작업한 에이전트 대신 새 맥락의 검증자가 한 번 더 확인한다 (스킬 dlc-gate)

에이전트는 "완료"를 보고하거나 커밋하기 직전에, 완전히 새 맥락의 검증자를 하나 띄운다. 검증자는 청사진·완료보고서·변경 내용과 규칙 문서를 직접 읽고, 항목마다 통과·실패와 근거를 보고한다. 실패가 나오면 에이전트는 그걸 조용히 넘기지 않고 근거째 사람에게 올린다(`dlc-gate` 스킬의 "독립 재검증").

실전에서 이 검증자가 실제로 문제를 찾았다. 게이트웨이 세션이 같은 맥락에서 한 검증은 전부 통과였는데, 새 맥락의 검증자가 완료보고서의 항목 누락, 커밋 이름 규칙 차이, 완료보고서의 사실 오류를 찾아냈다. 두 작업 모두에서 찾았다.

### 알아 둘 한계

- **얽힌 변경은 하나만 빼낼 수 없다.** B가 여러 기능이 같이 쓰는 공통 코드를 고쳤고 C도 그 코드를 쓴다면, 사람이 "C만 내보내기"로 골라도 실제로는 C와 B의 공통 코드 수정을 함께 내보내야 한다. 설계 문서(`design-notes/05`)가 제안하는 대응은 세 가지다. 에이전트가 공통 코드를 고치면 일찍 알린다. 공통 코드 수정은 처음부터 별도 작업으로 뗀다. 남는 비용은 사람이 미리 보고 고르게 한다. 얽힘 자체를 없애지는 못한다.
- **아직 설계 단계인 것:** "버리고 다시 만드는 통합 브랜치"와 "고른 조합 그대로 다시 테스트하기"는 설계 문서(`design-notes/05`)에 정리돼 있지만, 배포된 규칙에는 아직 들어가지 않았다. 지금 규칙에 있는 것은 팀 dev 통합 검증(BR-05)과 새 맥락 재검증(`dlc-gate`)이다.

## 해 보기

저장소를 받은 폴더에서 아래 명령을 실행한다. git과 Python 3만 있으면 되고, 스크립트는 임시 폴더에서만 작업한다.

```sh
bash examples/merge_break_demo.sh
```

```
== A 브랜치 테스트
  합계 통과
== B 브랜치 테스트
  합계 통과
  영수증 통과
== 병합: 충돌 없음
== 병합한 main 테스트
  합계 통과
  실패: ImportError: cannot import name 'total' from 'price' (...)
```

세 줄을 본다.

- A 브랜치와 B 브랜치는 **각자 테스트를 통과**했다.
- 스크립트가 두 브랜치를 main에 병합했고, git은 **충돌을 내지 않았다**.
- **병합한 main의 테스트는 실패했다.** B가 만든 영수증 기능이 A가 없앤 옛 이름 `total`을 부른다.

각 브랜치의 "통과"와 git의 "충돌 없음"만으로는 이 문제를 못 찾는다. 병합한 코드를 직접 테스트해야 드러난다.

## 확인

사람은 여러 작업을 병합할 때 아래를 점검한다.

| 확인 | 통과 기준 |
|---|---|
| 어디서 병합해 검증했나 | main이 아니라 통합 전용 브랜치(팀 dev 등)에서 병합하고 테스트했다 |
| 무엇을 테스트했나 | 각 브랜치가 아니라 **병합한 코드**를 테스트했다 |
| 누가 검증했나 | 작업한 에이전트의 맥락을 물려받지 않은 검증자가 한 번 더 확인했다 |
| 일부만 내보낼 때 | 내보낼 조합 그대로 병합해 다시 테스트했다 |
