# AI-DLC 하네스 (naroo)

**한국어** · [English](./README.en.md) — *English version of this page.*

**AI 에이전트는 "완료"라고 한다. 그 결과가 시스템 전체와 맞물리는지는 누가 확인하나?**

이 저장소는 Claude Code에 설치하는 플러그인입니다. 규칙 문서와 스킬(Claude가 정해진 때에 꺼내 쓰는 절차·도구)로 되어 있습니다. 설치하면 Claude가 작업 하나를 성공시키는 데서 멈추지 않고, 그 결과가 **시스템 전체의 정합성**을 깨지 않는지 확인하는 절차를 지킵니다. 사람이 결정할 지점에서는 멈추고 묻습니다.

AI-DLC(AI-Driven Development Lifecycle)는 AI가 계획·설계·코드·테스트를 맡고 사람이 검토·승인하는 개발 방법론입니다. 이 하네스는 SI 실무에서 필요할 때마다 조금씩 쌓아 온 규칙을 그 흐름 위에 정리한 것입니다.

처음이라면 [어떤 상황에서 이 하네스가 유용할까?](./docs/guide/00-상황지도.md)부터 읽어 보세요. "묻지도 않고 커밋했다", "하나하나는 성공했는데 합치니 깨졌다"처럼 AI를 쓰다 겪는 문제로 찾는 안내서입니다.

---

## 왜 만들었나

이 하네스는 실제 공공 조달 차세대 구축 사업(2026)에서 쓰던 것을 익명화해 공개한 것입니다. 그 사업에서는 AI 세션 여러 개에 역할을 나눠 화면을 개발했고, 이런 일을 겪었습니다.

- AI가 "완료, 테스트 통과"라고 보고한 작업도 다른 작업과 합치면 깨졌다.
- AI가 묻지도 않고 커밋하거나 파일을 지웠다.
- 세션이 늘수록 모든 승인 요청이 사람 한 명에게 몰렸다.

그때마다 규칙을 하나씩 더했습니다. 그 사업에서 하네스는 **화면 34개를 일정보다 한 달가량 앞당겨 납품**하는 데 쓰였고, **규칙 13개·스킬 27개·도구 31개**까지 늘었습니다. 역할을 나눈 AI 세션 7개(QA·규칙 관리·도구 제작·서비스별 구현)를 운영했고, 멈춘 세션을 찾으려고 10분 간격으로 순찰했습니다. 공개판은 그중 프로젝트에 묶이지 않은 핵심을 추린 것입니다. 익명화 방식은 [`NOTICE.md`](./NOTICE.md)에 있습니다.

## 누구를 위한 것인가

에이전트가 작업에 성공한 것으로 끝나지 않고, 전체 정합성을 지켜야 끝이라고 보는 SI·한국어 개발자. 그리고 그 확인을 나중에 다시 따라가 볼 수 있어야 한다고 보는 사람.

## 기능 하나를 맡기면 이렇게 진행된다

아래는 하네스의 기본 흐름입니다. 단계마다 출시 전 시험([gate3-trial](https://github.com/neisii/gate3-trial), 공개 저장소)에서 실제로 있었던 일을 붙였습니다. 그 시험은 작은 주문 처리 시스템을 만드는 일이었습니다. 먼저 뼈대(주문과 주문 상태 셋)를 만들고, 이어서 세 기능(주문 부분취소, 일별 매출 집계, 상태별 알림 문구)을 AI 세션 셋이 동시에 만들었습니다.

1. **사람이 작업을 맡깁니다.** 시험에서는 뼈대 작업부터 맡겼습니다.
2. **Claude는 바로 코드를 쓰지 않고, 먼저 청사진을 쓰고 멈춥니다.** 청사진은 고칠 파일, 테스트 계획, 사람이 정할 질문을 적은 작업 계획입니다. 시험에서 뼈대 청사진에는 부분취소 기능이 매출 집계와 알림 문구에 영향을 준다는 참고 메모가 있었습니다. 사람과 다른 세션 사이에서 메시지를 전하던 AI(게이트웨이 세션)가 이 메모를 "세 기능을 시작하기 전에 사람이 정할 일"로 따로 올렸습니다.
3. **사람이 청사진을 승인하고, 올라온 결정을 내립니다.** 승인 전에는 구현을 시작하지 않습니다. 시험에서 사람은 뼈대 청사진을 승인했고, 세 기능을 시작하기 전에 그 영향을 어떻게 다룰지 정했습니다. 매출 집계와 알림 문구는 일단 기존 상태 셋만 다루고, 부분취소를 합친 뒤 따로 고치기로 했습니다. 이때 후속 작업 둘이 생겼습니다.
4. **Claude가 구현하고 테스트합니다.** "테스트 통과"라고만 말하지 않고, 실행한 명령과 출력을 그대로 인용합니다. 확인하지 못한 것은 못 했다고 적습니다.
5. **작업 대화를 물려받지 않은 다른 AI(새 맥락의 검증자)가 결과를 다시 확인합니다.** 시험에서는 부분취소 기능을 합치기 전에, 병합 계획을 검증하던 검증자가 합친 코드를 실제로 실행해 봤습니다. 결제한 주문 두 건(합계 6,000원) 가운데 한 건을 부분취소하자, 남은 금액 3,000원까지 매출에서 빠져 합계가 4,000원이 아니라 1,000원이 됐습니다. 각 기능의 테스트는 모두 통과한 상태였습니다. 이 숫자가 매출 쪽 후속 작업 청사진의 근거가 됐고, 그 작업은 "모든 주문 상태가 매출에 넣을지 뺄지 정해져 있다"는 테스트를 더해 같은 일이 조용히 다시 생기지 않게 했습니다.
6. **커밋하기 전에 Claude가 커밋 계획(브랜치, 넣을 파일, 커밋 메시지)을 보여 주고, 사람이 승인합니다.** push와 병합도 사람 몫입니다. 시험에서는 선택 기능인 좁은 위임을 켜 두었습니다. 그래서 커밋 계획은 게이트웨이 세션이 직접 확인과 새 맥락 재검증을 둘 다 통과한 뒤 승인했고, 걸리는 것은 사람에게 올렸습니다. push는 사람이 그때그때 지시해 게이트웨이 세션이 했고, main 병합은 사람이 했습니다.
7. **합칠 때는 작업마다 통과했어도, 합친 결과를 다시 테스트합니다.** 시험에서는 main에 넣기 전에 마지막 조합을 미리 만들어 테스트 90건이 통과하는 것을 확인했고, 병합한 뒤 main에서 다시 확인했습니다.

사람이 판단하는 곳은 3번과 6번, 그리고 push·병합입니다. 나머지는 Claude가 하되, 다시 확인할 수 있게 근거를 남깁니다. 설치하면 `dlc-gate` 스킬이 "구현해", "커밋해", "완료했어" 같은 말에 반응해 이 순서를 안내합니다.

## 핵심 개념

1. **사람 게이트.** 게이트는 사람의 승인을 받아야 넘어가는 지점입니다. 청사진(작업 계획) 승인 전에는 구현하지 않고, 커밋 계획 승인 전에는 커밋하지 않습니다.
2. **확인한 것만 확인했다고 쓴다.** "통과"라는 말 대신 실행한 명령과 출력을 인용합니다. 확인하지 못한 일은 "확인하지 못함"으로 적고 넘어가지 않습니다.
3. **새 맥락 재검증.** 작업한 AI와 같은 대화 맥락을 가진 검증자는 같은 것을 놓칩니다. 그래서 커밋 승인 전에, 그 맥락을 물려받지 않은 AI가 한 번 더 봅니다. 위 예의 5번이 이것입니다.
4. **자기 채점 금지.** 결과를 만든 세션은 그 결과를 승인하지 않습니다.
5. **가역성 판정과 거부권.** 규칙에 정해 두지 않은 새 상황에서 "혼자 해도 되나, 멈추고 물어야 하나"를 기준 4개(되돌릴 수 있나 · 요구가 명확한가 · 영향 범위 · 사람이 정할 업무 규칙인가)로 판정합니다. 그중 셋(되돌릴 수 있나 · 요구가 명확한가 · 업무 규칙인가)은 거부권이 있습니다. 하나만 걸려도 다른 기준과 상관없이 멈추고 사람에게 묻습니다.
6. **플랫폼 기능을 쓰고, 다시 만들지 않는다.** 하네스는 전체 흐름을 잡는 것이지 모든 것을 통제하지 않습니다. 권한, 커밋 귀속 문구, 백그라운드 세션처럼 Claude Code에 이미 있는 설정은 그것을 씁니다.

Claude Code를 만든 쪽도 공식 블로그의 [활용 안내 글](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/)에서 비슷한 사용법을 권합니다. 끝났다고 볼 기준을 정해 맡기고, 파괴적인 일 앞에서 멈추게 하고, 결과를 확인하라는 것입니다. 이 하네스는 그 권장을 SI 팀이 매번 지키도록 규칙·게이트·기록으로 고정하고, 두 가지를 더합니다. 작업 하나가 아니라 합친 전체를 확인하는 것, 그리고 여러 세션을 사람의 결정 아래 엮는 것입니다.

## 두 가지 쓰는 법

| | 세션 하나로 (0.1부터) | 여러 세션으로 나눠서 (0.2.0, 선택) |
|---|---|---|
| 무엇 | Claude Code 세션 하나가 위의 규율을 지킨다 | 작업을 여러 세션에 나눠 동시에 진행한다. 사람(결정) → 게이트웨이 세션(사람과 다른 세션 사이에서 메시지를 전하고 진행을 지켜보는 AI) → 실무자 세션(구현하는 AI) |
| 누가 승인하나 | 사람 | 기본은 사람. 게이트웨이는 승인을 원문 그대로 전하고, 맡지 않은 일은 사람에게 올린다. 좁은 위임(선택)을 켜면 커밋 계획처럼 되돌릴 수 있는 게이트만 게이트웨이가 직접 확인과 새 맥락 재검증을 거쳐 승인한다 |
| 필요한 것 | 플러그인 설치 | 플러그인 + 게이트웨이에 맡긴 일을 적은 위임기록 한 장. 원본 사업에서 쓰던 전용 QA 세션, 대기 장부(세션마다 누구에게 무엇을 기다리는지 적는 장부), 순찰 없이 사람이 그 역할을 맡는다(이것을 소규모 모드라 부른다. 원본 사업의 전체 구성은 완전형이라 부른다) |
| 안내 | [`rules/`](./rules/향상된_AI-DLC_00-핵심규칙요약.md) (`00`부터) | [`docs/오케스트레이션-구성.md`](./docs/오케스트레이션-구성.md) |

여러 세션 구성은 0.2.0에서 새로 들어왔습니다. 실제 저장소 작업에 써 보며 검증했고(게이트 왕복, 좁은 위임, 실무자 세 명이 PR·병합까지 간 작업), 출시 전에는 위 예의 시험에서 실무자 네 명이 서로 영향을 주도록 일부러 짠 작업들을 처음부터 끝까지 다뤘습니다. 아직 표본이 작아, 안내서에 검증하지 않은 부분을 따로 표시해 두었습니다.

## 설치

필요한 것: [Claude Code](https://claude.com/claude-code), Python 3(스킬 스크립트와 예제가 씁니다. Windows에서는 `python3` 대신 `python`이나 `py`).

```sh
# Claude Code 안에서
/plugin marketplace add neisii/harness-naroo
/plugin install ai-dlc-harness@harness-naroo
```

설치 뒤 재시작하거나 `/reload-plugins`를 실행합니다. 규칙 문서는 플러그인 폴더에서 읽힙니다.

- **설치 확인:** 터미널에서 `claude plugin list`를 실행해 `ai-dlc-harness@harness-naroo`가 `enabled`로 보이면 됩니다.
- **적용 범위:** 설치할 때 범위를 고릅니다([공식 문서](https://code.claude.com/docs/en/plugins/install#choose-an-install-scope)). `/plugin` 화면에서는 나에게(모든 프로젝트, user) · 이 저장소의 협업자 모두에게(project) · 나에게, 이 저장소에서만(local) 가운데 고르고, 터미널의 `claude plugin install`은 기본이 user 범위입니다(`--scope project`·`--scope local`로 바꿉니다). 하네스를 한 프로젝트에서만 쓰려면 local이나 project로 설치합니다. user 범위로 설치했는데 어떤 프로젝트에서는 끄고 싶으면, 그 프로젝트 폴더에서 `claude plugin disable ai-dlc-harness@harness-naroo --scope local`로 끕니다(그 폴더에서만 꺼집니다). `dlc-gate`는 "구현해", "커밋해" 같은 말에 반응해 켜지므로, 범위를 정해 두는 편이 좋습니다.

로컬 사본으로 시험하려면, 먼저 저장소를 내 컴퓨터에 복제합니다.

```sh
# 터미널에서
git clone https://github.com/neisii/harness-naroo.git
```

그다음 Claude Code에서 복제한 폴더를 마켓으로 등록하고 설치합니다.

```sh
# Claude Code 안에서
/plugin marketplace add <복제한 폴더 경로>
/plugin install ai-dlc-harness@harness-naroo
```

## 해 보기

명령 하나로 가역성 판정이 어떻게 나오는지 볼 수 있습니다. 예제가 다섯 가지 상황을 기준 4개로 판정해, 각각 "혼자 한다(A) / 하고 나서 알린다(B) / 먼저 묻는다(C) / 보류하고 묻는다(D)" 가운데 하나로 나눕니다.

```sh
python3 examples/reversibility_demo.py
```

출력 가운데 세 가지를 옮깁니다.

```
[1] 내 feature 브랜치에서 변수 오타 수정
    → A 자율 실행   되돌릴 수 있고, 확실하고, 내 구역. 혼자 한다.

[3] 할인율을 15%로 코드에 반영
    → C 사전 승인   ④ '사람이 정할' 사업 결정 (거부권) — 되돌릴 수 있어도 혼자 못 정한다.

[4] 화면설계서에 '거기 그거 처리'로만 적힌 항목 구현
    → D 보류·질의   ② 뭘 하란 건지 모른다 (거부권) — 옆으로 치우고 다음 일부터.
```

눈여겨볼 것은 [3]번입니다. 할인율을 바꾸는 코드는 되돌릴 수 있고 요구도 명확해서 AI가 알아서 해도 될 것 같지만, 판정은 "C 사전 승인(먼저 묻는다)"입니다. 할인율은 사람이 정할 사업 결정이기 때문입니다. 다른 기준이 모두 괜찮아도 거부권 기준 하나에 걸리면 멈춥니다. 5분 안에 따라 할 수 있는 안내는 [QUICKSTART.md](./QUICKSTART.md)에 있습니다.

이 예제는 맛보기입니다. 하네스가 실제로 쓸모 있는 곳은 내 프로젝트입니다. 설치하면 위 "기능 하나를 맡기면"의 순서대로, 결정이 필요한 지점마다 Claude가 멈추고 확인을 받습니다.

설치하지 않고 바로 쓸 수 있는 도구도 있습니다. 한국어 문서에서 번역투·이모지·2인칭 호칭을 찾아내는 서술 린터입니다(Python 표준 라이브러리만 사용).

```sh
python3 skills/seosul-lint/seosul_lint.py <문서 폴더>
```

**규칙 12단계**

규칙은 단계마다 한 문서이고, 각 규칙에 ID(예: `CS-01`)가 붙어 있습니다. Claude는 해당 행동을 하기 직전에 그 단계 문서를 읽습니다.

| 단계 | ID | 다루는 것 |
|---|---|---|
| 1 | `GL` | 모든 작업에 걸리는 기본 규칙(짐작으로 채우지 않기, 확인한 것만 쓰기, 삭제는 휴지통으로, 서술 규칙 등) |
| 2 | `RL` | 사람이 정할 것과 AI가 할 것 |
| 3 | `RQ` | 구현 전 조사 범위, 사람에게 묻는 질문 형식, 청사진 양식 |
| 4 | `GT` | 구현 시작 승인(청사진 승인 전엔 구현하지 않음) |
| 5 | `CM` | 결과 검토, 완료보고서, 커밋 메시지 |
| 6 | `AG` | 세션끼리 주고받는 법, 다른 세션에 작업을 맡기는 지시 형식 |
| 7 | `BR` | 브랜치 이름과 병합 흐름 |
| 8 | `AR` | 청사진·완료보고서 같은 산출물의 위치와 형식, 인계 문서 |
| 9 | `CC` | 공통코드 조사와 후보 제시 |
| 10 | `TS` | E2E 테스트 시나리오와 테스트 계정 |
| 11 | `CS` | 커밋 계획 승인, 스테이징 대조, 위험한 git 명령 |
| 12 | `WT` | 작업 브랜치·워크트리 만들기, push, 서버 구동 |

## 유의할 점

- **규칙은 한국어 정본**입니다. 번역본과 내용이 갈라지지 않도록 기계 번역하지 않았습니다. 영어를 쓰는 분은 [README.en.md](./README.en.md)와 [`docs/overview-en.md`](./docs/overview-en.md)를 읽어 보세요. 대화 언어는 하네스가 정하지 않습니다.
- **고쳐 쓰지 말고 바꿔 읽기.** 규칙에는 원래 팀의 구체 값이 예시로 남아 있습니다. 무엇을 바꿔 읽을지는 [`docs/환경값-정의.md`](./docs/환경값-정의.md)에 모았습니다.
- 원래 하네스는 **Windows**의 PowerShell/C# 도구와 함께 운영됐습니다. 그 플랫폼 전용 도구는 빼고, 공용 스킬로 다시 썼습니다.
- 내부 하네스 전체가 아니라 **추린 핵심**입니다. 프로젝트에 깊이 묶인 기능(시나리오 검증, 문서 통합 등)은 방법론으로만 소개했습니다.
- **데이터:** 플러그인은 로컬에서 동작하며 개인·프로젝트 데이터를 밖으로 보내지 않습니다. 외부 호출은 `claude-update-check`가 Claude Code 최신 버전·체인지로그를 GitHub·npm에서 읽는 것 하나뿐입니다(버전 정보만). 일부 규칙은 로컬의 읽기 전용 DB 자격증명(`~/.claude/secrets/devdb_readonly.env`, AG-08)을 읽지만 출력·기록·전송하지 않으며, 비밀은 동봉돼 있지 않습니다.
