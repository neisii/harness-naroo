# 1단계 · 전역 제약

> **목적:** 모든 AI가 지켜야 할 기본 규칙과, 한 화면을 기준으로 한 전체 작업 흐름을 정한다.
> **언제 읽나:** 화면/기능 구현 지시를 받았을 때 항상([00 요약](향상된_AI-DLC_00-핵심규칙요약.md) 2장).

## 규칙

### 프로젝트/권한

| ID | 규칙 |
|---|---|
| GL-01 | 현재 작업 프로젝트 외의 프로젝트 코드는 임의로 수정하지 않는다. |
| GL-02 | 다른 프로젝트의 정보가 필요하면 추측하지 않고 질문/정보 요청을 한다. |
| GL-03 | 다른 프로젝트의 코드를 직접 수정해야 한다고 판단되면 먼저 사람(또는 2단계 RL-12 위임에 따라 qa-master)에게 확인받는다. **[사람 확인]** |
| GL-04 | 사람이 지정한 프로젝트 폴더에서만 작업한다. 워크트리를 쓰면 12단계 WT-02로 만든 그 워크트리가 작업 폴더다. 단, 산출물은 8단계 AR-01 원본 경로에 쓴다(12단계 WT-07). |
| GL-05 | 12단계 WT-02로 만든 브랜치에서만 작업한다. |

### 판단

| ID | 규칙 |
|---|---|
| GL-16 | 업무 규칙이 불명확하면 추측하지 않는다. 업무 규칙의 결정은 2단계 RL-12에 따라 qa-master에게 위임돼 있으므로, 불명확하면 qa-master에게 질의해 근거와 함께 확정받는다. 개발DB 행 데이터는 업무 규칙의 근거가 아니다. 근거는 테이블 명세·문서·기획·공통코드 정의이며, 행 값은 환경 사실 확인에만 쓴다. |
| GL-17 | 기획 의도가 불명확하면 임의로 결정하지 않는다. 단, 2단계 RL-12 위임 범위 안에서는 qa-master가 근거를 기록하고 확정할 수 있다(기획 담당자만 아는 사실 포함). |
| GL-18 | 구현 방법이 여러 개이고 선택에 따라 영향이 달라지면 선택지를 제시하고 사람(또는 2단계 RL-12 위임에 따라 qa-master)의 결정을 받는다. **[사람 확인]** |
| GL-19 | 문서와 실제 코드/DB가 다르면 어느 하나를 임의로 정답으로 간주하지 않는다. 단, 테이블·컬럼은 3단계 RQ-03을 따른다(테이블 명세가 구현 기준이므로 명세 기준으로 진행하고 차이를 알린다). |
| GL-20 | 검증하지 못한 사항을 검증 완료로 기록하지 않는다. |

### 파일·폴더 삭제

| ID | 규칙 |
|---|---|
| GL-28 | ① 파일·폴더를 지울 때는 **휴지통 이동이 기본**이다. 크로스플랫폼으로는 `safe-delete` 스킬을 쓴다(OS별 휴지통 처리를 대신함; 예: Windows는 `Microsoft.VisualBasic.FileIO.FileSystem`의 `SendToRecycleBin`). `rm`·`Remove-Item` 같은 영구 삭제는 사람(또는 2단계 RL-12에 따라 qa-master)에게 확인받은 뒤에만 한다(12단계 WT-14·WT-15의 워크트리 삭제 확인이 이에 해당). 임시 폴더나 빈 폴더라고 해서 예외로 두지 않는다. ② 여러 세션이 쓰는 공용 산출 폴더의 상위 폴더는 통째로 지우거나 비우고 다시 만들지 않는다. 대상은 `<공유문서 루트>\단위테스트\개선시나리오`·`검증결과`·`원본시나리오`·`판정보정`, `<공유문서 루트>\지시대기\대기현황`, 그리고 단위테스트 산출의 `_작업중` 폴더이며, 그 아래 타임스탬프·세션 하위 폴더는 소유 세션만 정리한다. `_작업중` 폴더는 폴더 자체를 지우거나 비우고 다시 만들지 않되, 그 안의 파일을 같은 이름으로 덮어쓰는 것은 허용한다(덮어쓰기와 비우기를 구분한다). 새 공용 폴더가 생기면 이 목록에 추가한다. ③ 삭제 전에 파일 수·소유 세션·git·백업 여부를 확인한다. ④ 테스트·검증용 산출은 `_`로 시작하는 fixture 경로를 쓰고 공용 폴더에 섞지 않는다. ⑤ AI 세션이 실행하는 스크립트·도구가 내부에서 파일·폴더를 지우는 경우도 이 규칙을 따른다. 도구가 지우는 대신 휴지통 이동을 쓰거나, 도구의 삭제를 사전에 확인받고 백업본을 보관한다(예: `api-spec-gen --apply` — 원본 SI 예시, 공개판에 없음). |

### 서술·표기

| ID | 규칙 |
|---|---|
| GL-29 | 산출물과 사람과의 소통 **전 과정**에서 서술 규칙을 지킨다. ① **이모지를 쓰지 않는다** — 완료·주의·경고 같은 상태나 강조는 텍스트로 표시한다. (근거: AI는 선호 학습 탓에 이모지를 남발하는데, 상태 이모지는 **결론을 미리 라벨링**해 읽는 사람과 **검수하는 AI의 판단을 편향**시킨다 — 특히 "검증 완료" 표시를 덜 따지게 만들어 GL-20을 약화한다 — 가독성도 해친다.) ② **과장을 줄인다** — 단정적·과장된 표현은 사실에 맞게 낮춘다. ③ 한국어 산출물은 **번역투·2인칭·수량 표기**를 `seosul-lint` 스킬로 점검한다. |

## 전체 흐름 (한 화면 기준)

`[H]`는 사람이 반드시 개입하는 지점이고, 나머지는 AI가 주도한다. 단 2단계 RL-12 위임 범위의 `[H]` 지점은 qa-master가 사람을 대신할 수 있다.

```
[H]    0. 화면/프로젝트 지정
[AI]   1. 문서·코드·DB·API 조사
[AI]   2. 질문/불확실성 분류
[H]    3. 질문 답변·결정·기획확인
[AI]   4. 구현 청사진 작성
[H]    5. 청사진 검토 및 구현 승인
[AI]   6. 구현
[AI]   7. 컴파일/ArchitectureTest/테스트/E2E
[AI]   8. 구현·검증 결과 문서화
[H]    9. 요구사항 ↔ 결과 대조           (5단계 CM-01)
[AI]  10. 완료 보고서 작성               (5단계 CM-02)
[H]   11. 최종 승인: 커밋 계획 승인       (11단계 CS-01)
[AI/H] 12. 커밋(AI), 팀 dev·팀 main 병합(qa-master 승인 후 developer) 및 루트 main PR(사람)     (7단계 BR-05·BR-06, RL-12)
```

- 브랜치는 사람이 지정하지 않는다. 사람이 화면/프로젝트를 지정하면 AI가 12단계 WT-02 절차대로 브랜치·워크트리를 만든다.

## 체크리스트

- [ ] GL-01~05 지정된 프로젝트·작업폴더와 WT-02로 만든 브랜치 밖을 임의로 건드리지 않았는가?
- [ ] GL-06~09 신규로 만들기 전에 기존 API·Client·공통 기능을 확인했는가?
- [ ] GL-10~15 core·공통 영역·화면 규칙을 지켰고, 공통 영역 수정과 화면설계서·퍼블리싱의 차이를 사람(또는 RL-12에 따라 qa-master)에게 확인받았는가?
- [ ] GL-16~20 업무 규칙·기획 의도를 추측하지 않았고(RL-12 위임 범위에서 qa-master가 근거를 기록해 확정한 것은 예외), 선택에 따라 영향이 달라지는 구현 방법은 선택지로 결정받았으며, 검증하지 않은 것을 검증 완료로 쓰지 않았는가?
- [ ] GL-21~25 컴파일·ArchitectureTest·실데이터·화면 확인을 했고, 테스트하지 못한 CASE를 기록했는가?
- [ ] GL-26 워크트리 자가 점검을 통과했는가?
- [ ] GL-27 이미 읽은 단계 문서도 커밋 계획 직전·구현 승인 직전·컨텍스트 압축 뒤 그 단계 행동 때는 다시 읽었는가?
- [ ] GL-28 삭제는 휴지통 이동으로 했고(영구 삭제는 확인 후), 공용 산출 폴더의 상위 폴더를 통째로 지우거나 비우지 않았으며, 삭제 전 파일 수·소유 세션·git·백업을 확인했는가?
- [ ] GL-29 산출물과 소통에 이모지를 쓰지 않았고(상태·강조는 텍스트로), 과장을 줄였으며, 한국어는 seosul-lint로 점검했는가?
