# 7단계 · 브랜치 네이밍

> **목적:** 화면 단위 작업 브랜치의 이름, 커밋 scope, 병합 흐름을 정한다.
> **언제 읽나:** 브랜치 이름이나 커밋 scope를 정하기 직전([00 요약](향상된_AI-DLC_00-핵심규칙요약.md) 2장).
> **이 문서가 정하지 않는 것:** 브랜치를 언제·어떻게 만드는지는 [12단계](향상된_AI-DLC_12단계-워크트리사용규칙.md) WT-02, 커밋 메시지의 나머지 규칙은 [5단계](향상된_AI-DLC_5단계-결과물검토및커밋규칙.md) CM-03~CM-12가 정본이다.

---

## 규칙

### BR-01 · 브랜치명 형식

```
<팀구분>/<이름약자>_dev/<화면ID>
```

| 구성요소 | 의미 | 예 |
|---|---|---|
| `팀구분` | 팀 식별자 | `team2` |
| `이름약자_dev` | 개발자 작업 브랜치 식별자 | `ghbaek_dev` |
| `화면ID` | 화면설계서상의 화면 ID | `screen-020` |

예: `team2/ghbaek_dev/screen-020`

### BR-02 · 화면ID는 그대로 쓴다

화면설계서에 정의된 화면 ID를 축약하거나 변형하지 않는다.

> 워크트리 디렉터리명은 경로 길이 때문에 화면ID를 압축하지만, 브랜치명은 압축하지 않는다(12단계 WT-06).

### BR-03 · 커밋 scope는 화면ID의 마지막 그룹

화면ID를 하이픈(`-`)으로 나눈 마지막 그룹을 커밋 scope로 쓴다. 도메인명·프로젝트명은 scope로 쓰지 않는다.

| 화면ID | scope | 쓰지 않는 것 |
|---|---|---|
| `screen-020` | `deliveryRequestDetail` | `buy`, `mydesk`, `inspection` |

### BR-04 · 정해진 절차 밖에서 브랜치를 만들거나 바꾸지 않는다

12단계 WT-02 절차로 만든 브랜치 외에 임의로 브랜치를 생성하거나 전환하지 않는다. 애매하면 사람에게 먼저 확인받는다. **[사람 확인]**

### BR-05 · 병합 흐름

```
화면별 작업 브랜치            <팀구분>/<이름약자>_dev/<화면ID>
   ├─ ① 병합 → 팀 dev        <팀구분>/dev   (통합 검증용)
   └─ ② 병합 → 팀 main       <팀구분>/main
                  ↓ ③ PR
              루트 main
```

- 이 흐름은 모든 프로젝트 공통이다(사용자 확정 2026-10-24). 팀 dev는 기능 브랜치를 모아 통합 검증하는 용도이며 팀 main으로 PR하지 않는다.
- 화면별 작업 브랜치는 팀 dev가 아니라 `<팀구분>/main`에서 만든다(12단계 WT-02). 팀 dev에만 있는 변경이 화면 브랜치에 섞이지 않게 하기 위해서다.

### BR-06 · 팀 dev·팀 main 병합은 승인 후 developer, 루트 main PR은 사람이 한다 **[사람 확인: 루트 main PR, 승인 기록 없는 병합]**

- ①·② 병합(`<팀구분>/dev`, `<팀구분>/main`)은 qa-master가 승인한 기록이 있으면(2단계 RL-12) 담당 developer 세션이 수행할 수 있다. 승인 기록이 없으면 사람이 한다.
- ③ 팀 main → 루트 main PR 생성·병합과 루트 `main`으로의 병합·push는 AI가 수행하지 않는다. 사람이 한다.
- ①·② 병합 결과의 `<팀구분>/dev`·`<팀구분>/main` push는 같은 qa-master 승인 범위에서 담당 developer가 할 수 있다. `--force`류는 예외 대상이 아니다(11단계 CS-06).
- 병합은 기준 브랜치가 체크아웃된 워크트리가 없을 때 임시 detach 워크트리(`git worktree add --detach`)에서 `merge --no-ff`로 수행할 수 있다. 병합 커밋(11단계 CS-10)과 push를 확인한 뒤 즉시 `git worktree remove`로 지운다(GL-28·WT-14). 위 승인 범위 안에서만 쓴다. 이름은 짧게 한다(예: `t1`, 12단계 WT-03의 임시 detach 워크트리 이름 규칙과 같다).

### BR-07 · 다음 화면으로 넘어가면 처음부터

새 화면 작업을 시작하면 이전 화면의 맥락을 리셋하고 12단계 WT-02(브랜치·워크트리 생성)부터 다시 한다.

---

## 예외

- **화면ID가 없는 작업:** `<화면ID>` 자리에 `<작업명>`을 쓴다(`<팀구분>/<이름약자>_dev/<작업명>`). 작업명은 세션이 정하고 알린 뒤 진행한다(12단계 WT-01).
- **화면 작업이 아닌 커밋의 scope:** 프로젝트에서 정한 기존 scope 규칙을 따른다(5단계 CM-06).

## 부록: 배경

- **왜 이 형식인가:** 상위→하위로 소속·작업자·작업 단위가 드러나서 브랜치명만으로 작업을 추적할 수 있다.
- **상위 원칙:** [1단계](향상된_AI-DLC_1단계-전역제약.md) GL-04·GL-05(지정된 작업 폴더와 브랜치에서만 작업)를 브랜치 관점에서 구체화한 문서다.
- **5단계와의 관계:** 5단계의 커밋 이후 절차(팀 dev·팀 main 병합, 루트 main PR)는 이 문서의 BR-05·BR-06을 인용한다.
