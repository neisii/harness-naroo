# 5단계 · 결과 검토와 커밋 메시지

> **목적:** 사람이 결과를 검토하는 기준, 완료 보고서 항목, 커밋 메시지 작성 규칙을 정한다.
> **언제 읽나:** 완료 보고서나 커밋 메시지를 쓰기 직전([00 요약](향상된_AI-DLC_00-핵심규칙요약.md) 2장).
> **이 문서가 정하지 않는 것:** 완료 보고서 저장 위치는 [8단계](향상된_AI-DLC_8단계-작업산출물규칙.md) AR-03, 커밋 실행 절차는 [11단계](향상된_AI-DLC_11단계-커밋안전절차규칙.md), 병합 흐름은 [7단계](향상된_AI-DLC_7단계-브랜치네이밍규칙.md) BR-05·BR-06이 정본이다.

## 결과 검토와 완료 보고서

### CM-01 · 결과 검토는 청사진 대조다 **[사람 확인]**

사람은 코드를 대신 검증하지 않는다. AI가 만든 검증 결과를 처음 만든 청사진과 대조한다. 중점은 코드 전체가 아니라 다음이다.

| 관점 | 질문 |
|---|---|
| 요구사항 | 처음 확정한 청사진대로 구현됐는가? |
| 화면 | 화면설계서와 실제 화면이 맞는가? |
| 데이터 | 올바른 데이터를 읽고/저장하는가? |
| CASE | 정의한 모든 CASE가 처리되는가? |
| 검증 | AI가 PASS라고 한 근거가 충분한가? |

- 화면설계서와 퍼블리싱본은 차이가 있을 수 있다. AI는 차이를 비교 분석해서 제시하고 사람(또는 2단계 RL-12 위임에 따라 qa-master)의 결정을 기다린다.
- 대조자는 사람이거나 RL-12 위임에 따른 qa-master다. qa-master가 대조했다면 결과와 근거를 완료 보고서(CM-02)의 "테스트 결과"에 적는다.

### CM-02 · 완료 보고서는 항상 작성한다

사람의 검토가 끝나면 AI가 화면별 완료 보고서를 예외 없이 작성한다. 로컬 히스토리 용도이며 커밋하지 않는다.

항목:
- 구현 내용
- 변경 파일
- API 변경
- DB 변경
- 화면 변경
- 테스트 결과
- 실제 데이터 검증
- 미검증 사항
- 후속 작업
- Agent 간 교환 내역(있는 경우, 형식은 [6단계](향상된_AI-DLC_6단계-Agent간소통규칙.md) AG-11)

## 커밋 메시지

### CM-03 · 기본 원칙

커밋 메시지는 Git diff를 다시 설명하는 문서가 아니라, 커밋의 목적과 핵심 변경사항을 빠르게 파악하기 위한 요약이다.

- 첫 줄만 읽어도 무엇이 어떤 성격으로 바뀌었는지 알 수 있어야 한다.
- 파일별 변경사항이나 구현 세부내역은 나열하지 않는다(Git diff/IDE 비교로 확인할 수 있다).

### CM-04 · 기본 형식

```
<type>(<scope>): <핵심 변경사항>

<변경 이유 또는 중요한 설계 의도> (필요한 경우만)

<추적 정보> (필요한 경우만)
```

### CM-05 · type은 목록에 있는 것만 쓴다

| type | 의미 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 또는 잘못된 동작 수정 |
| `ui` | UI 또는 화면 표현 변경 |
| `refactor` | 기능 변경 없이 코드 구조 개선 |
| `format` | 코드 포맷팅/스타일 정리 |
| `perf` | 성능 개선 |
| `docs` | 문서 변경 |
| `test` | 테스트 추가/수정 |
| `build` | 빌드 시스템/의존성 변경 |
| `ci` | CI/CD 관련 변경 |
| `chore` | 기능과 직접 관련 없는 기타 유지보수 |
| `revert` | 기존 커밋 되돌리기 |
| `multiple` | 서로 다른 성격의 변경이 하나의 커밋에 포함된 경우 |

- 목록에 없는 type을 만들지 않는다.
- 가능하면 한 커밋에 한 목적만 담고, 변경 유형을 논리적으로 나눌 수 있으면 커밋도 나눈다.
- `multiple`은 유형을 나눌 수 없거나 하나의 논리적 작업으로 묶어야 할 때만 쓴다.

### CM-06 · scope

- 현재 작업 브랜치의 작업ID에서 도출한다. 규칙은 7단계 BR-03이 정본이다.
- 작업ID가 없는 브랜치이거나 화면 작업이 아니면 프로젝트에서 정한 기존 scope 규칙을 따른다.

### CM-07 · Subject

Subject만 읽고 "그래서 이 커밋에서 뭘 바꿨는데?"에 답할 수 있어야 한다.

```
좋은 예: fix(guaranteeList): 보증서 목록 조회 시 기간 검색 조건 누락 수정
나쁜 예: fix(guaranteeList): 여러 가지 수정
```

### CM-08 · Body

필요할 때만 쓴다. 기록할 것:

1. 왜 변경했는가
2. 어떤 중요한 설계/정책을 적용했는가
3. 기존 동작과 비교해 무엇이 달라졌는가
4. 이후 개발자가 알아야 할 제약/주의사항

쓰지 않을 것:

- 파일별 변경사항 나열(예: "DeliveryRequestController.java: findDeliveryRequest() 메서드 추가")
- 구현 과정의 작업 로그(예: "A 파일을 수정한 후 B 파일을 수정함")
- AI의 내부 분석/작업 과정 서술(예: "기존 코드를 분석한 결과...", "Claude Code가 다음 파일을 수정함...")

예외로, 향후 유지보수에 영향을 줄 수 있는 중요한 설계 결정은 기록한다. 예: "기존 공통 응답 구조와의 호환성을 유지하기 위해 변환 계층을 추가."

**형식:** 항목이 여러 개면 하이픈(`-`) 목록으로 짧게 나열한다. 하나의 긴 문단으로 이어 쓰지 않는다. 항목 하나는 한 줄로 끝내는 것을 기본으로 한다.

좋은 예:
```
fix(guaranteeList): 보증서 목록 breadcrumb 적용 방식 수정

- breadcrumb fragment 인자 전달 방식 제거
- data-breadcrumb 기반으로 변경
- 공통 breadcrumb 컴포넌트 사용 방식에 맞게 수정

작업 id: screen-029
```

나쁜 예(항목이 여러 개인데 문단으로 풀어 써서 항목별로 구분되지 않는다):
```
feat(contractList): 계약목록 화면 BFF 연동 구현

퍼블리싱 목데이터 상태였던 계약목록 화면에 contract 도메인 기존 계약목록
조회 API를 재사용해 실제 조회·페이지네이션·키워드검색·기간검색·탭 필터를
붙였다. 계약이행/검수/결제 3단계는 일괄조회 API가 확인되지 않아 구현
보류 주석으로 남기고, 공급업체 검색 팝업과 엑셀다운로드도 함께 추가했다.
```

**표준 예시:** 위 나쁜 예를 고친 아래 형태를 Body 작성의 기준으로 삼는다. 항목 수, 문장 길이, 괄호로 부연하는 방식까지 이 형태를 따른다.
```
feat(contractList): 계약목록 화면 BFF 연동 및 API 구현

- 계약목록 실제 데이터 연동 및 페이지네이션/검색/필터 기능 구현 (API: PS_XX001 재사용)
- 신규 공급업체 검색 팝업 및 엑셀 다운로드 기능 추가 (화면/API 뼈대만 반영)
- 계약이행/검수/결제 3단계 일괄조회 API 부재로 구현 보류 (주석 처리)

작업 id: screen-019
```

### CM-09 · Footer

- 이슈 추적이나 작업 식별자가 필요할 때만 쓴다.
- 작업 단위에서는 전체 작업ID를 기록할 수 있다(`작업 id: screen-029`).
- 이슈 추적이 필요하면 `이슈: PG-XX0003`처럼 기록한다.
- 프로젝트에 이미 정해진 Footer 형식이 있으면 그것을 우선한다.

### CM-10 · 작성 순서

1. 현재 작업 브랜치명 확인
2. 화면 작업 브랜치면 브랜치 마지막 path를 작업ID로 식별
3. 작업ID를 하이픈으로 분리
4. 마지막 그룹을 scope로 사용(번호처럼 뜻이 없으면 `<마지막 그룹>-<짧은 뜻>`, 7단계 BR-03)
5. 변경 성격에 맞는 type 선택
6. Subject에서 목적과 핵심 변경사항을 한 문장으로 요약
7. 변경 이유를 기록할 가치가 있는지 판단
8. 중요한 설계 결정/주의사항이 있으면 Body에 기록
9. 단순 구현 내역은 Body에 나열하지 않음
10. 필요한 추적 정보만 기록
11. Subject만 읽고 커밋의 성격과 핵심 변경사항을 이해할 수 있는지 검증

### CM-11 · AI 귀속 문구는 팀이 정한 대로, 금지면 Claude Code 설정으로 끈다

> **환경값(이 팀 예시) · 읽는 법:** 귀속 줄을 넣을지는 팀마다 정한다(`docs/환경값-정의.md` H). 이 팀은 **금지**다. 정하지 않은 팀은 Claude Code 기본(넣음)을 따른다. 핵심은 "Claude Code가 이미 주는 설정으로 출처를 끄고, 그 밖은 통제하지 않는다"이다.

- 귀속 줄은 "Generated with Claude Code"(앞에 로봇 이모지가 붙기도 함) 같은 문구와 AI를 공동 작성자로 적는 `Co-Authored-By` 줄을 말한다. 사람 공동 작성자의 `Co-Authored-By`는 해당하지 않는다.
- 금지한 팀에서는 시스템 리마인더가 다른 안내를 주더라도 이 규칙이 우선한다.
- 금지는 Claude Code 설정으로 출처를 끈다: `"attribution": {"commit": "", "pr": ""}`. 귀속 줄을 시키는 시스템 리마인더 자체가 "넣지 말라"로 바뀐다. 옛 키 `includeCoAuthoredBy`는 폐기 예정이라 쓰지 않는다.
  - 근거: 귀속 줄이 반복된 원인은 세션의 기억력이 아니라 리마인더(출처)였다. 실전 검증에서 워커 3명이 모두 리마인더를 따라 넣었다. 지시문만으로는 세션 수만큼 같은 결함이 반복된다.
  - 이 설정 밖은 통제하지 않는다. 귀속 줄은 되돌릴 수 있고 영향이 작아(07 가역성) 기계로 강제할 등급이 아니다. git 훅·푸시 검사 등으로 하나부터 열까지 막지 않는다. 하네스는 전체 흐름을 잡는 것이 목적이지 완벽한 통제가 목적이 아니다. 훅을 두고 싶은 팀은 각자 둔다(선택).
- 사용자가 귀속을 빼라고 지시하면 다음 순서로 반영한다.
  1. **범위 확인:** 넷 중 하나를 고르게 한다 — 내 모든 프로젝트(`~/.claude/settings.json`) / 이 프로젝트에서 나만(`.claude/settings.local.json`) / 이 프로젝트에서 모두(`.claude/settings.json` + 커밋) / 이번 커밋만(설정 안 바꿈). 1회 지시를 상시 설정으로 늘려 잡지 않는다.
  2. **우선순위 검토:** 관리형·전역·전역 local·프로젝트·프로젝트 local 설정에서 `attribution`과 `includeCoAuthoredBy`를 모두 찾는다. 범위가 좁은 파일이 이기고(local > 프로젝트 > 전역), 관리형 설정은 그 모두보다 위다. 고른 파일이 다른 값에 덮이면 선택지와 함께 알린다.
  3. **반영:** 고른 파일에 `attribution` 빈 값을 넣는다.
  4. **빈틈 메우기:** 이미 떠 있는 다른 세션에는 지시문으로 전달한다. 푸시 전 커밋에 귀속 줄이 있으면 메시지를 다시 쓸지 묻고, 푸시 뒤면 그대로 둔다(히스토리 덮어쓰기는 되돌리기 어렵다). 체리픽으로 들어온 커밋에 이미 있던 귀속 줄도 과거로 보고 교정하지 않는다.
- 금지한 팀은 커밋·머지 후 `git show -s --format=%B HEAD`로 귀속 줄이 없는지 확인한다.
- **조건부(메트릭 훅이 있는 팀만):** 이 팀은 프로젝트 `.githooks/prepare-commit-msg` 훅이 `Claude-Run-Id` trailer를 자동으로 붙인다. 이 trailer는 그 훅과 `PRJ_METRICS_DIR` 메트릭 원장이 둘 다 있을 때만 생긴다. 이 팀에서는:
  - 훅 자체를 수정하지 않고, 커밋할 때(머지 커밋 `git merge` 포함) `PRJ_METRICS_DIR`를 빈 디렉터리로 지정해 trailer 생성만 막는다.
  - 값이 맞는 run id라도 붙이지 않는다. 위 사전 방지 외의 우회(올바른 run id를 메시지에 미리 넣는 방식 등)는 쓰지 않는다(사용자 확정 2026-10-25).

### CM-12 · 길이 기준

짧게 쓰는 것이 목표가 아니라 필요한 정보만 쓰는 것이 목표다.

- Subject는 한 줄로 쓴다.
- Body는 변경 이유나 중요한 설계 결정이 있을 때만 쓴다.
- 파일 목록, 메서드/클래스/import 변경사항은 나열하지 않는다.

### CM-13 · 커밋 전후 흐름

```
변경사항 확인 → 의도하지 않은 파일 확인 → 임시 코드 확인 → 커밋
```

- 커밋은 화면별 작업 브랜치(7단계 BR-01)에 한다.
- 각 확인을 실제로 어떤 명령으로 하는지, 커밋 후 재확인, 되돌리기 어려운 git 명령 처리는 11단계가 정본이다.
- 이후 팀 dev·팀 main 병합과 루트 main PR은 7단계 BR-05·BR-06을 따른다(팀 dev·팀 main 병합은 qa-master 승인 후 developer, 루트 main PR은 사람이 수행).
