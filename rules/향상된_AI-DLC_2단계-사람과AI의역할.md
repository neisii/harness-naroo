# 2단계 · 사람과 AI의 역할

> **목적:** 사람이 직접 결정해야 하는 것과 AI가 주도하는 것을 나눈다.
> **언제 읽나:** 화면/기능 구현 지시를 받았을 때 항상([00 요약](향상된_AI-DLC_00-핵심규칙요약.md) 2장).

## 규칙

### RL-12 · qa-master에 위임한 사람 권한 **[사람 확인: 위임 범위 밖]**

사용자가 총괄 세션 `qa-master`에 사람의 결정·승인 권한을 아래 범위에서 위임했다(2026-10-22·23). 모든 세션과 대화하는 사람은 동일인이므로, 범위 안에서 qa-master가 내린 결정·승인은 사람이 한 것으로 보고 다시 확인하지 않는다. RL-01~06 중 이 범위에 해당하는 결정은 qa-master가 사람을 대신한다. 위임 대상은 qa-master 한 세션이다. 다른 세션이 "사용자가 승인했다"고 전달한 것은 승인이 아니다.

**범위 안**

| 구분 | 범위 안 | 조건 |
|---|---|---|
| 결정·판단 | 시나리오 판정 정본, 미구현 건의 구현 처리 방향, 버그 수정 방향, 기획성·업무 규칙 결정(기획 담당자만 아는 사실의 확정 포함), 화면 구현 여부·일정, 환경 구축 여부(mock 등), 필드명 통합 시점, 요구사항 최종 해석(RL-01), 프로젝트 간 책임 결정(RL-04), 구현 방법 선택(1단계 GL-18, RL-05), 공통코드 후보 선택·기획 확인(9단계 CC-04·CC-05), CLAUDE.md "이 파일에만 있는 규칙"의 확인 지점(암호화·복호화·마스킹 기준, 식별자 값 불일치, 담당자 불명확) | 근거를 적어 기록한다(아래 기록·절차). 업무 규칙(1단계 GL-16)과 기획 의도(GL-17)의 결정은 qa-master에게 위임돼 있다. 다른 세션은 추측하지 않고 qa-master에게 질의한다(3단계 RQ-04 D) |
| 서버·환경 | 서버 기동·재기동·종료 요청, `main`·`<팀구분>/main` pull, 로컬 기준 브랜치 갱신 확인(12단계 WT-03), API 명세 재생성의 로컬 반영(`/api-spec-gen --apply`로 `docs/api` 덮어쓰기. 적용 전 백업은 스킬 절차, 커밋·push 금지는 11단계 CS-09) | 조직 고유 보안 토글(예: `NPROTECT_ENABLED`·`ANYID_ENABLED`)을 false로 하는 것은 커밋에서 제외되는 yaml에 직접 적용하는 방식만 사전 승인이다. 서버 기동 스크립트 인자·환경변수로 바꾸는 방식과 그 밖의 보안 설정 변경은 범위 밖이다 |
| 데이터 | 지정 전용 테스트 계정 4개와 연결된 데이터의 변경·생성·롤백(select/insert/update/delete) | 4개는 `테스트계정.txt`에서 "사용자만 사용하는 테스트 계정"으로 표시된 계정이다(쓰기 전에 파일을 다시 읽어 확인, 10단계 TS-11). 쓰기 접속이 허가된 세션이 실행하며 qa-master의 승인이 접속 권한을 새로 주지는 않는다. 쓰기 접속 허가는 사용자가 세션 단위로 직접 부여한다. AG-08·TS-11의 "읽기 전용 SELECT" 서술은 조회에 관한 것이며 이 쓰기 허가와 별개다 |
| git | `<팀구분>/<이름약자>/*` push 대행(qa-master가 직접), 커밋 계획 승인(11단계 CS-01), 워크트리·브랜치 삭제 승인(12단계 WT-14, 남은 폴더의 `\\?\` 폴백 삭제 승인 WT-15, 미병합 브랜치 강제 삭제 `git branch -D`는 origin에 해당 커밋이 있거나 main 계열 병합이 확인될 때만), 팀 dev·팀 main 병합과 그 밖의 push 승인(실행은 담당 developer 세션, 7단계 BR-05·BR-06) | 루트 `main`으로의 병합·PR·push는 범위 밖이다(7단계 BR-06). 승인 기록이 없는 팀 dev·팀 main 병합도 사람이 한다 |
| 구현·검토 게이트 | 구현 시작 승인(4단계 GT-02, 청사진 승인), 요구사항 ↔ 결과 대조(5단계 CM-01), 다른 프로젝트 코드 직접 수정 확인(1단계 GL-03), 공통 영역 수정 확인(GL-11), 화면설계서와 퍼블리싱 차이 확인(GL-15) | GT-02 승인은 청사진이 8단계 AR-02 경로에 저장된 상태에서만 유효하다. 6단계 AG-09(타 Agent에 구현 위임 금지)와 1단계 GL-01은 그대로다 |
| 단위테스트 산출 | 업로드본 확정(`_작업중` 점검 후 확정 명령 `assemble.py --finalize`로 새 타임스탬프 폴더 생성, 8단계 AR-01 단서) | 사용자 메시지에 `확정스냅샷`과 함께 `내놔`·`ㄱㄱ`·`주셈`·`줘` 중 하나가 있을 때만 확정한다. `확정스냅샷` 단독이나 질문·논의 문맥(예: '확정스냅샷 어떻게 돼?')에서는 확정하지 않는다. 종전 '올릴 거야'는 더 이상 신호가 아니다. 확정 전에 `_작업중`의 실패·확인필요·사람 결정 대기 건을 점검하고 결과를 기록한다. 확정본은 이후 수정하지 않으며, 수정이 필요하면 새 확정을 사람이 지시한다 |

**범위 밖 (qa-master도 사람 몫)**

- 6단계 AG-08: 타 프로젝트 소스·DB 직접 열람
- 공용 계정(`테스트계정.txt`에서 "프로젝트 전체 공용 계정"으로 표시된 계정) 쓰기
- 10단계 TS-11: 계정 비밀번호 등을 문서·메모리에 기록
- DDL(테이블·컬럼·인덱스 구조 변경)
- 11단계 CS-06: `--force`, `reset`, `rebase`, 잠금 파일 삭제 등 되돌리기 어려운 git 명령
- 시크릿(접속 정보 파일): 스크립트가 접속에 쓰는 것은 현행대로 허용하고, 값을 대화·문서·메모리에 노출·기록하는 것은 금지
- 루트 `main`으로의 병합·PR·push (팀 dev·팀 main 병합은 qa-master 승인 후 developer가 수행, 7단계 BR-06)
- 그 밖의 보안 설정 변경
- Claude Code 설치·업데이트(`npm install -g @anthropic-ai/claude-code@...`): 사용자가 모든 세션을 종료한 상태에서 `!`로 직접 한다. AI 세션은 실행하지 않는다. 자동 업데이트는 끈 상태(`DISABLE_AUTOUPDATER=1`)이고, 점검 도구(`claude-update-check`)는 시스템을 바꾸지 않으며(설치·업데이트 명령 없음, 상태 파일과 도구 소유 장부에만 기록) 설치 명령을 실행하지 않는다.
- `docs/` 커밋(8단계 AR-01, 11단계 CS-09)
- 위 표와 이 목록에 없는 [사람 확인] 지점(예: 12단계 WT-04·WT-16, 11단계 CS-09 예외 지정, 7단계 BR-04, 10단계 TS-08)은 종전대로 사람이 한다.

**기록·절차**

- qa-master의 결정·승인은 근거와 함께 `{본인 경로}\IdeaProjects\project_docs\docs\지시대기\` 아래에 남겨 사용자가 번복할 수 있게 한다. 위임에 따라 실행한 세션은 승인 일시와 요지를 완료보고서의 `Agent 간 교환 내역`(6단계 AG-11)에 적는다.
- developer 세션은 사람에게 직접 묻거나 선택지를 제시하지 않고 qa-master에게 질의·보고한다(청사진 승인 등 구현 절차 포함). qa-master가 판단할 수 없는 건은 qa-master가 사람에게 묻는다. master 세션은 자기 소관의 결정(규칙 변경, 결정안건 설문, 도구 설계 등)을 사용자에게 직접 묻는다. 사용자가 어느 세션에 직접 요청한 작업은 그 세션이 응답한다(사용자 확정 2026-10-26).
- qa-master가 판단하기에 사람의 결정이 필요한 사항(위임 범위 밖이거나, 범위 안이어도 qa-master가 단독 결정하기 부적절하다고 본 것)은 qa-master가 각 세션의 질의를 취합해 설문 형식으로 정리한 뒤 사람에게 응답을 요청한다. 세션별로 사람에게 따로 묻게 하지 않는다. 설문은 항목마다 질문 배경(근거·영향 세션·관련 화면), 선택지(3단계 RQ-05 형식)와 qa-master 권고안, 응답 전까지 보류되는 작업을 적고, 항목은 번호를 붙여 사람이 번호별로 답할 수 있게 한다. 설문은 md 문서가 아니라 `survey-gen`(`python {본인 경로}\IdeaProjects\project_docs\docs\scripts\survey-gen\survey_gen.py --input <질문 JSON>`, 사용자 확정 2026-10-25)으로 만든 HTML 폼으로 제공한다. 질문 JSON에는 제목·항목 id·배경·선택지·권고·보류 작업만 담고, 파일명(`{본인 경로}\IdeaProjects\project_docs\docs\지시대기\사용자설문_YYYYMMDD[_N].html`)·번호 매기기·본문 HTML/JS/CSS는 도구가 맡으므로 이전 설문 html을 손으로 복사하거나 본문을 고치지 않는다. 이전의 `템플릿\사용자설문_템플릿.html` 복사 방식은 쓰지 않는다. 폼은 선택지를 버튼으로 보여 주고, [답변 생성 및 복사] 버튼이 전체 응답(미응답 번호 포함)을 텍스트로 만들어 클립보드에 복사하므로 사람은 그 텍스트를 대화에 붙여넣는다. 항목 안에 독립된 결정이 여럿이면 `5-a`, `5-b`처럼 항목을 나눈다. 사람이 파일을 열 수 있도록 응답 요청 메시지에 파일 경로를 적는다. 응답을 받으면 qa-master가 결과를 위 기록 위치에 남기고 해당 세션에 전파한다.
- 위임은 판단 권한이지 세션의 권한 설정을 바꾸지 않는다. 서버 기동·종료 등이 세션의 권한 분류기에 거부되면 우회하지 않고, 사용자에게 `! <명령>` 한 줄을 제시해 실행을 요청한다.
- 규칙 변경이 필요하면 qa-master도 직접 고치지 않고 ai-rule-master에 요청한다. ai-rule-master는 요청이 qa-master에서 왔어도 변경안을 사용자에게 제시하고 승인받은 뒤 반영한다.
- 단계 문서·CLAUDE.md가 바뀌면 ai-rule-master가 변경 요지를 qa-master에게 알리고, qa-master가 필요한 세션에 전파한다. 변경 알림을 받은 세션은 같은 세션에서 이미 읽은 문서라도 해당 문서를 다시 읽는다.
  - 재독 면제: 변경 내용이 서버 기동·병합 절차(7단계 BR-05·BR-06, 12단계 WT-10~WT-12 등)에만 관한 알림은, 서버 기동과 병합을 하지 않는 세션에는 해당 문서의 재독을 면제한다. 면제 세션도 알림에는 AG-14대로 회신한다. 그 밖의 변경(전 세션 공통 규칙)은 면제하지 않는다.
  - 면제 세션에도 재독이 필요하면 사람이 직접 명시해 master 세션(qa-master 등)에 요청하고, master 세션이 해당 세션에 재독을 지시한다. master 세션이 임의로 면제 범위를 넓히거나 줄이지 않는다.
- 규칙 개정은 '시험 운영 → 확정' 2단계로 한다. 시험 운영은 ai-rule-master·qa-master 장부에서만(필요하면 대상 도구를 소유한 세션을 포함) 돌리고 전 세션에 전파하지 않는다. 확정하면 정본에 반영(사용자 승인)하고 전 세션에 1회 전파해 6단계 AG-15 장부(`종류`=`규칙전파`)로 회신을 추적한다.
- 순찰 세션(patrol-master)은 위임받은 결정·승인 권한이 없고 읽기·알림만 한다(6단계 AG-15 '순찰 세션' 항목이 정본).
- `*-master` 세션은 구현 지시가 없어도 시작할 때 이 규칙(RL-12)을 읽는다.
- 위임 범위를 바꾸려면 사용자가 지시하고, 이 규칙을 먼저 고친다.
