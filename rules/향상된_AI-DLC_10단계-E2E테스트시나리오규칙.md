# 10단계 · E2E 테스트 시나리오

> **목적:** QA팀이 준 E2E 테스트 시나리오를 실제 구현 코드 기준으로 재검증해 개선된 시나리오를 만드는 방법과, E2E 테스트 계정의 출처를 정한다.
> **언제 읽나:** 시나리오를 작성하거나 E2E 로그인을 하기 직전([00 요약](향상된_AI-DLC_00-핵심규칙요약.md) 2장).

---

## 규칙

### TS-01 · 원본에서는 형식만 가져온다

- 원본의 테이블 컬럼 구성(예: 시나리오ID/분류/우선순위/수행방법/예상결과/수행자~조치상태)과 시나리오ID 접두어 체계(예: `TC-P`/`TC-D`/`TC-G`/`TC-M`)는 템플릿으로 그대로 쓴다.
- 원본의 내용(수행방법·예상결과)은 처음부터 신뢰하지 않고 전부 재검증한다.

### TS-02 · 화면 HTML·JS는 전체를 읽는다

조사 기준은 화면설계서·퍼블리싱본이 아니라 실제 구현 코드다. 대상 화면의 HTML·JS를 처음부터 끝까지 읽는다. 부분 발췌로 판단하지 않는다.

### TS-03 · Java는 필요한 범위만 읽는다

- 시나리오가 서버 응답·계산·권한·상태 분기에 걸릴 때만 읽는다(순수 UI 시나리오는 HTML·JS만).
- 화면 JS가 실제로 호출하는 엔드포인트의 같은 프로젝트(BFF) 컨트롤러 메서드에서 시작해, 호출하는 서비스 메서드까지 끝까지 읽는다.
- 그 아래(공통 모듈·core·타 도메인 Feign)는 호출 계약(요청·응답 형태) 확인에서 멈춘다.

### TS-04 · 코드에서 특히 확인할 것

| 확인 대상 | 판단 기준 |
|---|---|
| 조건 분기 로직 | 어떤 코드값에 따라 어떤 라벨/컬럼이 바뀌는지 변수명·매핑 객체를 직접 읽는다 |
| 이벤트 핸들러 연결 | HTML에 버튼이 있어도 JS에 연결(addEventListener 등)이 없으면 죽은 버튼으로 본다 |
| TODO/백로그 주석 | "아직 구현 안 됨"이라고 코드가 스스로 밝힌 부분을 우선 신뢰한다 |
| 개발용 mock 진입 경로 | 있으면 실데이터 없이 케이스를 재현하는 방법으로 시나리오에 반영한다(팝업 테스트 전용 페이지는 제외, TS-13) |

### TS-05 · 원본 항목을 한 줄씩 세 갈래로 나눈다

| 대조 결과 | 처리 |
|---|---|
| 그대로 맞음 | 문구만 다듬어 유지 |
| 부분적으로 다름 | 실제 구현에 맞게 정정해서 유지 |
| 코드에 기능이 아예 없음 | 새 시나리오에서 제외 |

### TS-06 · 제외는 대조표로 남긴다

- 새 시나리오 표보다 앞에, 원본이 뭐라고 했고 실제 코드는 어땠는지 대조표를 먼저 넣는다.
- 원본에 있는데 코드에 없는 항목을 조용히 지우지 않는다.

> 이유: 문서만 봐도 원본과 달라진 근거가 남아야 한다. 그 차이가 "기획엔 있었는데 개발이 빠뜨린 것"이면 그 자체가 버그·누락 보고 거리다.

### TS-07 · 코드가 검증하지 않는 값은 "검증됨"이라고 쓰지 않는다

- 화면이 실제로 계산·검증하지 않는 값(예: 원본은 "자동 계산된다"고 했지만 실제로는 API 값을 표시만 하는 경우)은 "검증됨"으로 기록하지 않는다.
- 대신 그 사실을 적고 필요한 사전조건으로 남긴다(예: "화면은 재계산하지 않으므로 테스트 데이터 자체의 정합성을 별도로 확인해야 한다").
- 반대로 코드로 확인된 동작은 "실기 확인 필요", "권장" 같은 헤징 없이 단정적으로 쓴다.
- 근거가 부족해 단정할 수 없으면 헤징으로 얼버무리지 않고, 더 조사해 확신을 얻거나 그 항목을 뺀다.

> 1단계 GL-20("검증하지 못한 사항을 검증 완료로 기록하지 않는다")을 시나리오 작성에 적용한 규칙이다.

### TS-08 · 대상 정정이 모호하면 선택지로 확인한다 **[사람 확인]**

사람이 "위치/화면을 잘못 말했다"처럼 정정할 때, 경로만 틀렸다는 뜻인지 화면 자체가 틀렸다는 뜻인지 여러 해석이 가능하면 하나를 골라 진행하지 않는다. 3단계 RQ-05 형식(가능하면 `AskUserQuestion`)으로 확인한다.

### TS-09 · 원본 파일 위치는 사람이 지정한 대로 쓴다

QA팀 원본 파일의 경로·이름은 매번 다르다(예: 다운로드 폴더 하위). 위치를 가정하지 않고 사람이 지정한 경로를 쓴다.

### TS-10 · 신규 시나리오 파일

- 파일명: `{화면ID}-tests.md`. 원본과 같은 이름을 그대로 쓴다(화면ID가 이미 들어 있다).
- 위치: 8단계 통합 경로(AR-01) `<프로젝트>\docs\<팀구분>\<이름약자>\<화면ID>\{화면ID}-tests.md`. 청사진·완료보고서·SQL과 같은 폴더이며 커밋 제외 규칙도 같다.
- 시나리오를 고쳐 새 판을 만들 때는 원본을 덮어쓰지 않고 새 파일로 만든다. 수정 대상이 아닌 시나리오는 원본 그대로 새 파일에 복사해 배치한다.
- scenario-verify 파이프라인으로 검증할 때는 8단계 AR-01 단서에 따라 스킬이 정한 단위테스트 산출 폴더(`project_docs\docs\단위테스트\...`)가 기준이며 위 파일명·위치 규칙은 적용하지 않는다. 스킬을 쓰지 않고 직접 재검증할 때만 이 규칙을 따른다.

### TS-11 · E2E 테스트 계정은 한 파일에서만 가져온다

계정 정보의 출처는 아래 파일 하나뿐이다. 로그인할 때마다 이 파일을 읽어 확인하며, 다른 문서·메모리·이전 산출물의 계정 정보를 출처로 삼지 않는다.

```
{본인 경로}\IdeaProjects\project_docs\docs\테스트계정.txt
```

- **적어도 되는 것:** 로그인 아이디는 시나리오·산출물·SQL에 적어도 된다.
- **적지 않는 것:** 비밀번호 등 그 밖의 계정 정보는 이 문서, CLAUDE.md, 산출물(청사진·완료보고서·시나리오)에 옮겨 적지 않는다.
- **메모리:** 계정 정보를 메모리에 저장하지 않는다. 필요하면 이 파일의 경로만 기록한다.
- **소속 검증:** 계정의 소속(공급업체·수요기관 등)을 검증해야 하는 시나리오는 이 파일의 계정과 개발 DB 조회 결과가 일치하는지 먼저 확인한다(임의 값 사용 금지). 소속·담당자 번호는 문서의 대응표가 아니라 개발 DB 조회 결과를 기준으로 한다.
- **DB 조회 용도:** 테스트 계정 소속 같은 환경 사실 확인에만 쓰고 업무 규칙 판단의 근거로는 쓰지 않는다(개발DB 데이터는 타인의 테스트 부산물일 수 있다). 조회는 공용 개발 DB의 읽기 전용 SELECT로 하며 사전 승인되어 있다(6단계 AG-08).
- **계정이 없을 때:** 이 파일에 없는 계정이 필요하면 임의로 만들거나 추측하지 않고 사람에게 선택지로 확인한다. **[사람 확인]**

### TS-12 · 데이터에 따라 달라지는 값은 N건으로 쓴다 (사용자 확정 2026-10-26)

- 시나리오의 기대 결과에서 건수·합계 등 테스트 데이터에 따라 달라지는 값은 고정 기대로 쓰지 않고 `N건`(데이터 의존 값)으로 쓴다. 코드·설계로 고정된 값(예: 페이지당 건수, 최대 길이)은 대상이 아니다.
- 판정은 건수 자체가 아니라 조건에 맞는 행만 나오는지, 조건을 좁히면 결과가 부분집합인지(예: 전체 ≥ 필터 결과), 요청·표시가 조건과 일치하는지로 한다.
- 수행 결과에는 실제 관측 건수를 기록하되 기대 문구와 어긋나도 실패로 보지 않는다.
- TS-07과 함께 읽는다(건수 기대를 올려 둔 낡은 시나리오를 승계할 때도 건수는 N건으로 고친다).

> 이유: 같은 팝업 시나리오의 건수 기대가 데이터 변경으로 110→181, 69→83, 32→41, 17→21건으로 바뀌는 등 낡은 건수 기대를 승계해 헛 실패·오판이 반복됐다.

### TS-13 · 팝업은 실제 부모창 흐름으로만 검증한다 (사용자 지시 2026-10-30)

- 시나리오 검증에서 팝업은 실제 부모창에서 여는 흐름으로만 검증한다. 팝업 테스트 전용 페이지(개발용 진입·주소를 직접 열기)로 검증하지 않는다.
- 실제 부모창 흐름으로 팝업을 여는 것이 막히면(진입 데이터 부족 등) 전용 페이지로 대체하지 않고 그 사실을 적어 확인필요로 남긴다.

## 부록: 배경

- QA팀은 화면별로 테스트 시나리오 문서를 전달한다(파일명 예: `screen-020-tests.md`). 이 시나리오는 화면설계서를 기준으로 쓰는 경우가 많은데, 화면설계서와 실제 퍼블리싱·구현 사이에는 차이가 있을 수 있다(5단계 CM-01). 그래서 원본이 실제 구현과 맞지 않는 항목이 많이 생긴다.
- 사람이 일일이 대조·수정하는 것은 비효율적이므로, 해당 화면/BFF를 담당하는 AI 세션이 원본을 실제 구현 기준으로 재검증한다.
