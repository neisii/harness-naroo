# 12단계 · 워크트리 사용

> **목적:** 코드 작업을 git worktree 안에서 할 때의 브랜치·워크트리 생성, push, 서버 빌드·구동, 워크트리 삭제 절차를 정한다. 브랜치 생성 시점·절차의 정본이다.
> **언제 읽나:** 코드 작업을 시작하기 전(브랜치·워크트리 생성), 서버를 구동하기 전, 떠 있는 서버로 검증하기 전, 워크트리를 삭제하기 전([00 요약](향상된_AI-DLC_00-핵심규칙요약.md) 2장).
> **이 문서가 정하지 않는 것:** 브랜치 이름 형식은 [7단계](향상된_AI-DLC_7단계-브랜치네이밍규칙.md) BR-01, 산출물 경로는 [8단계](향상된_AI-DLC_8단계-작업산출물규칙.md) AR-01, 커밋 절차는 [11단계](향상된_AI-DLC_11단계-커밋안전절차규칙.md)가 정본이다. 이 문서는 세 문서를 대체하지 않고, 워크트리를 쓸 때 추가로 지킬 절차만 정한다.
> **적용 범위:** 특정 팀에 국한되지 않고 모든 `<팀구분>`(예: `team2`)에 공통으로 적용한다.

---

## 적용 범위

### WT-01 · 워크트리 의무와 면제

워크트리 의무는 **git 저장소 안의 코드·화면 작업**(조사 후 구현·수정으로 이어지는 작업 포함)에 적용한다.

- **면제:** 가벼운 요청(단순 질의응답, 탐색, 오탈자 수정 — CLAUDE.md "필수 선행 조치"의 예외와 같은 기준).
- **면제:** git 저장소 밖 파일의 수정(전역 `CLAUDE.md`, 향상된_AI-DLC 단계 문서 등. 워크트리를 만들 수 없다).
- **면제 아님:** 작업ID가 없는 코드 작업. 브랜치·워크트리·산출물 폴더의 `{작업ID}` 자리에 `{작업명}`을 쓴다(7단계 BR-01 예외, 8단계 AR-01).
  - 작업명은 세션이 작업 내용을 요약한 짧은 영문 이름(예: `fixLoginRedirect`)으로 정하고, "작업명을 X로 하겠다"고 알린 뒤 승인을 기다리지 않고 진행한다.
  - 사람이 작업명 변경을 요청하면 push 전에 브랜치명(`git branch -m`)과 산출물 폴더명을 함께 바꾼다. 워크트리 폴더명은 세션이 그 안에서 작업 중이고 작업이 끝나면 삭제하므로 바꾸지 않는다. 대신 이전 작업명과 바꾼 사실을 산출물 폴더의 완료보고서(8단계 AR-03)에 적는다.
- 면제에 해당하는지 애매하면 묻지 않고 워크트리를 만든다(WT-02). 만드는 비용은 스크립트 한 번이다.

## 생성

### WT-02 · 작업할 때마다 새 브랜치를 만들고 워크트리를 만든다

WT-01 면제 대상을 제외하고, 어떤 작업이든(화면 구현에 국한되지 않고 조사·수정 등 모든 코드 작업) 항상 워크트리 안에서 수행한다. 로컬 체크아웃에서 직접 작업하지 않는다. 기존 체크아웃 브랜치를 재사용하지 않는다.

1. `<팀구분>/main`을 기준으로 `<팀구분>/<이름약자>_dev/<작업ID>` 작업 브랜치를 새로 만든다(이름 형식은 7단계 BR-01).
2. 그 브랜치로, 세션이 바라보는 프로젝트 하위 `.claude\worktrees`에 워크트리를 만든다(WT-05).
3. checkout 전에 sparse-checkout으로 `docs/`를 제외한다(non-cone 패턴: `/*` + `!/docs/`). `.metrics/`는 제외하지 않는다(WT-13).
4. 워크트리의 `.claude\settings.local.json`에 환경변수 `PRJ_METRICS_DIR={본인 경로}\.prj-ai-metrics\<프로젝트>`를 기록한다(원장을 저장소 밖에 기록해 자동커밋을 막는다).
5. 이후 조사·청사진 작성·구현은 모두 이 워크트리 안에서 한다.

### WT-03 · 워크트리는 스크립트로만 만든다

- 위 1~4번은 `<공유문서 루트>\scripts\worktree\new-worktree.ps1`로 한 번에 수행한다.
  ```
  new-worktree.ps1 -Project <자기 프로젝트 폴더명> -Branch <브랜치명> -Name <워크트리명>
  ```
- 기준 브랜치(`-Base`)는 생략하면 `-Branch`의 첫 구간에서 `<팀구분>/main`으로 정해진다(예: `team2/ghbaek_dev/...` → `team2/main`). 로컬에 그 브랜치가 없으면 `main`으로 대체하고 알린다(예: catalog).
- 스크립트는 `git fetch`로 원격을 확인하고, 로컬 기준 브랜치가 `origin`보다 뒤처져 있으면 브랜치를 만들지 않고 중단한다. 이때 로컬 기준 브랜치를 임의로 갱신하지 않고 사람(또는 2단계 RL-12 위임에 따라 qa-master)에게 확인받는다. **[사람 확인]**
- `git fetch`가 실패하면(로그인 만료 등) 아무것도 만들지 않고 중단한다. 사람이 `! git -C <프로젝트 경로> fetch`로 한 번 로그인한 뒤 다시 실행한다.
- 스크립트는 저장소 로컬 설정으로 `core.longpaths=true`를 켠다(WT-06).
- 수동으로 `git worktree add`를 치지 않는다(sparse·env가 빠진다).
  - 예외: 읽기 전용 확인용 임시 detach 워크트리(`git worktree add --detach`, 예: API 명세 생성)는 수동으로 만들 수 있다. 커밋하지 않고 끝나면 즉시 `git worktree remove`로 지우며(GL-28·WT-14), 구현·수정 작업에는 쓰지 않는다. 이름은 짧게 한다(예: `t1`). 긴 이름은 Windows 260자 경로 제한에 걸려 체크아웃이 일부 실패할 수 있다(실제 사례 2026-10-28: `apispec-tmp-20261028`에서 긴 클래스명 소스 파일 미체크아웃, `t1`로 재생성해 해결, api-gen-master 보고).
- 배경(bg) developer 세션은 하네스 격리 없이 기동한다(전역 설정 `worktree.bgIsolation`이 `"none"`). 하네스가 `worktree-<랜덤이름>`으로 자동 격리한 세션을 발견하면 작업을 시작하지 않고 qa-master에게 보고한다.
- 워크트리는 이 절의 `new-worktree.ps1`로만 만들고 `EnterWorktree` 도구로 만들거나 들어가지 않는다. 하네스 격리가 걸리면 docs 원본 경로 쓰기와 `new-worktree.ps1` 실행이 막힌다.
- 가드에 막혀도 Bash heredoc 등으로 우회하지 않고 qa-master에게 보고한다(2단계 RL-12).
- 아래는 `new-worktree.ps1`이 내부에서 수행하는 순서이며 직접 실행하지 않는다. 순서가 중요하다: `git worktree add --no-checkout` → sparse 설정 → `git checkout`. sparse 설정 전에 checkout하면 파일이 전부 펼쳐졌다 지워져 상태가 꼬인다.

### WT-04 · 업스트림을 설정하지 않는다

- 새 브랜치는 `git branch <새브랜치명> <기준브랜치>`처럼 `-t`/`--track` 없이 로컬로만 만든다.
- 만든 직후 `git branch -vv`로 추적 정보(`[origin/...]`)가 없는지 확인한다.
- 추적 정보가 보이면 임의로 해제하지 않고 사람에게 확인받는다. **[사람 확인]**

> 이유: `<팀구분>/main`을 추적하도록 남겨 두면, 이후 브랜치명 없는 `git push`가 의도와 달리 팀 main에 커밋을 올릴 수 있다.

### WT-05 · 생성 위치는 고정이다

항상 세션이 바라보는 프로젝트 루트 하위 `.claude\worktrees`에 만든다. 프로젝트마다 고정이므로 매번 사람에게 확인하지 않는다.

예: buyer-portal에서 작업 중이면 `<워크스페이스>\<프로젝트 루트>\buyer-portal\.claude\worktrees` 하위.

### WT-06 · 워크트리 이름은 작업ID를 압축한다

디렉터리명은 `{작업ID}-{작업명}` 형식이고, Windows 260자 경로 제한 때문에 `{작업ID}`를 압축한다.

- 작업ID를 하이픈(`-`)으로 나눠, 마지막 그룹을 뺀 앞쪽 그룹은 각각 첫 글자만 남긴다.
- 마지막 그룹은 원문 그대로 둔다.

| 작업ID | 압축 | 워크트리명 |
|---|---|---|
| `screen-020` | `b-m-i-deliveryRequestDetail` | `b-m-i-deliveryRequestDetail-{작업명}` |

- 긴 경로 오류를 막기 위해 git 명령에 `core.longpaths=true`를 기본값으로 쓴다(`-c core.longpaths=true` 또는 저장소 로컬 설정, 커밋과 무관). 이 설정에서는 `git status`가 긴 경로 파일을 `AM`으로 잘못 표시하므로 `git add -A`와 `git commit -a`는 쓰지 않는다.

### WT-07 · docs는 항상 원본 절대경로로 읽고 쓴다

워크트리에는 `docs/`가 없다(WT-02 3번). docs 하위(8단계 통합 경로 포함)는 항상 원본 `<프로젝트>\docs\...` 절대경로로 읽고 쓴다.

- 워크트리는 항상 `<프로젝트>\.claude\worktrees\<이름>`에 있으므로 원본 경로는 정해져 있다(예: `...\buyer-portal\.claude\worktrees\X` → 원본 `...\buyer-portal\docs\`).
- 워크트리 안에 `docs\`를 새로 만들지 않는다.
- `docs/publishing-captures/` 같은 팀 추적 문서도 필요하면 원본 경로에서 찾는다. 워크트리에서 안 보인다고 "없다"고 결론 내리지 않는다.

## 작업 중

### WT-08 · Human Gate는 워크트리 안에서도 그대로다

- 청사진 문서화와 구현 착수 승인은 4단계 GT-02·8단계 AR-02를 그대로 따른다.
- 커밋은 11단계(계획 사전 승인, 스테이징 사전/사후 대조 등)를 그대로 따른다. 워크트리라고 완화하지 않는다.

### WT-09 · push는 사람이 한다. qa-master 승인 기록이 있을 때만 예외다 **[사람 확인]**

- AI는 커밋까지는(11단계 절차, 승인 후) 할 수 있지만 원격 push는 임의로 실행하지 않는다.
- push가 필요하면 명령문(예: `git push -u origin <브랜치명>`)만 제시하고, 사람이 `!` 접두사로 직접 실행하게 한다.
- 예외(2단계 RL-12): qa-master가 push를 명시적으로 승인하면 담당 developer 세션이 직접 push할 수 있고, `<팀구분>/ghbaek_dev/*` push는 qa-master가 직접 대행할 수 있다. 승인 일시와 요지를 완료보고서에 기록한다. 루트 `main`으로의 push와 `--force`류(11단계 CS-06)는 예외 대상이 아니다. `<팀구분>/dev`·`<팀구분>/main`에 병합한 결과의 push는 7단계 BR-06의 qa-master 승인이 있을 때만 담당 developer가 할 수 있다.
- push가 인증 실패(로그인 만료 등)로 거부되면 임의로 재시도하거나 자격증명을 바꾸지 않고 중단한다. 사람에게 `! git push ...` 재인증 명령 한 줄을 제시하고, 사람이 한 번 로그인한 뒤 다시 실행한다(WT-03의 fetch 실패 처리와 같은 방식).
- push 거부가 `[rejected] ... fetch first`(non-fast-forward)이면 인증 실패가 아니므로 위 재인증 대상이 아니다. 원격에 없는 커밋이 있어 다시 fetch한 뒤 재병합해야 하는 상황이며, 병합은 7단계 BR-05·BR-06을 따르고 `--force`로 밀어 넣지 않는다(11단계 CS-06).
- `<브랜치명>`은 로컬 브랜치명과 완전히 같은 이름을 명시한다. 이때 처음으로 업스트림이 설정된다(WT-04). 브랜치명을 생략한 `git push`는 제시하지 않는다.
- 커밋 계획 승인(11단계 CS-01)과 별개의, 그다음 게이트다.

## 서버 빌드·구동

### WT-10 · 워크트리 서버는 별도 포트를 쓴다 **[사람 확인: 사용 중일 때, 메모리 경고 시]**

- 기본: 로컬 포트 + 10000(예: 로컬 buy 서버가 8090이면 워크트리는 18090).
- 구동 전에 항상 OS 레벨 포트 조회(Windows는 `Get-NetTCPConnection` 또는 `netstat`)로 해당 프로젝트가 실제로 LISTEN 중인 포트를 확인한다.
  - `sscheck` 스킬의 `server-status.ps1 [-Project <name>] [-Json]`(위치는 스킬 문서가 정본)을 쓰면 7개 프로젝트의 포트·PID·로컬/워크트리 여부·브랜치·HEAD·미커밋 건수·HTTP 헬스를 한 번에 볼 수 있고, 기대 포트(로컬+10000)와 다르면 경고가 나온다. 점유 목적을 판단할 때 이 정보를 활용한다.
  - 이 스크립트는 파일·프로세스·설정을 바꾸지 않는 조회 도구이며, 떠 있는 서버마다 `http://127.0.0.1:<port>/`에 GET을 1회 보낸다. 어느 세션에서나 쓸 수 있다.
  - 같은 스킬의 `server-stop.ps1`은 확인 없이 지정 포트의 서버를 바로 종료한다. 종료는 아래 사용 완료 확인 절차와 WT-12를 따르며, 이 도구의 존재가 그 절차를 대체하지 않는다.
- 기본 포트가 비어 있으면 그 포트로 구동한다.
- 기본 포트가 점유돼 있으면 임의로 다른 포트를 고르지 않고 아래 순서를 따른다.
  1. 점유한 서버가 어느 세션의 어떤 목적인지 먼저 확인한다.
  2. 그 세션에 사용이 끝났는지 묻는다(연결은 6단계 AG-02 승인과 AG-06 handshake 후).
  3. 사용이 끝났으면 그 서버를 종료하고 기본 포트로 재기동한다.
  4. 사용 중이면 사람에게 "끝날 때까지 기다렸다가 재기동할까요?"를 예/아니오로 묻는다.
- 새 서버를 기동하기 직전(포트 확인 뒤)에 `memcheck` 스킬(`<공유문서 루트>\scripts\memcheck\memcheck.ps1`, 읽기 전용)로 여유 물리메모리와 java 프로세스별 사용량을 확인한다.
  - 여유가 서버 기동 기준(2.5GB) 미만이어서 경고가 뜨면 AI가 혼자 진행하거나 중단하지 않고, 결과를 제시해 사람(또는 2단계 RL-12에 따라 qa-master)에게 진행 여부를 확인받는다. 점유 중인 java 서버가 다른 세션 것이면 종료하지 않고 위 점유 절차를 따른다.
  - 테스트·훅(gradle) 실행 전에도 같은 방식으로 확인하되 기준은 4.0GB다.
  - 이미 떠 있는 서버로 검증만 하는 경우(신규 기동 아님)는 적용하지 않는다.

### WT-11 · 서버 빌드·구동은 기존 스크립트로 한다 (워크트리 여부와 무관)

`gradlew`/`bootRun`을 직접 조립하지 않고 `<공유문서 루트>\scripts\PRJ-server`의 스크립트를 쓴다. 로컬 체크아웃에서 띄울 때도 같다.

| 용도 | 스크립트 | 비고 |
|---|---|---|
| 빌드 | `build.ps1 <프로젝트> [-Dir <워크트리경로>]` 또는 `build-<프로젝트>.cmd`(`build-all.cmd` 포함) | `clean build -x test`라 테스트는 돌지 않는다 |
| 구동 | `start.ps1 <프로젝트> [-Port N] [-Dir <워크트리경로>]` 또는 `start-<프로젝트>.cmd`(`start-all.cmd` 포함) | 워크트리에서는 `-Dir`와 **`-Port`를 반드시 함께** 지정한다 |

- `start.ps1`은 `-Port`가 없으면 로컬 고정 포트(buy 8090 등)로 뜨고, 포트가 점유돼 있으면 에러로 끝날 뿐 선택지를 주지 않는다. 그래서 점유 확인(WT-10)은 AI가 구동 전에 한다.
- 스크립트는 출력을 로그 파일(`<프로젝트 루트>\logs\<p>.log`, `<p>-build.log`)에만 남긴다. 결과는 로그 끝부분이나 필요한 줄만 읽는다.
- 프로젝트별 CLAUDE.md·AGENTS.md의 "서버 실행 규칙"(기본 포트를 `curl`로 확인하고 꺼져 있으면 `./gradlew bootRun &` 직접 실행)보다 이 규칙이 우선한다.
- 이미 떠 있는 서버는 다른 세션이 쓸 수 있으므로, 그 세션의 사용 완료를 확인한 뒤에만 종료한다(WT-10).
- 이미 떠 있는 서버로 검증하기 전에 `server-status`의 Branch·Head가 검증 대상 커밋(담당 세션이 알려준 기준 브랜치 최신)과 같은지 확인한다. 다르면 낡은 코드로 검증하지 않고 담당 세션에 재기동을 요청한다(WT-12).
- 서버 구동·병합 현황 보고의 기준 브랜치는 `main`(origin/main)이다. `<팀구분>/main`이 아니며, 작업 브랜치의 기준(WT-02)과 구분한다. 구동 전에 로컬 `main`을 fetch한 뒤 fast-forward로 최신화한다.
- `gradlew`를 직접 실행하는 예외:
  1. WT-14 워크트리 삭제 전 `gradlew clean`
  2. ArchitectureTest와 전체 테스트(`build.ps1`은 `-x test`). `gradlew clean test` 등을 로그 파일로 리다이렉트해 실행하고 결과 XML·`BUILD` 줄 요약만 집계한다.
- 훅·단위 테스트(gradle)는 팀 간에 한 번에 하나만 돌린다. 서버가 떠 있는 동안 gradle 데몬 정리(`gradlew --stop`)는 서버가 같이 죽으므로 하지 않는다.

### WT-12 · 부모 경로 세션은 담당 서버를 직접 띄우지 않는다

- 작업 경로가 부모 `<워크스페이스>\prj`인 세션(프로젝트별 담당 세션이 아닌 루트·검증 세션)은 담당 세션이 있는 프로젝트(admin·buy·catalog·contract·member·sell)의 서버를 포트가 비어 있어도 직접 띄우지 않는다.
- 담당 세션에 "현재 워크트리 기준 재구동"을 요청한다(`SendMessage`, 6단계 AG-02 승인과 AG-06 handshake 후).
- 각 프로젝트 담당 세션은 자기 서버를 WT-11 스크립트로 직접 구동한다.
- 담당 세션이 없는 프로젝트(settlement 등)는 부모 경로 세션이 직접 구동할 수 있다.

## 삭제

### WT-13 · 삭제 직전에 `.metrics`를 일괄 커밋한다

워크트리의 원장은 저장소 밖 `{본인 경로}\.prj-ai-metrics\<프로젝트>\`에 기록돼 자동커밋이 일어나지 않는다. 집계에서 빠지지 않도록 삭제 직전에 매번 아래를 수행한다.

1. 저장소 밖 원장(`ledger-*.jsonl`) 중 워크트리 `.metrics\`의 같은 이름 파일과 내용이 다른 것을 모두 찾는다(이전 달 파일 포함).
2. 저장소 쪽에만 있는 줄이 있는지 줄 단위로 확인한다.
   - 없으면 그대로 복사한다.
   - 있으면 합집합(중복 제거, 원래 순서 유지)으로 병합한다.
   - 확인 없이 덮어쓰지 않는다.
3. 11단계 절차를 그대로 따른다: 커밋 계획(브랜치·파일·메시지) 제시 → 승인 → `git diff --cached --stat` 대조 → 커밋 → `git show --stat HEAD`. 메시지는 기존 템플릿 `chore(metrics): AI 개발 세션 기록`.
4. push는 WT-09를 따른다(기본은 명령문만 제시하고 사람이 `!`로 실행, qa-master 승인 기록이 있으면 예외).
5. 그다음에 워크트리 삭제 확인을 받는다.

- 이 일괄 커밋은 직접 구현·수정하는 프로젝트(sell·buy·admin·contract)만 대상이다(contract는 화면 없는 API 전용이지만 contract-developer가 직접 API·쿼리를 구현·수정한다, qa-master 확인 2026-10-26). member·settlement·catalog처럼 직접 구현하지 않는 프로젝트에서 생긴 `.metrics/`는 커밋하지 않고 버린다(삭제 전 `git restore --staged`로 스테이징을 풀고 내용을 확인한다).
- `.metrics`는 11단계 CS-09 추적 제외 목록에 없으므로 이 커밋은 제외 대상이 아니다. 다만 일반 기능 커밋에 `.metrics/`가 섞이지 않게 별도 커밋으로 나눈다.
- 기능 브랜치 끝(원장 커밋 포함)을 팀 `<팀구분>/dev`·`<팀구분>/main`에 직접 병합하지 않는다. 원장 커밋은 현재 팀 main 끝을 부모로 하는 별도 브랜치에 올려 병합한다. 이 별도 브랜치의 원장 변경은 append-only로만 한다(기존 줄 삭제·순서 변경 금지, 팀 브랜치에 없는 줄만 끝에 추가).
- push 전에 `git merge-tree`로 병합 시뮬레이션을 돌려 원장 줄 수·중복 그룹 수를 측정하고, 기존(병합 전 팀 브랜치) 대비 증가가 없는지 확인해 결과를 보고한다. 중복이 늘면 push하지 않고 원인을 다시 확인한다.
- 여러 화면 브랜치가 같은 원장 파일을 커밋하므로 병합(팀 dev·팀 main은 qa-master 승인 후 developer, 루트 main은 사람 수행, 7단계 BR-06) 때 `.metrics/*.jsonl`이 충돌할 수 있다. 이때는 양쪽 줄의 합집합(중복 제거, 원래 순서 유지)으로 해결한다. AI가 해결을 요청받으면 같은 방식으로 하고, 결과를 알린다.

> 실제 사례(2026-10-28): sell 기능 브랜치 끝을 그대로 병합 시뮬레이션했을 때 원장이 5554→5950줄, 중복 그룹이 0→283으로 급증(단순 이어붙이면 5532그룹). 같은 원인으로 10-27 contract에서도 원장 병합 2건을 되돌렸다(36eb4294·7e394c57). append-only 별도 브랜치로 해결(sell 원장 c9d571d14, buy 원장 59ee583eb, 둘 다 중복 그룹 증가 없음).

> 이유: 원장은 사람과 AI의 대화 이력이며, AI 활용이 개발 생산성에 미치는 영향을 평가하는 지표의 원천이다. 커밋 빈도나 한 번에 커밋하는 양은 중요하지 않고, 전체 이력이 커밋에 빠짐없이 포함되는 것이 핵심이다. 저장소 안에 기록하면 체크아웃한 브랜치마다 원장이 쌓여 브랜치를 전환할 때 방해가 되므로, 저장소 밖에 기록했다가 한 번에 커밋한다.
>
> 원장은 줄만 추가되는 월별 누적 파일이다. 저장소 밖 파일이 이관 시점에 저장소 파일 내용으로 시드됐으므로 보통은 그대로 복사해도 상위집합이다.

### WT-14 · 삭제 실행 순서 **[사람 확인]**

WT-13를 마치고 **사람이 삭제를 확인한 뒤**(또는 qa-master가 승인한 기록이 있을 때, 2단계 RL-12)에만 아래 순서로 실행한다.

1. 워크트리에서 띄운 서버·gradle 프로세스를 먼저 종료한다(파일 잠금 방지).
2. 워크트리 안에서 `gradlew clean`으로 빌드 산출물(`build\`)을 비운다. 추적 파일·산출물은 건드리지 않는다.
3. 본인이 2단계 RL-12의 yaml 방식(조직 고유 보안 토글, 예: NPROTECT·ANYID)으로 수정한 추적 파일이 있으면 `git restore <파일>`로 되돌린다. 본인이 수정한 파일만 되돌리고, 그 밖의 미커밋 변경이 있으면 되돌리지 않고 보고한다.
4. `git worktree remove <경로>`를 실행한다. `--force`는 사람 확인 없이 쓰지 않는다(11단계 CS-06).
5. 4번 후에도 폴더가 남았거나 "Filename too long" 등으로 실패하면 WT-15로 간다.

작업 브랜치 삭제는 `git branch -d`가 기본이다. 병합 여부와 무관한 강제 삭제 `git branch -D`는 origin에 해당 커밋이 있거나 main 계열에 병합된 것이 확인될 때만 qa-master 승인(2단계 RL-12)으로 허용한다. 그 확인이 안 되면 사람이 결정한다.

> 이유: `build\` 안의 중첩 클래스 경로가 Windows 260자 제한을 넘기면(실제 사례: 최장 327자) `git worktree remove`가 실패하거나 폴더가 일부 남는다. 빌드 산출물은 다시 만들 수 있으므로 먼저 비우는 것이 안전하다.

### WT-15 · 남은 폴더는 `\\?\` 경로로 삭제한다 (폴백) **[사람 확인]**

`git worktree list`에서 등록은 사라졌는데 폴더만 남은 경우가 대표적이다. 일반 경로로는 지워지지 않으므로 PowerShell에서 `\\?\` 접두 경로로 `Remove-Item -Recurse -Force`를 수행한다. 되돌릴 수 없으므로 실행 전에 아래를 보고하고 확인받는다. 확인자는 사람 또는 qa-master(승인 기록이 있을 때, 2단계 RL-12)다.

- 남은 폴더의 전체 경로, 파일 수, 최장 경로 길이
- 남은 내용의 분류: 빌드 산출물 / 추적 파일(커밋·push 완료 여부) / 루트 스크린샷·설정 파일 / docs
- 삭제 대상은 그 폴더 하나뿐이며 다른 경로는 건드리지 않는다는 선언

실행 시:

- 삭제 대상이 `<프로젝트>\.claude\worktrees\<이름>` 형태의 단일 폴더인지 실행 직전에 확인한다. 상위 경로(`worktrees` 자체, 프로젝트 루트 등)는 절대 대상으로 삼지 않는다.
- 삭제 후 `git worktree prune`으로 잔여 등록을 정리하고, 폴더가 없어졌는지와 `git worktree list`를 확인한 결과를 사람에게 알린다.
- 작업 브랜치는 이 절차로 삭제하지 않는다. 커밋·push된 브랜치는 폴더가 사라져도 남는다.

### WT-16 · 정해진 시점마다 스스로 점검한다

워크트리 절차는 스크립트와 규칙 준수에 의존하므로, 각 세션은 아래 시점마다 스스로 확인한다. 어긋남을 발견하면 아래 표의 "어긋나면" 열대로 처리한다. 열에 "보고"로 적힌 것은 사람에게 확인받고, "명시"로 적힌 것은 알린다. **[사람 확인: 어긋날 때]**

| 시점 | 확인할 것 | 어긋나면 |
|---|---|---|
| ① 워크트리 생성 직후 | `new-worktree.ps1`로 만들었는가(수동 `git worktree add` 금지), `git sparse-checkout list`에 `!/docs/`, 워크트리 `.claude\settings.local.json`에 `PRJ_METRICS_DIR`, **세션 셸에서 실제 값 출력**(PowerShell `$env:PRJ_METRICS_DIR`, bash `echo $PRJ_METRICS_DIR`)이 `{본인 경로}\.prj-ai-metrics\<프로젝트>`인지, `git branch -vv`에 추적 정보 없음 | 작업을 시작하지 않고 보고 |
| ② 산출물 쓰기 직전 | 쓰려는 경로가 원본 `<프로젝트>\docs\...`인가, 경로에 `.claude\worktrees`가 들어 있지 않은가 | 쓰지 않고 중단 후 보고 |
| ③ 커밋 계획 제시 전 | 스테이징 후보에 `docs/`가 섞이지 않았는가, WT-13 일괄 커밋이 아닌 일반 커밋에 `.metrics/`가 섞이지 않았는가 | 계획에서 걸러내고 걸러낸 사실을 계획에 명시 |
| ④ 작업 중 이상 신호 | 워크트리 안에 `.metrics/` 변경이나 `chore(metrics)` 자동커밋이 새로 생기면 env 누락 신호 | 임의로 원복하지 않고 보고 |
| ⑤ 워크트리 삭제 직전 | WT-13 `.metrics` 일괄 커밋과 push 완료 여부, 삭제 실행은 WT-14 순서(서버 종료 → `gradlew clean` → `git worktree remove`) | 삭제하지 않고 보고 |
