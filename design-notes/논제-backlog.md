## T1 — 하네스 서술 규칙  — 승격 완료(정본) → [문서 08](./08-서술규칙.md)

- **배경:** 쉬운말 치환을 하다 보니, 하네스에 **문서/서술 방식에 대한 규칙**도 필요하다는 생각이 들었다.
  기존 [`쉬운-글쓰기-기준.md`](./쉬운-글쓰기-기준.md)(원칙 0 + 표1·2)가 그 모태.
- **핵심 질문:** "모든 전문용어를 쉬운 말로 바꾼다"가 아니라 — **무엇을 바꾸고, 무엇을 그대로 둘 것인가?**
  (대치 여부의 **선별 기준**)
- **첫 예시:** `cherry-pick`은 **개발자 공용어**라 굳이 대치할 필요 없다(오히려 그대로가 더 명확).
  반대로 `영향 폐포` 같은 건 바꾸는 게 낫다. → 둘을 구분하는 기준이 이 논제의 핵심.
- **생각해 둘 기준(미확정, 설계 시 발전):**
  - 독자가 누구인가(개발자 ↔ 비전문가) — 독자에 따라 "공용어"의 범위가 다름
  - 용어가 **업계 표준 공용어**인가, **우리만 쓰는/모호한 전문어**인가
  - **어른본 ↔ 쉬운말본에서 기준이 달라도 되는가** (어른본은 공용어 유지, 쉬운말본만 전면 대치?)
- **결과(승격됨):** **문서 08이 정본 서술 규칙.** `쉬운-글쓰기-기준`=상세 how-to, `번역투-교정사전`=T2 데이터,
  용어 사전(쉬운-글쓰기 표2)=T1 데이터. `rules/` 이관은 하네스 구성 시.
  - **개별 판정 확정:** `cherry-pick`·`오케스트레이터` 유지, `프리미티브`→**기본 단위**. (08 예시 판정표)
- **상태:** **완료(정본 승격).** 스킬화("서술 린터")는 T2와 함께 추후.

## T10 — 컨텍스트 비우기 시점 (/clear·/compact)  — 신규

- **배경:** 사용자 제안(2026-11-19, 검색 자료 첨부). 대화가 길어지면 매 턴 보내는 맥락이 커져 사용량 한도를 빨리 쓰고, 앞선 잘못된 시도에 끌려 답이 흐려진다. 하네스에는 "언제 비우나"를 다룬 규칙이 없다. 있는 건 비운 **뒤**의 처리뿐이다(6단계 AG: `/clear`로 초기화된 상대와는 handshake를 다시 함, 8단계 AR-13: 새 세션은 인계 문서를 읽음).
- **후보 시점(자료 기준, 하네스 흐름에 대응):**
  - 커밋 직후 다음 작업으로 넘어갈 때 — 하네스의 작업 단위 끝(CS-04 확인 뒤)과 맞음. 맥락은 코드·완료보고서·위임 기록에 이미 남아 있음.
  - 조사에서 구현으로 넘어갈 때 — 하네스의 청사진 승인(GT-02) 시점과 맞음. 조사 결과가 청사진에 정리돼 있으니 그걸 들고 새로 시작.
  - 같은 실패가 3번 이상 반복될 때 — 문서 10 부록 B의 "같은 맥락 검증자는 맹점이 있고 새 맥락이 더 잡는다"와 같은 원리. 실패 로그와 원인 후보만 정리해 새로 묻는다.
  - 비우기 아까운 큰 작업 중간이면 `/clear` 대신 `/compact`(대화를 요약으로 압축).
- **하네스 쪽에서 따질 것:**
  - **비우기 전 조건:** 인계 문서·완료보고서·위임 기록이 최신인지 먼저 확인(핸드오프 규율). 안 남긴 합의는 비우면 사라진다.
  - **무엇이 살아남나:** 비운 뒤 자동으로 읽히는 건 CLAUDE.md와 메모리 목록뿐이다. 핸드오프·규칙 파일은 세션이 찾아 읽어야 한다. 귀속 문구 건(`귀속문구-논의정리.md`)에서 본 "필요한 절만 읽고 지나침"이 비운 직후 그대로 재발할 수 있다 — 꼭 지켜야 할 규칙은 CLAUDE.md나 설정·훅처럼 자동으로 걸리는 곳에 둬야 한다.
  - **누가 실행하나:** `/clear`·`/compact`는 사용자가 치는 명령이라 세션이 스스로 못 할 가능성이 높다(미확인). 그렇다면 세션은 "지금이 비우기 좋은 시점, 인계 문서 갱신 완료"를 알리는 데까지만 한다. bg 워커는 게이트웨이가 세션을 끝내고 새로 띄우는 방식이 대안.
  - **게이트웨이:** 게이트웨이를 비우면 진행 중인 워커들의 상태를 잃는다. 위임 기록·워커 목록을 파일로 다시 읽어 복구할 수 있어야 한다(부록 D의 재시작 복구와 같은 문제).
  - **사용량 기준:** 자료는 "컨텍스트 50~60%를 넘으면 비울 신호"라 한다. 다만 "토큰 과금이 기하급수로 커진다"는 설명은 과장이다 — 턴마다 맥락 전체를 다시 보내니 크기에 비례해 늘어난다. 자동 압축(auto-compact)도 따로 있다. 기준값은 실측으로 정한다.
- **용어 — "새 세션"이 가리키는 것 (2026-11-19, 사용자 요청):** 지금까지 문서에서 "새 세션"을 두 뜻으로 섞어 썼다. ① **새로 실행** — Claude Code 프로세스를 새로 띄움(`claude`, `claude --bg`, 재시작 뒤 실행). ② **맥락 비우기** — 같은 프로세스에서 `/clear`로 대화만 비움. 둘은 무엇이 다시 읽히는지가 다르다.

  | 상황 | 대화 기록 | CLAUDE.md·메모리 목록 | 설정 파일·훅 |
  |---|---|---|---|
  | 새로 실행 | 없음 | 읽음 | 읽음 |
  | `/clear` | 비움 | 다시 읽힘(대화가 새로 시작되므로) | 설정·훅은 세션 중 바뀌면 자동 반영되는 것으로 보임(2026-11-19 시험: local 설정에 훅을 추가하자 새로 실행 없이 바로 동작). 플러그인·스킬은 `/reload-plugins`·`/reload-skills`로 다시 읽음 |
  | `/compact` | 요약으로 바뀜 | 미확인 | 그대로 |
  | `--resume`·`--continue`·session-wake | 이전 대화 복원 | 읽음 | 읽음(새 프로세스) |
  | Claude Code 재시작 | bg 세션은 사라짐, 대화형은 resume으로 복원(부록 D) | 복원 때 읽음 | 복원 때 읽음 |

  쓰는 법: "설정은 새 세션부터 적용"은 ①(새로 실행)을 뜻한다. `/clear`로 충분한지는 미확인이라 확실히 하려면 새로 실행한다. 반대로 "새 세션은 인계 문서를 읽는다"(AR-13)는 대화 기록이 비는 모든 경우 — ①과 ② 둘 다 — 에 해당한다. 앞으로 문서에선 "새로 실행"과 "맥락 비우기"로 나눠 쓰고, 둘 다면 "새 세션(실행·/clear 모두)"이라 적는다.
  확인(2026-11-19): 공유 `.claude/settings.json`을 새로 만들어 `attribution` 빈 값을 넣자, 재시작 없이 같은 세션의 귀속 리마인더가 "넣지 말라"로 바뀌었다(표본 1).
  미확인: 기존 훅을 고치거나 지울 때도 바로 반영되나 · 전역 설정도 같은가 · `/compact` 뒤 CLAUDE.md가 다시 붙나.
- **선택지별 안내 (사용자가 고름, 2026-11-19 사용자 제안):** 비울지 새로 실행할지는 사용자 선택이다. 하네스는 고른 쪽에서 무엇을 하면 안전한지만 알려 준다.

  | 선택 | 하기 전 | 한 직후 | 그다음 지시 |
  |---|---|---|---|
  | 맥락 비우기(`/clear`) | 인계 문서·완료보고서·위임 기록이 최신인지 확인 | 이 세션 중 플러그인을 바꿨으면 `/reload-plugins`, 스킬을 바꿨으면 `/reload-skills`. 설정·훅은 자동 반영(관찰 1회) | "핸드오프 읽고 이어가" — 전체 규칙이 아니라 핸드오프와 지금 할 일의 규칙 절만 |
  | 압축(`/compact`) | 요약에서 빠지면 안 되는 합의는 파일에 먼저 적기 | 없음 | 그대로 이어감. 규칙을 안 지키는 낌새가 보이면 해당 규칙 절을 다시 읽게 함 |
  | 새로 실행 | 비우기와 같음 | 없음(전부 새로 읽음). "이 세션 동안 허용"한 권한은 다시 물어봄 | 비우기와 같음 |

  공통:
  - 다른 세션과 주고받던 중이면 상대에게 handshake를 다시 한다(6단계).
  - 게이트웨이를 비우거나 새로 실행해도 bg 워커는 별도 세션이라 계속 산다. 잃는 건 워커가 있다는 사실이므로, 위임 기록·워커 목록을 파일에서 다시 읽어 복구한다.
  - 대화형 세션 하나를 새로 실행해도 다른 bg 세션은 죽지 않는다. bg 세션이 사라지는 건 Claude Code 자체를 재시작했을 때다(부록 D) — 둘을 섞지 않는다.
- **일부러 걸어 둔 예약·감시 — 비우기 전 사용자 확인 (2026-11-19 사용자 결정):** 한 번 돌고 끝나는 백그라운드 작업·서브에이전트는 다 끝낸 뒤 비우므로 따로 챙길 것이 없다. 문제는 계속 돌라고 건 것(`/loop` 예약, 오래 걸어 둔 Monitor, 정해진 시각에 깨우는 예약)이다. 그대로 비우면 나중에 온 알림을 왜 걸었는지 모르는 빈 세션이 받는다. → 비우기 전에 사용자에게 "끌까, 둘까, 둘 거면 무엇을 위한 것인지 파일에 적을까"를 확인받는다.
  - 세션이 먼저 "지금 비우기 좋은 시점"을 권할 때: 권하기 전에 걸린 예약·감시 목록을 확인하고 함께 묻는다.
  - 사용자가 예고 없이 `/clear`를 치면 세션이 미리 막을 수 없다(사용자 명령). 그때는 `SessionStart`(`clear`) 훅의 첫 안내에 "이전 대화에서 건 예약·감시가 남아 있을 수 있다, 목록부터 확인"을 넣어 사후에 복구한다.
- **자동화 후보 — `SessionStart` 훅:** Claude Code의 `SessionStart` 훅은 시작 이유를 `startup`(새로 실행)·`resume`·`clear`·`compact`·`fork`로 나눠 받는다(2.1.328 설정 정의에서 확인). matcher를 `clear|compact|startup` 등으로 걸어, 대화가 새로 시작될 때마다 "핸드오프부터 읽기, 할 일이 바뀌면 해당 규칙 절 다시 읽기, 플러그인·스킬을 바꿨으면 reload 명령" 같은 첫 안내를 맥락에 자동으로 넣을 수 있다. 사용자가 안내를 외울 필요가 없어지고, 비우기·새로 실행 어느 쪽이든 같은 안내가 들어간다. 한계: `/reload-*`는 사용자가 치는 명령이라 훅이 대신 실행하지 못한다(알려 주는 데까지). 시범은 린터 훅처럼 `settings.local.json`에서 먼저.
  - **2026-11-19 시범 설치(사용자 승인):** harness-naroo `settings.local.json`에 matcher `startup|clear|compact`. 모든 시작에 "핸드오프부터, 할 일이 바뀌면 해당 규칙 절 다시"를 넣고, `clear`·`compact`일 때만 "`/reload-*` 권하기"와 "남은 예약·감시 확인 후 끌지 둘지 묻기"를 더한다. 입력을 흉내 낸 시험은 통과. 실제 `/clear`에서도 안내가 들어옴을 확인(2026-11-21, 첫 응답에 0번 표시).
- **연결:** [T9](#t9--예산-인지-작업-분할-핸드오프-케이던스---신규) 예산 인지 분할(언제 끊고 인계하나 — 이 논제는 그 실행 수단) · 6단계 handshake 재수행 · 8단계 AR-13 인계 문서 · 문서 10 부록 B(새 맥락 효과)·D(재시작 복구).

## T15 — session-stall-check가 "권한 창 대기"와 "게이트 답 대기"를 구분  — 신규 (gate3 소견)

- 배경: 2026-11-21 gate3에서 게이트웨이가 실무자에게 보내기 전 `session-stall-check`를 돌렸는데, 스킬은 `state=blocked`와 `status=waiting`을 한데 묶어 "사람 입력 대기"로만 알려 줬다. 그래서 게이트웨이가 실무자 대화 기록을 직접 읽어 확인하느라 권한 창을 여러 번 더 불렀다.
- 관측(표본 수십 건, 같은 PC·같은 버전): `status=waiting` = 권한 창·입력 창에서 멈춤(사람이 attach해 답해야 함, 메시지가 안 들어감). `state=blocked` + `status=idle` = 턴을 끝내고 답을 기다림(게이트 대기, 메시지를 보내면 깨어남).
- 핵심 질문: 이 구분이 Claude Code 버전이 바뀌어도 유지되나. 둘을 나눠 알려 줄 때 판정 문구(보내도 됨 / 사람이 창을 열어야 함)를 어떻게 쓰나.
- 첫 예시: 실무자가 게이트 보고를 보내고 기다리는 중(blocked/idle) → "보내도 됨". 커밋 명령 권한 창(blocked/waiting) → "사람이 그 세션에서 답해야 함, 메시지는 안 들어감".
- 연결/영향: `skills/session-stall-check/`, 가이드 `docs/오케스트레이션-구성.md` 4걸음, 순찰(0.5.0). auto 모드를 기본으로 하면 권한 창 자체가 드물어져 급하지 않다.
- 상태: **완료(2026-11-22, 0.2.1).** 시험 세션으로 실측 — 권한 창: `state=blocked`·`status=waiting`·`waitingFor="permission prompt"`, 답 대기: `state=blocked`·`status=idle`·`waitingFor` 없음. 스킬은 "창 대기"(메시지 안 들어감, 사람이 세션을 열어 답)와 "답 대기"(메시지를 보내면 깨어남)로 나눠 판정. 6단계 AG-15 재요청 절차·가이드·README도 맞춤. 기록 `tasks/session-stall-check-waitingfor/`.
