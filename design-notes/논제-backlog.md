## T1 — 하네스 서술 규칙  — 승격 완료(정본) → [문서 08](./08-서술규칙.md)

- **배경:** 쉬운말 치환을 하다 보니, 하네스에 **문서/서술 방식에 대한 규칙**도 필요하다는 생각이 들었다.
  기존 [`쉬운-글쓰기-기준.md`](./쉬운-글쓰기-기준.md)(원칙 0 + 표1·2)가 그 모태.
- **핵심 질문:** "모든 전문용어를 쉬운 말로 바꾼다"가 아니라 — **무엇을 바꾸고, 무엇을 그대로 둘 것인가?**
  (대치 여부의 **선별 기준**)
- **첫 예시:** `cherry-pick`은 **개발자 공용어**라 굳이 대치할 필요 없다(오히려 그대로가 더 명확).
  반대로 `영향 폐포` 같은 건 바꾸는 게 낫다. → 둘을 가르는 기준이 이 논제의 핵심.
- **생각해 둘 기준(미확정, 설계 시 발전):**
  - 독자가 누구인가(개발자 ↔ 비전문가) — 독자에 따라 "공용어"의 범위가 다름
  - 용어가 **업계 표준 공용어**인가, **우리만 쓰는/모호한 전문어**인가
  - **어른본 ↔ 쉬운말본에서 기준이 달라도 되는가** (어른본은 공용어 유지, 쉬운말본만 전면 대치?)
- **결과(승격됨):** **문서 08이 정본 서술 규칙.** `쉬운-글쓰기-기준`=상세 how-to, `번역투-교정사전`=T2 데이터,
  용어 사전(쉬운-글쓰기 표2)=T1 데이터. `rules/` 이관은 하네스 구성 시.
  - **개별 판정 확정:** `cherry-pick`·`오케스트레이터` 유지, `프리미티브`→**기본 단위**. (08 예시 판정표)
- **상태:** **완료(정본 승격).** 스킬화("서술 린터")는 T2와 함께 추후.

- **배경:** AI가 자주 쓰는, **한국인에게 어색한 표현**(번역투·과용어)을 자연스럽게 바꾸는 사전/스킬.
  "하나 떠오른 게 있어" — 사용자 제안(2026-11-10).
- **T1과의 구분:** T1=난이도(어려운 전문어), T2=자연스러움(번역투). **필터가 달라 사전도 따로.**

- **상태:** 점검 스킬 **승격 완료** — `skills/seosul-lint/`(구현 정본), design-notes `tools/seosul_linter.py`는 shim. 남은 조각: 사전 확장, rule 결합.

## T8 — 오케스트레이션 구성 층 (0.2.0 우산)  — 신규, 개밥 스펙 수집 중

- **배경:** 0.1.2 개밥(status-relay-rebuild, 2026-11-15)에서 드러난 이음새. per-세션 규율(청사진→승인→구현→검증·가역성·커밋안전·서술)은 빈 저장소에서 **혼자 잘 돌았다.** 터진 건 전부 **"여러 세션을 엮는 구성"** — 이게 0.2.0의 영역. (버전 로드맵: `0.1.x`=규율 층 / `0.2.0`=이 구성 층.)
- **핵심 질문:** 소비 저장소에서 오케스트레이션 환경을 **어떻게 깔거나 면제하고**, 규칙이 전제하는 인프라가 없을 때 어떻게 **축소 모드로 돌릴까?**
- **개밥이 드러낸 핵심 결함:** 규칙이 qa-master·장부(AG-15)·순찰·공유문서 루트가 **이미 있다고 전제** → 빈 저장소에선 "이름만 qa-master일 뿐 규칙의 절반이 안 돈다"(세션 자평). 지금은 사람+세션이 문답으로 **하나씩 짜 맞춘다**(위임기록.md까지 수기 작성).
- **반복된 설정 결정(손으로 짜 맞춘 체크리스트 → 자동 구성 후보):**
  1. 오케스트레이터 정체성·위임 범위 선언·기록(위임기록.md 정식화?)
  2. 전제 인프라를 깔거나 **명시적 면제**: 장부 위치(AG-15)·문의처(AG-16③)·공유문서 루트·순찰
  3. 역할 분리(오케스트레이터 ≠ 구현자 — 자기 승인 방지)
  4. 세션 생성 레시피(모델·권한 모드·AG-16 3줄 지시문·이름)
  5. 오케스트레이터가 자식 메시지에 깨어나는가(개밥 "미확인")
- **가드레일:** 자동 구성은 **바닥 깔고 결정 지점 드러내기까지만.** 위임 자동부여·게이트 자동승인 금지 — 개밥에서 자기승인 거부·"전달된 승인≠승인(RL-12)"은 하네스가 선 지킨 것이지 버그가 아니다.
- **아키텍트가 먼저 정할 열린 결정(이게 정해져야 sub 할당 가능 — AG-16 정본 요건):**
  - "최소/소규모 모드"의 구체(장부·순찰 없이 뭘 켜고 끄나)
  - 위임 범위 선언·기록 포맷
  - coordinator 큐·락·Workflow 연동(T3)
  - 자식 메시지 깨움 메커니즘(폴링 vs 이벤트)
- **연결:** T3(coordinator=디스패치 엔진, 이 층의 한 부품) · T4(의존성 DAG) · 03(사람 병목) · 06(핵심+환경값: 환경값 가이드 패턴을 오케스트레이션 "구성 선언"에 적용).
- **유의:** 개밥 **데이터 1점**(저장소 1·흐름 1). 최소 모드 가이드부터 만들어 **1~2회 더 개밥** 뒤 설계 확정(사전 17번: 실전 검증=쓸만한지·어디 상했는지지 증명 아님).
- **할당 가능성(현재):** "구현"은 불가(정본 없음, AG-16 위반·정체 사고 재현). "transcript+핸드오프에서 설정 결정 초안을 수집·구조화"는 보조 세션에 가능(결정은 비우고 열린 질문으로 표시). 설계 확정 뒤 AG-16 3줄로 쪼개면 조각별 할당 가능.
- **상태:** **설계 확정 + 개밥 1회 검증 통과(2026-11-16).** 정본 [문서 10](./10-오케스트레이션-구성층.md): 최소/소규모 모드 + D-1~D-4 처분(D-1 3층·D-2 위임 목록화만·D-3 coordinator 제외·D-4 깨움 관측 확정) + 부록 A 위임기록 템플릿 + 부록 B·C 개밥 소견. 공개 가이드 `docs/오케스트레이션-구성.md`. `0.2.0` 브랜치(원격 백업됨). **미검증:** 유휴 한계·② 게이트 위임·coordinator 큐·락·장기/다세션 스케일.
