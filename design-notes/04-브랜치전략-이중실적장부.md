# 04 — 브랜치 전략과 이중 실적 장부

> **핵심 한 줄:** 이건 기술 문제처럼 보이지만 **인센티브 문제**다. 세 상태가 하나로 뭉개졌고
> 보상이 마지막 하나(폐쇄망 배포)에만 걸려서, 사람들이 미완성을 main에 밀어넣은 건
> **나쁜 인센티브에 대한 합리적 반응**이었다. 인센티브부터 고치지 않으면 어떤 브랜치 규칙도
> 일정 압박 때 또 뚫린다.

---

## 겪은 상황 (S / 폐쇄망)

- 불명확한 결정·세부 정책·UIUX 전략이 큰 병목이었고,
- 고객은 **폐쇄망에 배포된 것만 "실적"으로 인정** — 배포 전 산출물은 기간 실적으로 안 쳐줌.
- 이게 각 개발자의 **신뢰도를 깎는** 방해 요소였고,
- 일정에 쫓겨 **폐쇄망 미배포 구현/수정이 main·팀 브랜치에 병합**됨 →
  결국 **팀원 본인 작업에도 영향**.
- 폐쇄망은 **불가항력**. 하지만 브랜치 관리 전략은 하네스에 녹이고 싶다.

## 진단: 세 상태가 뭉개졌다

원래 구분돼야 할 세 상태:
1. **완료·검증됨** (verify 게이트 통과)
2. **통합됨** (main/팀 브랜치 병합 — 남 코드와 합쳐짐)
3. **배포됨** (폐쇄망 = 고객 인정 실적)

고객이 **3번에만 실적**을 줬고 그게 신뢰도까지 깎으니, 사람들이 **1번도 안 끝난 걸 2번(main)에**
밀어넣어 진척처럼 보이게 했다. 부주의가 아니라 **합리적 반응**.

> 쉬운 예로, '**손님상에 나간 것만** 매출로 쳐준다'니까 다들 급해서 **아직 안 끝난 음식을 공용 작업대(main)에
> 그냥 올렸다** — 남들 요리까지 망치면서. 게으름이 아니라 **규칙이 그렇게 시킨 것**이다.

> **원리: 규칙은 인센티브를 이기지 못한다.** 인센티브를 안 고치면 좋은 브랜치 규칙도 또 뚫린다.

## 1순위: 브랜치 규칙이 아니라 "내부 실적 장부"

고객의 "폐쇄망만 실적" 규칙은 불가항력이라 못 바꾼다. 하지만 **내부 신뢰 신호는 통제 가능**.
작업 항목마다 **두 마일스톤**을 장부에 기록:
- `검증완료` (verify/시나리오 게이트 통과 시각) ← **내부 실적으로 인정**
- `폐쇄망배포` (실제 배포 시각) ← 고객 실적

→ 개발자가 "검증은 끝났는데 배포가 안 돼 티 안 나는" 상태를 **main 오염 없이 증명** 가능.
main에 밀어넣을 동기 자체가 사라짐. 기존 AG-15/pending-status-check 장부의 자연스러운 확장.

> 비유하자면, **'검증 끝남' 표시**와 **'손님상에 나감' 표시**를 따로 **남긴다**(장부에 두 번).
> '검증은 끝났는데 배포가 안 돼 티 안 나는' 사람도 **작업대를 더럽히지 않고** 증명된다.

## 2순위: 폐쇄망에 맞춘 브랜치 모델

폐쇄망은 **연속 배포 불가**(배포가 주기적·배치·수동)라 GitFlow도 트렁크 기반도 그대로는 안 맞음.
배포를 **릴리스 트레인**으로:

```
main          = 폐쇄망 반영본 (실제 배포된 진실). 안정. 팀원은 여기서 분기.
integration   = 검증 통과분 누적 / 일회용 합치기 (→ 문서 05)
feature/*     = 워크트리 격리
release/폐쇄망-YYYYMMDD + tag  = 배포 단위 = 실적 단위
```

**이 모델이 문제를 없애는 이유:**
- **main = 배포된 것**으로 고정 → "main 병합 = 배포 주장" → **거짓 실적이 구조적으로 불가능.**
- **팀원이 main(=실제 배포본)에서 분기** → 남이 밀어넣은 미배포·미완성 코드가 내 기반을 깨는 일 소멸.
- 고객의 "폐쇄망만 실적" ↔ "main/tag만 실적"이 **1:1 정직 매핑.**
- "병합됐지만 미배포"는 integration에 **눈에 보이게 격리.**

> 쉬운 예로, 공용 작업대(main)엔 **'진짜 손님상에 나간 것만'** 둔다 → 깨끗하다.
> 남들이 거기서 시작하니 **반쯤 된 음식이 내 일을 망치는 일**이 사라진다.

## 하네스 반영 (BR 규칙, 계획 — 공개판에 없음)

- **BR: main은 폐쇄망 반영본만.** 미배포 변경의 main 직접 병합 금지.
- **BR: integration 진입은 verify 게이트 통과 필수.** (실적 압박성 조기 병합 차단)
- **BR: 폐쇄망 배포 = 릴리스 트레인.** `release/폐쇄망-<date>` + tag.
- **AR/실적 장부: 이중 마일스톤**(`검증완료`/`폐쇄망배포`).
- worktree 격리 기간을 늘려 integration 전까지 팀 브랜치 미접촉.

## 하네스가 못 하는 것 (정직하게)

- 고객의 "폐쇄망만 실적" 규칙 자체는 못 바꿈 — 내부 신호로 **완충**만.
- 불명확한 결정·정책·UIUX 병목은 **브랜치로 안 풀림** → 문서 03(비동기 검수)이 담당.

## 결정 (2차 검토) — 확정(도장) 두 번 채택 + "검수는 두 곳에서"

**이중 실적 장부(확정 두 번) 채택.** 식품 공장↔식당 비유로 보면, 두 확정은 **서로 다른 주체의 검수**다:

- **① 공장 QC = "검증완료" 확정.** 재료(기능)가 **납품 가능한 상태**인지 **만든 쪽**이 검증. = 기능별 verify 게이트.
- **② 식당 주방 검수 = "손님상에 나가도 되는지".** 납품된 재료가 **이번 요리에 실제로 쓰여도 되는지**,
  **내는 쪽(식당=통합 측)**이 **의무적으로** 다시 검수. = 릴리스 후보 재검증(문서 05).

**핵심:** 공장 QC를 통과했어도(=검증완료), **식당은 손님상에 내기 전 반드시 주방을 거친다.** 즉
**"검증완료 ≠ 이번 릴리스에 바로 써도 됨".** 그래서 **두 번째 확정(폐쇄망배포) 직전에 주방 검수(재검증)가 반드시 들어간다.**
→ 04는 **"검수가 두 곳"이라는 개념**만 소유한다. **재검증의 "범위·방법"과 "왜 필요한가"(낡은 정보·얽힘)는 문서 05.**

→ 이로써 문서 04(확정)와 문서 05(재검증·얽힘)가 **한 그림**으로 닫힌다:
**공장 QC(확정①) → [식당 반입] → 주방 검수 = 재검증 → 손님상 = 배포(확정②).**

## 내가 정할 것 (남은 것)

- ✓ **결정(2차 검토): `main`은 "손님상에 나간 것만"(폐쇄망 반영본)만 둔다.**
  거짓 실적 구조적 차단 + 팀원이 **깨끗한 배포본에서 분기**. hotfix는 main 분기 → 배포 → 머지백.
- **이 규칙들이 범용본에서 어떻게 일반화되나?** `폐쇄망배포`→`프로드 배포/릴리스`,
  `실적=배포`→`조직별 done-done 기준`. (문서 06)
