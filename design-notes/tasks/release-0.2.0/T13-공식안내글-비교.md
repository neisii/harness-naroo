# T13 — 공식 활용 안내 글과 하네스 0.2.0 비교 (2026-11-22)

> 비교 대상: "Getting the most out of Opus 5.5 in Claude and Claude Code"(Addy Osmani, claude.dev Blog, 2026-09-22, https://claude.dev/blog/getting-the-most-out-of-opus-5-5/). 글은 웹 읽기 서브에이전트가 전문을 받아 요약했고, 아래 인용은 그 보고에서 옮긴 것이다(직접 확인 등급은 "글이 그렇게 말한다"까지).
> 하네스 쪽 대상: `0.2.0` 브랜치 `b5806ce`의 규칙·스킬·가이드.

## 결론

- **충돌은 하나, 정할 것이 하나다.** 글은 "길게 맡기되, 파괴적 명령에는 권한 창을 켜 둬라"고 하고, 하네스 0.2.0 가이드는 "권한 모드 기본 auto"다. auto에서 파괴적 명령이 어떻게 처리되는지 하네스는 아직 확인하지 않았다.
- **나머지는 겹치거나, 하네스가 규칙으로 더 강하게 만든 것이다.** 완료 기준 명시, 파괴적 일 전에 멈춤, 서브에이전트 결과의 근거 확인, 진행 상황을 파일로, 확인 못 한 것 표시, 리뷰 패스 — 하네스는 이것들을 권장이 아니라 게이트·규칙·기록으로 둔다.
- **하네스만 더하는 것:** 전체 정합성(합친 결과를 다시 테스트), 청사진 단계의 사람 게이트, 가역성 판정과 판정 근거 JSON, 자기 채점 금지, 별도 세션 여럿을 엮는 구성(게이트웨이·위임기록), 한국어 서술 규칙, 환경값. 글은 별도 세션을 여럿 엮는 이야기를 하지 않는다(서브에이전트까지).
- **글에만 있고 하네스가 받아들일 만한 것:** 넷(아래 3절). 하네스가 다시 만들 필요 없는 플랫폼 기능(빠른 모드, 모델 전환 설정, 차트 첨부 등)은 받아들이지 않는다(하네스 원칙: 플랫폼 기능은 쓰고 다시 만들지 않는다).
- 글이 지우라고 한 "think carefully", "step by step" 같은 문장은 하네스 규칙·스킬·가이드에 없다(grep 확인).

## 1. 겹치는 것 — 하네스가 이미 하는 일

| 글의 권장 | 하네스 0.2.0 | 차이 |
|---|---|---|
| "done"이 무엇인지 말하고, 언제 멈춰 물을지 정한 뒤 맡긴다 | 청사진(고칠 파일·테스트 계획·사람이 정할 질문) → 사람 승인(GT-02) | 하네스는 구현 전에 한 번 멈춘다. 글은 기본적으로 멈추지 않고 끝까지 가게 한다 |
| 삭제·force push·저장소 밖 변경 전에는 멈추고 묻는다 | GL-28(삭제는 휴지통, 영구 삭제는 확인 뒤), CS-06(위험 git 명령은 사람), WT-09(push), 가역성 판정의 거부권 | 하네스는 "파괴적인가"를 기준 4개로 판정하고 근거를 JSON으로 남긴다 |
| 큰 일은 서브에이전트로 나누고, 각 결과의 근거를 확인한 뒤 받는다 | 새 맥락 재검증(dlc-gate), 6단계 서브에이전트 위임, 게이트웨이의 직접 확인 | 하네스는 별도 세션까지 쓴다(게이트를 여러 번 오가야 하는 일) |
| 할 일 목록을 파일에 두고 그 파일로 진행을 본다(긴 실행은 맥락이 요약되므로) | 인계 문서(AR-13), 완료보고서, 위임기록, 대기 장부(AG-15), 이 저장소의 HANDOFF | 같은 원리. 하네스는 맥락 비우기·압축 뒤 처리까지 다룬다(backlog T10) |
| 끝나면 "사람에게 필요한 것"부터 읽는다. 요약 머리를 CLAUDE.md로 정할 수 있다("Blocked on me, Changed, Found") | 결정은 배경·선택지·추천과 함께 모아 묻는다(RL-12, survey-gen), 완료보고서 항목(CM-02) | 하네스엔 게이트 보고의 고정 머리가 없다(3절 후보) |
| 사람이 보기 전에 리뷰 패스(병합을 막을 문제만, 파일·줄, 실패를 보이는 법) | 커밋·완료 직전 새 맥락 재검증(규칙 기준 항목별 통과·실패와 근거) | 하네스는 필수, 글은 사용자가 요청할 때 |
| "확인하지 못한 것은 표시하고, 어디를 봤는지 말하라" | GL-20 근거 등급(직접 확인 / 겪은 일 / 추론·미확인), 6장 증거 인용 | 하네스가 규칙으로 고정 |
| 실행 중에 지시를 덧붙인다(다시 시작하면 비용이 크다) | 가이드 4걸음 "Esc로 끊어도 메시지는 전달된다" | 하네스는 주의만 적음 |
| 프로젝트에서 "정해진 답은 다시 따지지 않는다"를 알려 준다 | HANDOFF의 "재논의 불필요" 절 | 같은 원리(이 저장소의 작업 관행) |

## 2. 하네스만 더하는 것

- **전체 정합성:** 작업마다 통과해도 합친 결과를 다시 테스트한다(9장, gate3의 merge-tree 사전 계산). 글의 리뷰 패스는 브랜치 하나의 diff를 본다.
- **청사진 단계의 사람 게이트:** 업무 결정(예: 할인율)은 되돌릴 수 있어도 AI가 정하지 않는다. 글은 "파괴적인가"만 멈춤 기준으로 든다.
- **가역성 판정 + 판정 근거 기록:** 멈출지를 기준 4개로 정하고, 나중에 사람이 diff 없이도 따라갈 수 있게 남긴다.
- **자기 채점 금지:** 만든 세션은 승인하지 않는다.
- **별도 세션 여럿 엮기:** 게이트웨이 세션, 위임기록, 좁은 위임, 세션 상태 확인·깨우기.
- **한국어 서술 규칙과 린터, 환경값(규칙은 고치지 않고 값만 바꿔 읽기).**

## 3. 글에만 있는 것 — 받아들일 후보

| # | 글의 권장 | 하네스에 넣는다면 | 시점 제안 |
|---|---|---|---|
| ① | **파괴적 명령에는 권한 창을 켜 둔다**("keep going" 규칙을 써도) | 가이드 3걸음 "권한 모드": auto로 띄워도 파괴적 명령(`rm -rf`, `git push --force`, `git reset --hard` 등)은 설정의 확인(ask)·거부(deny) 규칙에 넣어 둔다. **auto가 이 규칙을 따르는지는 미확인** — 확인 뒤 적거나, 미확인 꼬리표를 달아 적는다 | **태그 전 권장** (0.2.0의 auto 기본값과 직접 닿음) |
| ② | **멈춰서 보고만 하는 버릇을 지시로 막는다**: 사람 입력이 필요 없는 단계면 계속 가고, 상태는 다음 행동과 같은 메시지에. 파괴적 일 전과 막혔을 때만 멈춘다 | 실무자 지시문(가이드 3걸음 ②)에 한 줄: "게이트가 아니면 멈추지 말고 계속한다. 상태 보고는 다음 행동과 함께." | 태그 전 가능(문서 한 줄) |
| ③ | **보고 머리를 고정한다**("Blocked on me, Changed, Found") | 게이트웨이가 사람에게 올리는 보고 머리를 "사람이 정할 것 / 바꾼 것 / 찾은 것"으로 고정(위임기록 템플릿 또는 dlc-gate) | 공개 뒤(0.4.0 비동기 검수와 함께 설계) |
| ④ | **메시지가 걸리면(flag) 이전 모델로 바뀌어 이어진다** | 가이드 "알아둘 것"에 한 줄: 긴 백그라운드 실행 중 모델이 바뀔 수 있으니, 이상하면 세션의 모델을 확인한다. 백그라운드 세션에서도 그런지는 미확인 | 공개 뒤(관측 뒤) |

받아들이지 않는 것: "think hard" 문장 지우기(하네스에 없음), 디자인 스타일 금지 목록(하네스 범위 밖, 다만 번역투 사전이 같은 원리 — "피할 것을 구체적으로 적는다"), 차트 첨부·완성 파일 요청·빠른 모드·모델 선택기(플랫폼 사용법).

## 4. 하네스의 자리 (README·문서 01에 쓸 수 있는 한 줄)

모델 제공자의 권장은 "길게 맡기고, 멈출 곳을 정하고, 결과를 확인하라"다. 하네스는 그 권장을 SI 팀이 매번 지키게 규칙·게이트·기록으로 고정하고, 거기에 두 가지를 더한다: 작업 하나가 아니라 **합친 전체**를 확인하는 것, 그리고 **여러 세션**을 사람 결정 아래 엮는 것.

## 5. 후보 ① 확인 결과 (2026-11-22, Claude Code 공식 문서)

claude-code-guide 서브에이전트가 공식 문서를 읽어 인용과 함께 보고했다. 직접 확인 등급은 "문서가 그렇게 말한다"이다.

- auto = 분류기 모드. force push·`git reset --hard`·`git clean -fd`·`git stash drop`·세션 전 파일의 비가역 삭제 등을 기본으로 막고, 핵심 경로 삭제(`rm -rf /` 등)는 허용 규칙으로도 못 푼다 — [Permission modes](https://code.claude.com/docs/en/permission-modes.md)
- 거부(deny) 규칙은 모든 모드에서 막는다. 적용 순서 거부 → 확인 → 허용 — [Permissions](https://code.claude.com/docs/en/permissions.md)
- 확인(ask) 규칙은 auto에서도 권한 창을 띄운다 — [Permission modes](https://code.claude.com/docs/en/permission-modes.md)
- 백그라운드 세션은 권한 창에서 기다린다(`blocked` / 입력 필요), 거부되지 않는다 — [Agent view](https://code.claude.com/docs/en/agent-view.md). 거부시키는 설정 `permissions.denyInsteadOfPrompting`(사용자·관리 설정) — [Settings reference](https://code.claude.com/docs/en/settings-reference.md)
- Bash 규칙은 명령 글자 기준이라 보안 경계가 아니다, 확실한 경계는 샌드박스 — [Permissions](https://code.claude.com/docs/en/permissions.md)
- 문서에 없음: 작업 폴더 안 `rm -rf`의 분류기 검토 여부, 분류기 연속 차단 뒤 백그라운드 세션 동작, 분류기와 PreToolUse 훅의 순서. `claude --bg`가 `--permission-mode`를 받는 것은 gate3에서 실제로 동작함(겪은 일).

**판단:** 0.2.0 가이드의 "auto 기본 + 꼭 막을 장치"는 문서와 맞는다. 글의 "파괴적 명령에 권한 창 유지"는 대화형 세션용이고, 백그라운드 실무자에게는 거부 규칙 + 분류기가 맞다(확인 규칙은 멈춰 기다리게 만든다). 가이드 3걸음 "권한 모드"에 출처와 함께 반영함(사용자 승인).
