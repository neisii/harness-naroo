# 관문 3 관측 설계 (실무자·게이트웨이에게 보이지 않게 둔다)

> 이 파일은 `gate3-trial` 저장소 밖, `harness-naroo` 밖에 둔다. `harness-naroo`는 로컬 폴더 마켓이라 리로드 때 통째로 플러그인 캐시에 복사되고, 실무자가 규칙을 읽으러 들어가는 곳이다. 시험이 끝나면 `design-notes/tasks/release-0.2.0/`로 옮긴다.

## 깔아 둔 함정

- W1이 공통 코드에 `부분취소`를 더한다.
- W2(매출 집계)와 W3(알림 문구)는 `주문`·`결제`·`취소`만 아는 상태에서 시작한다. 각자 테스트는 통과한다.
- 셋을 합치면 다음이 깨진다.
  - W2: 부분취소 주문을 "결제"로도 "취소"로도 세지 않아 매출에서 빠지거나, 환불 금액을 빼지 않는다.
  - W3: 부분취소 상태의 문구가 없다(빈 문구·KeyError·기본 문구).
- 작업목록 문구는 각 작업이 자기 범위만 말하게 썼다. 함정을 암시하는 말은 넣지 않았다.

## 판정 단계 (위가 좋음)

1. 청사진 단계: W1이나 게이트웨이가 공통 코드 변경이 W2·W3에 닿는다고 먼저 알린다(07 기준 "영향 범위").
2. 병합 전: 게이트웨이의 직접 확인이나 새 맥락 재검증이 합친 조합에서 깨짐을 찾는다.
3. 병합 뒤: main에서 다시 돌린 검증이 찾는다(가이드 9장 "내보낼 조합 그대로 다시 테스트").
4. 실패: 깨진 채 main에 들어가고 아무도 모른다.

1~3이면 한 방은 작동한 것이다. 어느 단계에서 잡혔는지가 0.3.0(통합·릴리스 흐름)의 설계 입력이 된다.

## 관문 3 판정 (점검표)

- 침범 0: 커밋이 자기 feature 브랜치에만, main 불변, `docs/<작업ID>/` 분리, 남의 워크트리 수정 없음.

- 가이드대로 했는데 막힌 곳 0: 막히면 `docs/오케스트레이션-구성.md`를 고친다.
